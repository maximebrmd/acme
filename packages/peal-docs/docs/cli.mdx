`peal` works with a Peal instance from a terminal. It signs in as you, in a browser, and then acts with your role in each of your workspaces: it writes and discards drafts, uploads and imports media, schedules, publishes, moves and cancels posts, follows up on those that went out, reads analytics, billing, members and invitations, invites people, and saves a copy of your data. Connecting channels and changing roles stay in the web app. A script or an agent that nobody attends runs it with a workspace's [API key](#api-key) instead of a sign-in, and reads its answers as [JSON](#json).

## Get it [#install]

There are no released builds yet. Build it from a clone of the repository, with Bun installed:

```sh
bun install --frozen-lockfile
bun nx run peal-cli:build
packages/peal-cli/dist/peal --help
```

`packages/peal-cli/dist/peal` is one file with Bun inside: copy it anywhere on your `PATH`.

## Choose the instance [#instance]

Point `peal` at the address you open Peal at, such as `https://peal.example.com`, with `--api-url` or `PEAL_API_URL`. The flag wins; without either, `peal` uses `http://localhost:3000`, a server running from source.

`peal` sends your sign-in or an API key over HTTPS, or to this machine (`localhost`), alone: over plain HTTP anywhere else, anything on the way could read them, so the command is refused before it sends any, and `peal doctor` says so. For a self-hosted server on a network you trust that has no TLS, pass `--insecure-http`, or set `PEAL_INSECURE_HTTP=true`.

```sh
export PEAL_API_URL=https://peal.example.com
peal health
```

`peal health` says whether the instance answers. It exits with 0 when it does, and with 1 when it is unreachable (after 5 seconds) or answers with an error, so scripts can wait on it. `peal health --json` prints what it measured, `{"healthy": true, "milliseconds": 12, "url": "https://peal.example.com"}`, and [`peal doctor`](#doctor) checks the rest of the setup.

## Sign in [#login]

```sh
peal login
```

`peal login` prints an address and a code of eight letters and digits:

```text
To sign in to https://peal.example.com, open https://peal.example.com/device in a browser and enter the code WDJB-MJHT.
Or open https://peal.example.com/device?user_code=WDJBMJHT, where the code is filled in.
Waiting for you to approve the sign-in (the code works for 10m)…
```

1. Open the address. Sign in to Peal there if you are not signed in yet.
2. Check that the code matches the one in your terminal, then choose **Allow**. Approve only a code you asked for yourself: whoever started the sign-in gets your access.
3. Back in the terminal, `peal login` says where it saved the sign-in.

The code works for 10 minutes. **Deny** refuses the sign-in, and `peal login` stops.

When your account has [two-step verification](/settings#two-step) on, the browser asks for the code from your authenticator app, or a recovery code, when you sign in there; the command does not change. In a workspace that [requires it](/settings#require-two-step) while your account does not have it on, every command is refused, and says so: turn it on in the web app's account settings, then run the command again, with the same sign-in. `peal doctor` names such a workspace. No command manages two-step verification, and with `PEAL_API_KEY` nothing changes: keys are not concerned.

`peal` asks to do what your role allows in your workspaces, to schedule and publish posts, and to stay signed in. A sign-in made before `peal` asked for publishing does not hold it: the commands that put posts out then say so, and ask you to run `peal login` again and approve it. It saves the sign-in for that instance in `credentials.json`, which only you may read, in the first of these folders that is set:

- `PEAL_CONFIG_DIR`;
- `$XDG_CONFIG_HOME/peal`;
- `%APPDATA%\peal`, on Windows;
- `~/.config/peal`.

Each instance has its own sign-in, keyed by its address, so you can be signed in to several. `peal` renews its access on its own; it never prints its tokens.

## Who am I [#whoami]

```sh
peal whoami
```

```text
Signed in to https://peal.example.com as Sam Example <sam@example.com>.
Workspaces:
  Studio (owner)    studio   7c9e6679-7425-40de-944b-e07fc1f90ae7
  Clients (editor)  clients  3f2b8a41-5d6c-4e7f-8a9b-0c1d2e3f4a5b
```

Each workspace comes with its slug and its id, which `--workspace` takes. With an [API key](#api-key), a key being nobody, `peal whoami` says which key it is instead, through `GET /api/credential`: its name, its workspace's name and id, its permissions and when it expires, never the key.

```text
The API key in PEAL_API_KEY is "nightly" (peal_AbCd…), of the workspace Studio (7c9e6679-7425-40de-944b-e07fc1f90ae7), on https://peal.example.com.
Permissions: channel:read, post:read, post:create.
It never expires.
```

When the sign-in no longer works, because it was revoked or your account was banned, `peal whoami` says so and asks you to run `peal login` again. Before you sign in at all, it answers that you are not signed in.

## Across workspaces [#across-workspaces]

```sh
peal overview
peal agenda --from 2026-11-20T00:00 --to 2026-11-27T00:00 --workspace clients
peal report --days 90 --csv report.csv
```

`peal overview` says what needs attention in each workspace you belong to: posts that failed or must be checked, approvals waiting, channels to reconnect or off, comments waiting for an answer, a workspace over its plan, or once that nothing needs attention. Each workspace shows what your role there may read, and one that requires two-step verification your account does not have on is named with no figure. `peal agenda` lists what goes out across those workspaces, the next 14 days unless `--from` and `--to` say otherwise (31 days at most), each post with its time in UTC, its workspace, its platforms, its status and how its text starts; `--workspace`, repeated, keeps some of them, by slug or id. `peal report` shows each workspace's posts, engagement, impressions and followers over the last 7, 30 or 90 days (`--days`, 30 unless given; `--time-zone`), each beside the days before, where your role reads analytics; `--csv` saves the report as a CSV file, one line a workspace, never over a file that exists. All three take `--json`, `--limit` and `--cursor`, and are for a person signed in: an API key belongs to one workspace ([Across your workspaces](/settings#across-workspaces)).

## Sign out [#logout]

```sh
peal logout
```

`peal logout` tells the instance to revoke the sign-in, then forgets it, even when the instance does not answer within 5 seconds.

## Run it with an API key [#api-key]

For a run nobody attends, such as a scheduled job or an agent on a server, set `PEAL_API_KEY` to a workspace's [API key](/settings#api-keys), and name the workspace by its id:

```sh
export PEAL_API_URL=https://peal.example.com
export PEAL_API_KEY=peal_…
export PEAL_WORKSPACE=7c9e6679-7425-40de-944b-e07fc1f90ae7
peal doctor
peal drafts list --json
```

- The key is read from the environment alone. There is no flag for it: a flag lands in the shell's history and in the list of processes. `peal` never prints it.
- While `PEAL_API_KEY` is set, it wins over a saved sign-in. A blank value is no key.
- `--workspace` or `PEAL_WORKSPACE` must give the workspace's id, not its slug, and there is no default: a key cannot look workspaces up. The id is in the address of the workspace's pages in the web app (`/app/<id>/settings`), and `peal whoami`, signed in as a person, lists it. Otherwise the command stops with `workspace_id_required`.
- The key does what its permissions allow, and no more: without `post:schedule` it writes drafts at most. A refusal comes in the server's words, with the permission it lacks.
- What only a person does is refused before any request (`person_required`): `peal login`, `peal account export` and `peal account apps`, `peal members list`, and every `peal invitations` command.
- A key the server no longer takes, revoked, expired or another server's, is told as such (`api_key_refused`), not as a sign-in to renew.

## Check the setup [#doctor]

```sh
peal doctor
peal doctor --workspace studio --json
```

`peal doctor` checks what a run would use, and changes nothing. Run it first, before a script or an agent does anything else.

```text
ok  api-url        https://peal.example.com, from PEAL_API_URL.
ok  health         The server answers.
ok  ready          The server and its database both answer.
ok  changelog      The API's latest release is of 2026-11-09: The API as the SDKs' release 0.3.0 calls it: 49 operations. Later entries list what each release adds to it.
ok  credential     The sign-in saved for https://peal.example.com. PEAL_API_KEY is not set.
ok  access         Signed in as Sam Example <sam@example.com>, in 2 workspaces: Studio (studio, 7c9e6679-7425-40de-944b-e07fc1f90ae7, owner); Clients (clients, 3f2b8a41-5d6c-4e7f-8a9b-0c1d2e3f4a5b, editor).
ok  publish-scope  The sign-in has workspace:publish: it can schedule and publish, where your role allows it.
ok  workspace      Commands act in Studio (studio, 7c9e6679-7425-40de-944b-e07fc1f90ae7, owner), from --workspace.
ok  mcp            MCP clients connect to https://peal.example.com/api/mcp: peal mcp shows how.
```

| Check           | What it looks at                                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `api-url`       | The instance's address, and whether it came from `--api-url`, `PEAL_API_URL` or the default. Fails for plain HTTP beyond this machine, unless `--insecure-http` allows it.           |
| `health`        | That the server answers, within 5 seconds.                                                                                                                                           |
| `ready`         | That it reaches its database.                                                                                                                                                        |
| `changelog`     | That it answers `GET /api/changelog`, with the API's latest release ([Changelog](/api-conventions#changelog)): a server that does not is older, or is not a Peal server.             |
| `credential`    | Which credential a run uses: the key in `PEAL_API_KEY`, or the saved sign-in. Never printed.                                                                                         |
| `access`        | That the credential works: who is signed in and where, or, for a key, that it reads the workspace's channels.                                                                        |
| `publish-scope` | Whether the sign-in may schedule and publish. Skipped for a key, which has permissions and no scope. A sign-in without it is `ok`: it writes drafts, and that is not to work around. |
| `workspace`     | Which workspace commands act in, and where the choice came from.                                                                                                                     |
| `mcp`           | The address MCP clients connect to.                                                                                                                                                  |

Each check is `ok`, `failing` or `skipped`: a check is skipped when it cannot be made, as when the server does not answer, or does not apply. A failing check comes with what to do, on a line starting with `To do:`. `peal doctor` exits with 1 when any check fails.

With `--json`, it prints `{"checks": [{"name", "status", "detail", "fix"}], "ok"}` on stdout, `fix` only where there is something to do, and, when a check fails, the [failure](#json) `checks_failed` on stderr, with the names of the failing checks in `failed`.

## Connect an MCP client [#mcp]

```sh
peal mcp
```

`peal mcp` prints the instance's MCP endpoint and a configuration most MCP clients take, and warns when the instance does not let MCP clients register themselves. [Connect an MCP client](/mcp) explains the rest.

## Choose the workspace [#workspace]

Every command below acts in one workspace. Name it with `--workspace` (or `-w`), by its slug or its id, or set `PEAL_WORKSPACE` once for the commands that follow. If you belong to one workspace only, `peal` takes it; if you belong to several and name none, it lists their slugs and stops. With an [API key](#api-key), give the workspace's id.

```sh
export PEAL_WORKSPACE=studio
peal drafts list
peal drafts list --workspace clients
```

Each command does what your role allows there, as the web app does: a viewer reads, an editor writes, schedules, publishes and follows up, an owner or an admin invites. When the instance refuses, `peal` says why (your role, the post's status, the plan) and exits with 1. The refusal ends with the request's id and the error's code, such as `Request 019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68 (forbidden).`: quote the id when you ask for help ([Requests and answers](/api-conventions#requests)).

## Channels [#channels]

```sh
peal channels list
peal channels list --platform youtube --status disabled --search "client a"
peal channels rename <channel-id> "Client A"
peal channels rename <channel-id> --clear
peal channels disable <channel-id>
peal channels enable <channel-id>
peal channels capabilities [<channel-id>] [--json]
peal channels lookup <channel-id> [<lookup>] [--region <country>] [--language <tag>] [--vanity-name <name>] [--limit <n>] [--cursor <cursor>] [--json]
peal channels tiktok <channel-id>
peal channels defaults show <channel-id>
```

`peal channels list` lists the workspace's channels with their ids, which drafts and posts take, the [name the workspace gave each](/channels#name) before its handle, and whether each one posts, is turned off or must be reconnected; a closing line counts them by status. `--platform`, `--status` (`active`, `disabled` or `refreshNeeded`) and `--search`, text the channel's handle or one of its names holds, narrow the list, every filter holding, a page at a time (`--limit`, then the `--cursor` the page before printed); the counts then tell of every status, whatever `--status` asked for. With one of those flags, `--json` prints the page (`items`, `nextCursor`, `counts`); without any, it prints the list of channels, as it always did. Connecting a channel is for the web app.

`peal channels rename` gives a channel the name your workspace calls it by, 60 characters at most, shown in Peal beside the handle its platform gives the account and sent to no platform; without a name, or with `--clear`, it takes that name back. `peal channels disable` [turns a channel off](/channels#turn-off): nothing goes out on it, and a post that reaches its time meanwhile fails on that channel, goes out on its others, and is not sent later. The channel keeps its connection, its history and its place in your plan. `peal channels enable` turns it back on: it posts again, or says it must be reconnected when its platform stopped accepting Peal's access meanwhile. All three need the right to connect channels.

`peal channels capabilities` shows [what a channel takes](/api-overview#capabilities): how its text is counted and limited, the media it takes with each file type's limits, its platform's options (which `peal drafts save --options` sets) and what the account itself restricts, read from the platform at that moment. Without a channel, it sums up every platform on a line each.

`peal channels lookup` asks a channel's platform for account data its options refer to: without a lookup, it lists those the channel has; with one, it runs it, such as `peal channels lookup <channel-id> youtubeVideoCategories --region FR` for the categories a YouTube video can be filed under in France. `peal channels lookup <channel-id> pinterestBoards` lists a Pinterest account's boards, and `pinterestBoardSections --board <board-id>` a board's sections. A paged lookup ends with the `--cursor` that reads its next page. It changes nothing. With `--json`, both commands print the server's answer as JSON, for scripts.

`peal channels tiktok` reads a TikTok channel's settings from TikTok, as TikTok asks before a post: who it posts as, the audiences a post may choose (its `privacyLevel`, with no default), the interactions the account turned off, which stay off, and its longest video, or why it cannot post today. Posting to TikTok means agreeing to its Music Usage Confirmation, and to its Branded Content Policy for branded content.

`peal channels defaults` shows, sets and clears a channel's [default options](#default-options): what a new post takes there when it gives none.

## Drafts [#drafts]

```sh
peal drafts list                  # newest first; --limit and --cursor page through them
peal drafts save --text "Spring catalogue is out" --channel <channel-id> --channel <channel-id>
peal drafts save --post <post-id> --text "Spring catalogue is out today"
peal drafts save --post <post-id> --options '<channel-id>={"platform":"youtube","title":"Spring catalogue","madeForKids":false}'
peal drafts save --post <post-id> --tag "Spring campaign"
peal drafts save --text "Spring catalogue is out" --set Launch --default-signatures
peal drafts discard <post-id>
```

- `peal drafts save` without `--post` writes a new draft, for the channels `--channel` names (none yet is fine). With `--post`, it changes that draft: the text, when `--text` is given, and the channels, when any `--channel` is. What you leave out stays as it was, its media and its [platform options](/scheduling#options) on the channels it keeps included.
- `--then <text>`, repeated, gives the draft the parts that follow it, as `peal post` takes them, with `--then-delay <seconds>` between them. A draft you change keeps its parts without `--then`, and takes the new ones instead with it.
- `--options <channel-id>=<json>` sets a channel's platform options, as JSON with its `platform`: for YouTube, `title` and `madeForKids` (both needed to schedule), `privacy`, `tags`, `categoryId`, `notifySubscribers`, `containsSyntheticMedia`, `license`, `embeddable`, `publicStatsViewable`, `defaultLanguage`, `recordingDate` (as `2026-11-27`), `thumbnailMediaId` (a JPEG or PNG of the [library](/media), by its id); for TikTok, `privacyLevel` (needed, one `peal channels tiktok` lists), `disableComment`, `disableDuet`, `disableStitch`, `commercialContent`, `brandOrganic`, `brandContent`, `aiGenerated`, a video's `videoCoverTimestampMs`, a photo post's `photoTitle`, `autoAddMusic` and `photoCoverIndex`; for Pinterest, `boardId` (needed, one `peal channels lookup` lists), `boardSectionId`, `title`, `link`, `coverSecond`, `dominantColor`; for LinkedIn, `visibility` (`public` when left out, `connections` on a profile, or `loggedIn`), `disableReshare`, `mentions` (company pages, each a `name` and a `urn` that `peal channels lookup` finds on a company page channel), `linkUrl` with its `linkTitle` and a `linkDescription`, and a PDF document's `documentTitle`; for Google Business Profile, `postType` (`standard` when left out, `event` or `offer`), `title`, `startsAt` and `endsAt` (needed for an event or an offer, as `2026-11-27T09:00`, on the location's clock), `callToAction` with `callToActionUrl`, and an offer's `couponCode`, `redeemUrl` and `terms`; for Mastodon, `visibility`, `contentWarning`, `sensitive`, `language`, `quotePolicy`; for Bluesky, `languages`, `contentLabel`, `replies` (`everyone`, `nobody`, or `limited` to those of `replyFollowers`, `replyFollowing` and `replyMentioned` that are `true`), `disableQuotes`; for Threads, `replyControl`, `topicTag`, `linkAttachment`; for X, `replySettings`, `communityId`, `shareWithFollowers`, `paidPartnership`, `madeWithAi` (see [the options of Mastodon, Bluesky, Threads and X](/scheduling#feed-options)); for Instagram, `format` (`story`, sent without the text), a reel's `shareToFeed`, `coverMediaId` (a JPEG of the library), `thumbOffsetMs`, `audioName` and `trialReel`, and `collaborators` (usernames, each invited); for Facebook, `format` (`story` or `reel`) and a video's or a reel's `videoTitle` (see [post formats](/scheduling#formats) and [the options of YouTube, TikTok, Instagram and Facebook](/scheduling#media-options)). Repeat it for several channels; it replaces that channel's options whole.
- `--tag <id-or-name>` files the draft under one of the workspace's [tags](#tags); repeat it for several. A draft you change keeps its tags without it, and takes those given instead of them with it.
- `--set <id-or-name>` names one of the workspace's [channel sets](#sets) instead of listing its channels; repeat it for several. The draft is for the set's connected channels as well, with the options the set keeps for them where `--options` gives none. A channel of the set that is no longer connected is left out, and `peal` says which.
- `--signature <id-or-name>` puts one of the workspace's [signatures](#signatures) under the draft's text, on every channel, and `--default-signatures` each channel's default one. A signature is then text of the draft, and is never added under a text that already ends with it.
- A new draft takes a channel's [default options](#default-options) on a channel where it gives none; a draft you change keeps what it has.
- A draft goes out at no time. Its text, media and options are checked against each platform's rules when it is scheduled, with `peal posts schedule` or in the web app.
- `peal drafts discard` deletes a draft for good. A post that is scheduled or went out is not a draft: unschedule or cancel it instead.

## Write and send a post [#post]

```sh
peal post "Spring catalogue is out" --channel <channel-id> --at 2026-11-20T10:00 --time-zone Europe/Paris
peal post "Spring catalogue is out" --channels <channel-id>,<channel-id> --now
peal post "Spring catalogue is out" --channel <channel-id> --at 2026-11-20T09:00:00Z \
  --media ./cover.jpg --alt "A paper catalogue open on a wooden table" \
  --idempotency-key spring-catalogue-2026-11-20
peal post "Spring catalogue is out" --channel <channel-id> --at 2026-11-20T10:00 --time-zone Europe/Paris --dry-run
peal post "Spring catalogue is out" --channel <channel-id> --now --wait 30
```

`peal post` writes a post and sends it in one command, to the public of the accounts its channels connect. What goes out cannot be taken back from Peal.

- **When.** `--at` schedules it, `--now` publishes it at once, `--queue <name-or-id>` or `--default-queue` puts it on a [queue's](#queues) next free slot, and one of these is required: publishing is never the default. `--at` takes an instant with its offset, such as `2026-11-20T09:00:00Z` or `2026-11-20T10:00:00+01:00`, or a local time without one, such as `2026-11-20T10:00`, read in `--time-zone` (or `--zone`), an IANA zone such as `Europe/Paris`. Without the flag, the zone is `TZ`, then your computer's. A local time the clocks skip or repeat in that zone is refused: give the instant with its offset.
- **Where.** `--channel` (or `--channels`) names a channel by its id; repeat it, or separate ids with commas. `--set <id-or-name>` names a [channel set](#sets), and stands for its connected channels: at least one channel or one set. A channel of a set that is no longer connected is left out, and `peal` says which after the post; when none of them is left and no `--channel` is given, nothing is posted.
- **Media.** Each `--media` is a file, uploaded first; an `https://` address, which the server imports; or the id of a media the workspace has, as `peal media list` shows it. They show in the order given, 20 at most. The first `--alt` describes the first `--media`, the second the second.
- **Thread.** Each `--then <text>` adds a part after the post, in the order given, text alone: a reply to the part before it on the platforms with [threads](/scheduling#threads). `--then-delay <seconds>` makes each part wait that long after the part before it went out, a day (86400) at most; without it they follow one another. A platform that takes a post alone refuses the post.
- **Options.** `--options <channel-id>=<json>` sets a channel's [platform options](/scheduling#options), as `peal drafts save` takes them. A channel on which you give none takes the options of a set you name, then the channel's [default options](#default-options).
- **Signatures.** `--signature <id-or-name>` puts one of the workspace's [signatures](#signatures) under the text, on every channel; `--default-signatures` puts each channel's default one. A signature is text of the post: it counts against each platform's limit, and is never added twice.
- **Tags.** `--tag <id-or-name>` files the post under one of the workspace's [tags](#tags); repeat it for several.
- **Short links.** `--shorten-links` sends its links shortened, on a server that has [short links](/scheduling#short-links), and `--no-shorten-links` as written; without either, the post takes the workspace's default. `peal short-links list` then reads their clicks.
- **Running it again.** `--idempotency-key` takes any text of your choosing, of 255 characters at most, such as a UUID: within 24 hours, the same key with the same post answers the post the first run made, and makes no other; with another post it is refused. Without it, `peal` sends no key. To run a post with media again, give `--media` as media ids: files and addresses are stored anew on each run, which makes it another post.
- **The same post twice.** Apart from keys, a post whose content (the text the channel receives and the same media, in the same order) already goes to one of its channels less than 23 hours from its time is refused, and `peal` names the post that has it. `--allow-duplicate` lets it through, when you mean to post the same twice ([Duplicate posts](/posting-api#duplicates)).
- **Checking first.** `--dry-run` checks the post and posts nothing: it tells what would be refused, and which channels of a set would be left out.
- **Waiting for the outcome.** With `--now`, `--wait <seconds>` (60 at most) waits until every channel has its result before it answers. When the time runs out first, the post goes on publishing: `peal posts wait` waits for the rest.

The post is checked against every channel's platform first. When it breaks a rule, nothing is posted, and `peal` lists every violation on a line of its own, with its channel, platform, option or media, and the limit.

## Posts [#posts]

```sh
peal posts list
peal posts list --from 2026-11-01T00:00:00Z --to 2026-12-01T00:00:00Z
peal posts list --tag "Spring campaign"
peal posts show <post-id>
peal posts attempts <post-id>
peal posts wait <post-id> --seconds 30
peal posts import posts.csv --dry-run
peal posts import posts.csv --idempotency-key spring-campaign-2026-11
peal posts schedule <post-id> --at 2026-11-20T10:00 --time-zone Europe/Paris
peal posts schedule <post-id> --at 2026-11-20T09:00:00Z --channels <channel-id>,<channel-id>
peal posts publish <post-id>
peal posts reschedule <post-id> --at 2026-11-21T10:00 --time-zone Europe/Paris
peal posts unschedule <post-id>
peal posts cancel <post-id>
peal posts repost <post-id> <target-id>
peal posts confirm <post-id> <target-id> published --permalink https://mastodon.example/@studio/1
peal posts confirm <post-id> <target-id> not-published
peal posts unpublish <post-id> --channel <channel-id> --yes
peal posts edit <post-id> --channel <channel-id> --text "Doors open at 7 pm, not 6."
peal posts changes <post-id>
peal posts tag <post-id> --tag "Spring campaign" --tag Evergreen
peal posts duplicate <post-id>
```

- `peal posts list` lists the workspace's posts, whatever their state, a page at a time, with how each went ([List posts](/posting-api#search)). `--tag` keeps the posts filed under a [tag](#tags).
- `peal posts attempts` lists every attempt Peal made at publishing the post, by channel, round and attempt: when it started, how it ended, the code behind a refusal, the platform's own or Peal's, and when Peal tried again.
- `peal posts show` prints the post's status and time, its tags when it has some, then one line per channel, starting with its target id, with how it went there: failed and why, unconfirmed and why, or published at its address (and kept private, when YouTube kept a public or unlisted video private), then the post's options on each channel that has some.
- `peal posts wait` waits until every channel of a post has its result, up to `--seconds` (60 at most), then shows the post as it stands. Waiting changes nothing: run it again when the time ran out first.
- `peal posts import` creates and sends the posts a CSV file lists, one per row, with the columns `text`, `channels` (channel ids, or a [channel set](#sets) by its id or by a name without spaces, commas or semicolons) and `at`, and optionally `media`, `time_zone`, `allow_duplicate` and `idempotency_key` ([Import posts from a CSV file](/posting-api#import)). Every row is checked first, and nothing is made unless every row is valid. `--dry-run` only checks the file. `--idempotency-key` makes the import safe to run again within 24 hours: the rows already made are not made twice.
- `peal posts schedule` schedules a draft for `--at`, read as `peal post` reads it, on the channels it has, or on those `--channel` names. Its text, media and options must fit each platform's rules, or nothing is scheduled.
- `peal posts publish` publishes a draft, or a scheduled post, now, on the channels it has. It reaches the accounts' public, and cannot be taken back from Peal once it is out.
- `peal posts reschedule` moves a scheduled post to another time. A draft is scheduled then, on the channels it has.
- `peal posts unschedule` takes a scheduled post back to draft, so it goes out at no time until it is scheduled again. A post already publishing cannot be unscheduled.
- `peal posts cancel` cancels a draft or a scheduled post for good: it goes out on no channel. A post already publishing finishes with what its channels did, and those not yet sent are cancelled. To change a scheduled post and keep it, unschedule it instead.
- `peal posts repost` sends the post again, now, on one channel where it failed or is unconfirmed. When it is unconfirmed, check the platform first: it may be live already.
- `peal posts confirm` records what you found on the platform for a post Peal could not confirm: `published`, with its address if you have it, or `not-published`, which fails it there so `peal posts repost` can send it again. See [Scheduling](/scheduling) for how posts end.
- `peal posts unpublish` deletes a published post from its platforms, for everyone, every part of a thread ([Unpublish a post](/scheduling#unpublish)): from one channel with `--channel` (its id, its exact handle, or its platform and handle, as in `--channel "bluesky studio.example"`; a handle two of the post's channels share is refused, listing them), or from every channel it can be. It cannot be undone: it asks first, unless `--yes`, and with `--json` it needs `--yes`. `--wait <seconds>`, with `--channel`, waits for the deletion to end. `peal posts changes` lists what was asked of the post once live, and `peal posts list --removed` the posts removed from a channel.
- `peal posts edit` replaces the text of a published post on one channel, on Mastodon and Google Business Profile ([Edit a published post](/scheduling#edit-live)): `--channel` names it as `peal posts unpublish` does, `--text` is the new text, `--part <n>` the part of a thread (from 0, the post itself). Only the text changes, and the change is public at once. `--wait <seconds>` waits for the edit to end; `peal posts changes` says how it went.
- `peal posts duplicate` makes a new draft that says what a post says ([Duplicate a post](/organise#duplicate)), whatever the post's status: its text, its media, its channels with their text and options, and its tags. What the workspace no longer has (a channel disconnected, media or a tag deleted) is left out, and `peal` says so. The draft has no time, and the post itself does not change.

## Tags [#tags]

```sh
peal tags list
peal tags create "Spring campaign" --colour green
peal tags update "Spring campaign" --name "Spring 2027" --colour teal
peal tags delete "Spring 2027"
peal posts tag <post-id> --tag Evergreen
```

- Tags are the labels a workspace files its posts under, 100 at most. They say nothing to the platforms: nothing of a tag goes out with a post.
- `peal tags create` takes a name of 40 characters at most, which no other tag of the workspace has, whatever its case, and a `--colour` (`gray` unless you say otherwise, `red`, `orange`, `amber`, `green`, `teal`, `blue`, `purple` or `pink`).
- Wherever a command takes a tag, give its id or its name, whatever its case: `peal tags list` shows both.
- `peal tags update` changes the name, the colour or both, and keeps what you leave out. Its posts keep the tag.
- `peal tags delete` deletes a tag for good and takes it off every post that had it; the posts stay.
- `peal posts tag` files a post under the tags `--tag` names, 10 at most, instead of those it had; without `--tag`, it takes them all off. A post takes tags whatever its status, sent or not.
- Every member who reads posts reads the tags; creating, changing and deleting a tag, and tagging a post, need the right to change posts.

## Signatures [#signatures]

```sh
peal signatures list
peal signatures create "Sign-off" --text "The Studio team" --default
peal signatures create "Fediverse" --text "#studio" --platform mastodon
peal signatures update "Sign-off" --text "See you next week"
peal signatures delete "Fediverse"
```

- A signature is a text a workspace keeps to end its posts with, 2000 characters at most; a workspace keeps 50. It is meant for every channel, for the channels of one platform (`--platform`) or for one channel (`--channel <channel-id>`).
- `--default` makes it the default where it is meant for: posts that ask for the default signatures (`--default-signatures`) take it there, the workspace's under the post's text, a platform's or a channel's own under the text that channel has instead. The signature that was the default there is one no longer.
- Once under a post's text, a signature is text of the post: it counts against each platform's limit when the post is scheduled, and it is never added under a text that already ends with it. A post in several parts (`--then`) is signed under its last part.
- Wherever a command takes a signature, give its id or its name, whatever its case: `peal signatures list` shows both.
- `peal signatures update` changes what its flags name (`--name`, `--text`, `--whole-workspace`, `--platform` or `--channel`, `--default` or `--no-default`) and keeps the rest. Posts that already hold the signature's text keep it as it was.
- `peal signatures delete` deletes a signature for good; posts that already hold its text keep it.
- Every member who reads posts reads the signatures; creating, changing and deleting one need the right to change posts.

## Channel sets [#sets]

```sh
peal sets list
peal sets create "Launch" --channel <channel-id> --channel <channel-id>
peal sets create "Videos" --channel <channel-id> --options '<channel-id>={"platform":"youtube","madeForKids":false}'
peal sets update "Launch" --name "Launch day"
peal sets delete "Videos"
peal post "Spring catalogue is out" --set Launch --at 2026-11-20T09:00:00Z
```

- A channel set is a selection of the workspace's channels kept under a name, 50 channels at most, with the options posts take on some of them (`--options`, as `peal drafts save` takes them); a workspace keeps 50 sets. `peal post --set` and `peal drafts save --set` name a set instead of listing its channels.
- Wherever a command takes a set, give its id or its name, whatever its case: `peal sets list` shows both. A CSV import names a set only by its id or by a name without spaces, commas or semicolons.
- `peal sets list` shows each set's channels, and says which are no longer connected. A post made with the set leaves those out and says so; it is never sent to fewer channels silently.
- `peal sets update` changes the name, the channels (those `--channel` names replace the set's) or the options, and keeps what you leave out, but the channels that are no longer connected: a set is saved with connected channels only, so this is also how one is taken out. Posts made with the set before keep their channels.
- `peal sets delete` deletes a set for good; its channels, and the posts made with it, stay.

## Queues [#queues]

```sh
peal queues list
peal queues create "Weekdays" --slot mon@09:30 --slot wed@09:30 --slot fri@17:00 --zone Europe/Paris --channel <channel-id>
peal queues update "Weekdays" --slot tue@12:00 --default
peal queues show "Weekdays"
peal queues preview "Weekdays" --count 5
peal queues reshuffle "Weekdays"
peal queues delete "Weekdays"
peal post "An evergreen tip" --default-queue
peal post "An evergreen tip" --queue Weekdays --channel <channel-id> --dry-run
peal posts queue <post-id> --queue Weekdays
peal posts list --queue Weekdays
```

- A [queue](/scheduling#queues) is a weekly timetable of slots in a time zone, for some channels and at most one channel set (`--set`). `--slot` takes a day (`mon` or `monday`…) and a time of day on a 24-hour clock, such as `mon@09:30`; repeat it, 100 at most. `--zone` is the queue's IANA zone, `TZ` or your computer's without it. A workspace keeps 20 queues, and a queue is named by its id or its name, whatever its case.
- `peal queues update` keeps what you leave out, but the channels that are no longer connected; `--slot` replaces the week and `--clear-slots` empties it, `--channel` replaces the channels and `--clear-channels` takes them all off, `--no-set` takes the channel set off, `--default` makes it the default queue. Posts the queue placed keep their times. `peal queues delete` leaves them scheduled.
- `peal queues preview` lists the coming slots, free or taken, and where a post added now would go: nothing is held.
- `peal queues reshuffle` moves the posts that wait in a queue onto its slots as they are now, in the order of their times, those moved by hand included ([how](/scheduling#reshuffle)), and says how many moved and how many stayed: "Moved 12 posts of Weekdays onto its slots; 3 already on theirs or not yours to move." When it stops, at a month the plan has no room in, with no slot left, or because the queue was saved meanwhile, it says so and how many posts it left: run it again. With `--json` it prints the API's answer.
- `peal post --queue <name-or-id>` puts a post on that queue's next free slot (`--queue=<name-or-id>` too), and `peal post --default-queue` on the default queue's. Each is one of `--at`, `--now`, `--queue` and `--default-queue`, and without `--channel` or `--set` the post goes to the queue's channels. With `--dry-run` it prints the slot it would take.
- `peal posts queue` puts a draft, or a scheduled post, on a queue's next free slot (`--queue`, or the default). `peal posts list --queue` lists the posts a queue placed.

## Repeating posts [#recycling]

```sh
peal recycling start <post-id> --every 2w --count 6 --variant "Open all summer, as before."
peal recycling list --status active
peal recycling show <rule-id>
peal recycling update <rule-id> --until 2026-12-31 --variant "Another way to say it"
peal recycling pause <rule-id>
peal recycling resume <rule-id>
peal recycling end <rule-id>
peal posts list --recycling <rule-id>
```

- `peal recycling start` makes a scheduled or published post [repeat](/scheduling#recycling): `--every` takes a count and `d`, `w` or `m` (1d to 365d, 1w to 52w, 1m to 12m); `--count` the posts in all, this one counted (2 to 100); `--until` the last day; `--variant`, repeated, the texts said in turn after the post's, 10 at most; `--queue` a queue, by name or id. It prints the next three posts and the variant each says.
- `peal recycling update` changes the count (`--no-count` takes it away), the end date (`--no-until`) or the variants (`--variant` replaces them all, `--no-variants` takes them away). `pause` and `resume` stop and restart it; `resume` also restarts a rule that ended for the plan's room, a refused text, its channels, its queue's slots or its post cancelled or taken back to draft (once it is scheduled again), and `resume --variant` gives it other variants, as a refused text asks. `end` stops it for good; the posts it made stay. A count, a day or more than 10 variants out of range is refused before anything is sent.
- `peal recycling list` prints 50 rules a page (`--limit`, 100 at most) and a `More:` line with the `--cursor` of the next.
- `peal posts list --recycling` lists the posts a rule made.

## Feeds [#feeds]

```sh
peal feeds preview https://blog.example/feed.xml --template "New on the blog: {title}"
peal feeds add https://blog.example/feed.xml --channel <channel-id> --template $'{title}\n\n{link}'
peal feeds add https://blog.example/feed.xml --mode queue --queue Weekdays
peal feeds list
peal feeds show <feed-id>
peal feeds items <feed-id>
peal feeds update <feed-id> --template "{title}: {link}"
peal feeds pause <feed-id>
peal feeds resume <feed-id>
peal feeds remove <feed-id>
```

- `peal feeds add` follows a [feed](/scheduling#feeds): what it holds then is never posted, and each item that appears afterwards becomes a draft, or with `--mode queue` a post on the queue's next free slot (`--queue`, by name or id; the default queue otherwise), without anyone reading it first. `--channel` (repeated, or ids separated by commas) and `--set` say where its posts go, `--template` what they say (`{title}`, `{link}`, `{summary}`), and `--picture` attaches each item's picture, imported into the media library.
- `peal feeds preview` reads an address and prints its three newest items as the template would write them, keeping nothing. `peal feeds items` prints what became of its 50 newest items, never what they said.
- `peal feeds update` changes the channels, mode, queue (`--default-queue` takes the workspace's default, and either goes with `--mode queue` or a feed already on a queue), set (`--no-set` takes it away), template or address (read at once); `pause` and `resume` stop and restart it, `resume` reading it at once. `remove` stops following it; its drafts and posts stay.

## Default options [#default-options]

```sh
peal channels defaults show <channel-id>
peal channels defaults set <channel-id> --options '{"platform":"youtube","madeForKids":false,"privacy":"unlisted"}'
peal channels defaults clear <channel-id>
```

- A channel's default options are what a new post takes on it when it gives no [platform options](/scheduling#options) there and no channel set it names does: a new draft, and a post made in one command. A draft you change keeps what it has.
- `--options <json>` takes the options of the channel's platform, as JSON with its `platform`, as `peal drafts save --options` takes them after the channel's id. They replace any the channel had, and may be unfinished.
- Defaults are a starting point, never a way round the rules: a post that takes them is checked when it is scheduled as one that wrote them itself.
- `peal channels defaults clear` leaves the channel without default options; posts already made keep theirs.

## Media [#media]

```sh
peal media upload ./cover.jpg --alt "A paper catalogue open on a wooden table"
peal media import https://files.example/spring/cover.jpg --alt "A paper catalogue open on a wooden table"
peal media generate --prompt "A paper catalogue open on a wooden table, morning light" --aspect landscape
peal media list                   # newest first; --limit and --cursor page through them
peal media show <media-id>
peal media describe <media-id> --text "A paper catalogue open on a wooden table"
peal media delete <media-id>
```

- `peal media upload` sends a file to the workspace's media: JPEG, PNG, GIF or WebP up to 16 MiB, MP4 or QuickTime up to 1 GiB, or a PDF document up to 100 MiB and 300 pages, told by its extension. The file goes straight to the media store, then Peal checks and reads it.
- `peal media import` has the server fetch an image, a video or a PDF document from a public `https://` address, without credentials, within 90 seconds ([Images and videos](/media#import)). Upload larger or slower files instead.
- `peal media generate` has the workspace's own [image provider](/settings#image-provider), or else the instance's image model, make an image from `--prompt` (1 to 1,000 characters, sent as it is to that provider) into the workspace's media, `--aspect` `square` (the default), `landscape` or `portrait` ([Generate an image](/media#generate)). With the instance's model it costs 5 of the workspace's daily assistant requests, with the workspace's own provider none; the image is marked as made by AI: set the platform's AI label in the post's options, and describe it with `--alt` when you attach it. A workspace without its own provider, on an instance without an image model, is refused.
- `peal media list` lists the workspace's images and videos, newest first, with the ids posts attach and whether each is ready. `--limit` takes 100 at most.
- `peal media show` prints one media: its type, its size, when it was stored, whether it is ready to attach, and its description. After an upload or an import, it tells when a video Peal is still reading becomes `ready`.
- `peal media describe` sets a media's description in the library with `--text`, or removes it with `--clear`. Posts that already attached it keep the alt text they have.
- `peal media delete` deletes a media for good. It first says which drafts show it and lose it, then asks (`--yes` otherwise, and with `--json`); a media a scheduled post shows is refused, with those posts.
- `--alt` says what the file shows, for people who cannot see it.

Each command prints the media's id. Only a media that is `ready` goes in a post.

## The assistant's providers [#assistant]

```sh
peal assistant image-provider show
peal assistant image-provider set --base-url https://images.example.com/v1 --model <your-provider-model> < key.txt
peal assistant image-provider set --base-url https://images.example.com/v2 --model <your-provider-model> --keep-key
peal assistant image-provider clear
```

- These keep the workspace's own [image provider](/settings#image-provider), and need `assistant:configure` (owners, admins, and the keys given it).
- `set` never takes the key as an argument, which the shell's history and the list of processes would keep: at a terminal it asks for it, without showing what you type; otherwise it reads it from standard input, to its end, without its last line break. `--keep-key` keeps the key already saved, which the server takes only while `--base-url` stays exactly the same (to change the model alone); any other address asks for the key again.
- `show` prints the address, the model and whether the key can still be read, never the key. `clear` removes the provider and deletes its key, after asking (`--yes` otherwise).

```sh
peal assistant text-provider show
peal assistant text-provider set --kind anthropic --model <your-provider-model> < key.txt
peal assistant text-provider set --kind openai-compatible --base-url https://text.example.com/v1 --model <your-provider-model> < key.txt
peal assistant text-provider test
peal assistant text-provider clear
```

- These keep the workspace's own [text provider](/settings#text-provider), for the writing assistant, the same way and with the same permission. `--kind` is `anthropic` or `openai-compatible`; `--base-url` defaults to `https://api.anthropic.com` for `anthropic`. `test` sends the provider one short request and says whether it answered with a suggestion the assistant can use; it counts as one of the 500 requests a day the workspace's provider takes, none of Peal's.
- The server leaves `assistant:configure` to no application connected over OAuth but this command line, which you sign in yourself at your terminal: an MCP client cannot set either provider.

## Reviews and approvals [#review]

```sh
peal approvals list
peal approvals approve <post-id> --approval <approval-id> --subject <fingerprint>
peal approvals request-changes <post-id> --approval <approval-id> --subject <fingerprint> --comment "Say Thursday, not Friday."
peal approvals policy
peal approvals policy --set always
peal review show <post-id>
peal review comment <post-id> --text "Looks good." --reply-to <comment-id>
peal review link <post-id> --access comment --hours 48
peal review links <post-id>
peal review revoke <link-id>
```

- `peal approvals list` prints the posts that wait for an [approval](/review), with the time each was asked for and who asked. `approve` schedules one; approved after its time, it goes back to draft instead. `request-changes` sends it back to draft with your comment. Both decide on what you read: `list` and `peal review show` print, for each post that waits, the `--approval` and `--subject` a decision takes, and a post that changed since is not decided on (`peal` says so; read it again).
- The command line is an application: under the policy that holds applications' posts, what it schedules waits, and it approves only what a member asked for in the web app.
- `peal approvals policy` shows which posts wait; `--set never`, `contributorsAndApplications` or `always` changes it, for owners and admins.
- `peal review show` prints the post as each channel will receive it, its approvals and its comments, thread by thread. What reviewers typed is printed as text, with control characters replaced.
- `peal review link` creates a review link (`--access view` or `comment`, the default; `--hours`, 14 days unless given) and prints its address, once. A link that lets its holders approve is created in the web app only: the command line is an application, and would approve its own posts with one. `links` lists a post's links without their addresses, and `revoke` ends one.

## Output for scripts [#json]

`--json` prints the API's answer as one JSON document on stdout, and nothing else there, with instants in ISO 8601, in UTC. Every command that reads or changes something through the API takes it, and so do `peal health` and `peal doctor`; `peal login`, `peal logout` and `peal mcp` do not.

```sh
peal post "Spring catalogue is out" --channel <channel-id> --now --json
peal posts show <post-id> --json
```

- The document is the answer of the endpoint the command calls, as the [API reference](/reference) describes it: a post, a page with `items` and `nextCursor`, an array.
- A command whose endpoint answers without a body, such as `peal drafts discard`, `peal invitations revoke` or `peal webhooks delete`, prints `null`.
- `peal billing --json` holds the two answers it reads, under `billing` and `standing`; `peal health --json` and `peal doctor --json` print documents of their own ([Choose the instance](#instance), [Check the setup](#doctor)).

A failure under `--json` is one JSON document too, on stderr, with exit code 1, and stdout stays empty:

```json
{
  "error": {
    "code": "forbidden",
    "message": "This API key does not have the permission post:schedule. An owner or an admin of the workspace gives it to the key, or creates a key that has it.",
    "permission": "post:schedule",
    "reason": "missingPermission",
    "requestId": "019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68"
  }
}
```

For a refusal of the API, `error` is the error as the server sent it: its `code`, its `message`, the `requestId` and its own fields ([Error codes](/api-conventions#error-codes) lists every code). Branch on `code`, never on `message`. The command line has codes of its own for what stops it before, or instead of, an answer of the API:

| Code                      | When                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `invalid_usage`           | The arguments cannot be read: an unknown flag, a missing argument.                                           |
| `unreachable`             | No answer came from the instance: a refused connection, an unknown host, a timeout.                          |
| `unhealthy`               | `peal health` got an answer that is not a healthy one.                                                       |
| `unexpected_answer`       | The instance answered something the API's contract does not describe: it may be older, or not a Peal server. |
| `not_signed_in`           | No sign-in is saved for the instance, and `PEAL_API_KEY` is not set.                                         |
| `sign_in_expired`         | The saved sign-in no longer works: run `peal login` again.                                                   |
| `api_key_refused`         | The instance refused the key in `PEAL_API_KEY`: revoked, expired, or another server's.                       |
| `person_required`         | The command is for a person signed in, and `PEAL_API_KEY` is set.                                            |
| `workspace_id_required`   | With an API key, no workspace is named, or it is named by something other than its id.                       |
| `workspace_required`      | You belong to several workspaces and named none.                                                             |
| `workspace_unknown`       | You belong to no workspace of that slug or id.                                                               |
| `no_workspace`            | You do not belong to any workspace yet.                                                                      |
| `credential_store_failed` | The sign-in could not be read from, or saved to, `credentials.json`.                                         |
| `checks_failed`           | `peal doctor` found failing checks, named in `failed`.                                                       |
| `refused`, `failed`       | Anything else the command line refuses or fails at, with the reason in `message`.                            |

An answer with an error status that carries no error of the API has the API's general code for that status, such as `internal_error`, and the `requestId` when the server gave one.

An agent that runs commands rather than MCP tools works the same way: [Posting from an AI agent](/agents#cli).

## Analytics [#analytics]

```sh
peal analytics summary                                     # the last 30 days, today included
peal analytics summary --from 2026-10-01 --to 2026-10-31 --time-zone Europe/Paris
peal analytics post <post-id>
peal analytics dashboard --days 7                          # against the 7 days before
peal analytics channel <channel-id> --days 30
peal analytics best-times --channel <channel-id> --days 90
peal analytics export posts --output posts.csv --from 2026-10-01 --to 2026-10-31
peal analytics export accounts --format json --output accounts.ndjson
```

`peal analytics summary` adds up the counts of the posts published over a range of days: in all, by channel, and the posts people did the most with. Days run in `--time-zone`, an IANA zone such as `Europe/Paris`; without it, in `TZ`, then in your computer's zone. `peal analytics post` prints a post's latest counts on each channel it went out on. A dash stands for a count the platform does not give. See [Analytics](/analytics).

`peal analytics dashboard` shows a range beside the same number of days before it: each total with what changed, followers with what they gained, each channel, and the top posts. `peal analytics channel` prints one channel day by day: followers, following, views, reach, and the interactions its posts gained. Both take `--days 7`, `30` or `90` (30 unless said), or `--from` and `--to`. `peal analytics best-times` says when one channel's posts did best, by weekday and hour in `--time-zone`, over `--days 30`, `90` (the default) or `180`: the best hours, and how many posts each weighed hour holds. It is the channel's past, never a prediction, and ranks nothing under 20 posts ([When posts did best](/analytics#best-times)). `peal analytics export posts` or `accounts` saves the figures to the file `--output` names, as CSV or, with `--format json`, one JSON object a line; it replaces no file.

## Billing [#billing]

```sh
peal billing
```

`peal billing --json` prints the API's two answers in one document, under `billing` and `standing`. Without it, the command prints the workspace's plan and subscription, and, for each limit (channels, members, posts going out this month, assistant requests today, media stored), how much is used of what the plan allows, and whether the workspace may still start its trial. It changes nothing: owners and admins order, cancel or withdraw on the workspace's **Billing** page ([Plans and billing](/billing)). On an instance that does not bill, nothing is limited.

## Usage [#usage]

```sh
peal usage
peal usage --from 2026-10-01 --to 2026-10-31
```

`peal usage` prints the workspace's plan, each limit against what is used now, then, over UTC days (the last 30 unless `--from` and `--to` say otherwise, 92 at most), the posts that went out by platform, the channel-days, the posts on platforms that bill per post, and a row for each day that has anything: its posts, the channels, members and media as the day's snapshot found them (a dash for a day without a snapshot), and its assistant requests. `--json` prints the API's answer as it came. It changes nothing, and nothing in it is priced ([Usage](/billing#usage)).

## Short links [#short-links]

```sh
peal short-links status
peal short-links set-default on
peal short-links list --post <post-id>
peal short-links show <link-id> --from 2026-11-01 --to 2026-11-30
```

`peal short-links status` says whether the server has [short links](/scheduling#short-links) and whether the workspace's new posts ask for them by default, which `peal short-links set-default on` or `off` changes (owners and admins). `peal post` and `peal drafts save` follow that default unless `--shorten-links` or `--no-shorten-links` says otherwise for the post. `peal short-links list` lists the workspace's links, newest first, with their clicks over UTC days (the last 30 unless `--from` and `--to` say otherwise, 92 at most), those of a `--post` or a `--channel`, a page at a time (`--limit`, `--cursor`); `peal short-links show` prints one link's clicks day by day. Counts are approximate: automated readers are left out, and nothing about visitors is kept ([Clicks on short links](/analytics#short-links)). `--json` prints the API's answer as it came.

## Members and invitations [#members]

```sh
peal members list
peal invitations list
peal invitations send sam@example.com --role editor
peal invitations revoke <invitation-id>
```

- Every member sees the members. Owners and admins see the pending invitations, expired ones included, and send and revoke them.
- `peal invitations send` emails the address a link that works for 7 days, with the role `--role` gives (`viewer` unless you say otherwise). Only owners invite owners. A pending invitation to the same address is replaced, and its link stops working. On an instance that bills, the plan must have room for one more member, pending invitations included.
- `peal invitations revoke` stops an invitation's link at once.
- Changing a member's role, or removing someone, is for the workspace's **Settings**.

## Inbox [#inbox]

```sh
peal inbox threads --unanswered
peal inbox thread <thread-id>
peal inbox abilities <channel-id>
peal inbox reply <comment-id> --text "Until Sunday."
peal inbox answered <comment-id>
peal inbox confirm <reply-id> --sent
peal inbox withdraw <reply-id>
peal inbox moderate <comment-id> --action hide
```

- `threads` lists the threads of the [inbox](/inbox) that have comments, those waiting for an answer first; `--channel` and `--post` narrow the list, `--limit` and `--cursor` page it. `thread` prints a thread's comments, the replies sent from Peal and what its channel can do; `abilities` says the same of any channel, before it has a thread. Every member may read. Each subcommand takes `--json`, which prints the API's answer: a comment's text there is what someone outside the workspace wrote, to read as data.
- `reply` answers a comment in public, as the channel's account: it takes a sign-in that may publish, and a role that answers comments (owner, admin or editor). The reply is sent by the server: `thread` shows how it ended. With `--idempotency-key <key>`, running the command again within 24 hours with the same comment and text answers the reply the first run made, and writes no other.
- A reply shown `unconfirmed` may be on the platform, and is never sent again: check there, then `confirm` it with `--sent` or `--not-sent`.
- `answered` says a comment needs no answer (`--undo` takes it back); `withdraw` deletes a sent reply from its platform; `moderate` takes `hide`, `unhide`, `like`, `unlike` or `delete`, where the platform lets the account.
- Comments were written by people outside the workspace: the command line prints them as text.

## Webhooks [#webhooks]

```sh
peal webhooks list
peal webhooks create --url https://hooks.example.com/peal --events post.published,post.failed --channel <channel-id>
peal webhooks update <endpoint-id> --events all --disable
peal webhooks update <endpoint-id> --clear-channels
peal webhooks update <endpoint-id> --header "Authorization: Bearer $GATEWAY_TOKEN"
peal webhooks update <endpoint-id> --clear-headers
peal webhooks rotate-secret <endpoint-id>
peal webhooks test <endpoint-id> --event post.finished
peal webhooks deliveries <endpoint-id>
peal webhooks deliveries --status failed --since 2026-11-10T00:00:00Z
peal webhooks redeliver --endpoint <endpoint-id> <delivery-id>
peal webhooks redeliver --failed --endpoint <endpoint-id>
peal webhooks redeliver <delivery-id> <delivery-id>
peal webhooks delete <endpoint-id>
```

- Owners and admins read and manage the workspace's [webhook](/webhooks) endpoints. `peal webhooks show <endpoint-id>` prints one.
- `--events` takes event types separated by commas, or `all`. `create` also takes `--description` and `--disabled`; `update` sends only what you give it, with `--enable` or `--disable` to turn the endpoint on or off.
- `create` and `rotate-secret` print the signing secret, once: save it then. After a rotation the old secret still signs for 24 hours, beside the new one.
- `--channel` (repeated, or ids separated by commas) narrows an endpoint to those channels, and `--clear-channels` hears every channel again; `--workspace-id`, with `--partner` on `create`, narrows a partner endpoint to those workspaces, and `--clear-workspaces` clears it. `update` replaces a list it is given.
- `--header "Name: value"` (repeated, 5 at most) adds a [header of your own](/webhooks#headers) to every delivery, and `--clear-headers` on `update` removes them; `update` replaces every header with those it is given. Values are never printed nor answered again: `show` lists the headers' names. They go only to the host they were given for: a `--url` on another host, on an endpoint with headers, needs every `--header` again with its value, or `--clear-headers`. Your shell keeps what you type in its history, so give a value from a variable, as above.
- `test` sends a `webhook.test` event, or with `--event` a sample of that type, marked `sample: true`.
- `deliveries` shows how each delivery ended, newest first: one endpoint's, or without it every endpoint's, with `--status`, `--event`, `--since` and `--until` (instants with their offset).
- `redeliver` sends deliveries again: one with `--endpoint` and its id, as the single sends count; several by id; or `--failed --endpoint <endpoint-id>` for an endpoint's failed ones, oldest first, 100 a call, with `--since`, `--until` and `--event`, which go with `--failed` only. It prints what it skipped and why, and how many are left: run it again for those. When it sends nothing again it ends as a refusal (`nothing_redelivered`, exit code 1). Its arguments are delivery ids: an older command line took the endpoint first (`redeliver <endpoint-id> <delivery-id>`), which now names the endpoint with `--endpoint`; an endpoint's id given as a delivery is skipped, and said so.

## Activity log [#activity]

```sh
peal activity list
peal activity list --operation posts.schedule --limit 50
peal activity list --actor <user-id|api-key-id> --json
```

`peal activity list` lists the requests that asked to change something in the workspace, newest first: when, the operation, the status answered and the error's code, who asked, through which key or application, the ids the request named, and the request's id. Owners read it, and a key an owner gave `activity:read`; an event is kept {{keep-activity-en}} ([The activity log](/settings#activity)).

- `--operation` keeps one operation, such as `posts.schedule`, or `mcp.create_draft` for a tool of the MCP endpoint; `--actor` keeps what one member, by their user id, or one API key, by its id, asked for.
- `--limit` takes 100 at most. When there is more, the last line gives the command for the next page, with its `--cursor`.

## Connect links [#links]

```sh
peal links create --platform linkedin
peal links create --platform mastodon --hours 24 --locale fr
peal links create --platform instagram --channel <channel-id>
peal links list
peal links show <link-id>
peal links revoke <link-id>
```

- `peal links create` makes a [connect link](/channels#connect-links): a hosted page where whoever owns an account of that platform connects it to the workspace, without a Peal account. It prints the link's address, once: hand it over a channel you trust. For members who may connect channels.
- `--hours` says how long it works, from 1 to 720 (168 unless given); `--locale` the language its page opens in; `--channel` reconnects that channel instead of connecting a new account; `--return-url` where the page sends them once done, an address on an origin the workspace's partner account registered.
- `peal links list` shows those waiting, and those used, revoked or expired in the last 30 days; `show` tells which channels a link connected, or how its last sign-in failed; `revoke` takes one back.

## Partner account [#partner]

```sh
peal partner show
peal partner keys
peal partner workspaces --external-id cus_42
peal partner usage --from 2026-11-01 --to 2026-11-30
peal partner overview --limit 100
```

For the owners and admins of a workspace with a [partner account](/embedding): `show` prints what its customers see, the origins hosted pages may send them back to, and what it holds; `keys` lists its keys, never the keys themselves; `workspaces` lists the workspaces it owns, newest first, with their external ids and channels, `--external-id` finding one exactly and `--name` searching; `usage` prints what the account used per customer over a period of UTC days (`--from`, `--to`, the last 30 by default, 92 at most): on the first page, what it holds now and the totals; then a row per workspace, external id first, its home workspace first on the first page, `--limit` and `--before` paging as the [API](/embedding#usage) does, and the command for the next page, with the same days; `overview` prints what needs attention in each customer's workspace ([Health](/embedding#health)): channels to reconnect or turned off, posts that failed, wait to be confirmed or approved, threads waiting, once "Nothing needs attention." where nothing does, and on the first page whether the plan holds their channels, newest first, `--limit` and `--cursor` paging. Creating and deleting those workspaces is for the partner API, with a partner key, and creating a key for the workspace's **Settings**.

## Ads [#ads]

These commands follow the [ads](/ads) page: read it first, as boosting
spends money. No command signs in to an ad network, connects an ad account,
turns spending on or sets the monthly ceiling: a person does that in the web
app. Boosting from a sign-in takes the `workspace:ads` scope, which
`peal login --ads` asks for and which is never asked without the flag;
`peal doctor` says whether the sign-in holds it.

| Command                                                                     | What it does                                                                                                                                           |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `peal ads status`                                                           | Says what the server offers of ads: nothing, reading ad accounts, or boosting too.                                                                     |
| `peal ads accounts`                                                         | Lists the connected ad accounts: network, currency, status, whether an owner allowed each to spend, and its monthly ceiling.                           |
| `peal ads account <account-id>`                                             | Shows one ad account, its ceiling and what its boosts commit this month.                                                                               |
| `peal ads campaigns <account-id> [--from <YYYY-MM-DD>] [--to <YYYY-MM-DD>]` | Lists the account's campaigns as last read, with what their ads did over the days (the last 30 by default, 366 at most).                               |
| `peal ads list <account-id> [--campaign <campaign-id>] [--from …] [--to …]` | Lists the account's ads, those of one campaign with `--campaign`, each with the workspace's post it promotes.                                          |
| `peal ads insights <account-id> [--from …] [--to …]`                        | Sums what the account's ads did each day: spend, impressions, reach, clicks, results.                                                                  |
| `peal ads post <post-id>`                                                   | Shows a published post's organic counts beside its paid numbers, by ad account, and its boosts: side by side, never summed.                            |
| `peal ads boosts [--post <post-id>] [--cursor <cursor>]`                    | Lists the workspace's boosts, newest first.                                                                                                            |
| `peal ads boost show <boost-id>`                                            | Shows one boost, where it stands, and the requests Peal sent the ad network for it.                                                                    |
| `peal ads boost quote …`                                                    | Checks a boost and makes nothing: the most it can cost, its days, and the room under the monthly ceiling.                                              |
| `peal ads boost create … [--idempotency-key <key>] [--yes]`                 | **Spends money.** Quotes, prints what it will spend and for how long, asks, then boosts the post.                                                      |
| `peal ads boost pause <boost-id>`                                           | Pauses a boost; it spends nothing while paused. Safe to run twice.                                                                                     |
| `peal ads boost resume <boost-id> [--yes]`                                  | **Spends money.** Runs a paused boost again until its end, after asking.                                                                               |
| `peal ads boost stop <boost-id> [--yes]`                                    | Stops a boost for good, after asking.                                                                                                                  |
| `peal ads audit [--cursor <cursor>]`                                        | Lists the ads audit trail, which answers to owners alone (`ads:authorize`): with an API key an owner gave that permission, as no application holds it. |

`boost quote` and `boost create` take the same flags:

| Flag                                     | Meaning                                                                                                                                                                    |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--account <account-id>`                 | The ad account that pays. Required.                                                                                                                                        |
| `--post <post-id>`                       | The published post to boost. Required.                                                                                                                                     |
| `--channel <channel-id>`                 | The channel it is boosted on: a Facebook Page, or an Instagram account connected through its Page. Required.                                                               |
| `--total <amount>` or `--daily <amount>` | The budget for the whole run, or for each day, in the currency's units (`50`, `50.00`). Exactly one. More decimals than the currency has are refused.                      |
| `--currency <EUR>`                       | The budget's currency. Required, never defaulted: it must be the ad account's, and nothing is ever converted.                                                              |
| `--ends <instant>`                       | When the run ends. Required: at least a day after the start, 90 days at most.                                                                                              |
| `--starts <instant>`                     | When it starts. Now when left out.                                                                                                                                         |
| `--time-zone <zone>`                     | The zone `--starts` and `--ends` are read in when written without an offset.                                                                                               |
| `--countries <FR,BE>`                    | ISO alpha-2 country codes, 25 at most. Required.                                                                                                                           |
| `--age-min <n>`, `--age-max <n>`         | 18 to 65 (65 means 65 and over). 18 and 65 when left out.                                                                                                                  |
| `--not-special-category`                 | A required declaration: Peal does not boost ads about housing, employment, financial products or services, or social issues, elections or politics.                        |
| `--beneficiary <name>`, `--payer <name>` | Who benefits from the ad and who pays for it: required when a country is in the European Union.                                                                            |
| `--idempotency-key <key>` (create)       | Makes the command safe to run again: the same key never makes a second boost. Made up and printed when left out.                                                           |
| `--yes` (create, resume, stop)           | Answers the confirmation beforehand. Required with `--json`, and where the input is not a terminal: the command then refuses with `confirmation_required` rather than ask. |

## Your data [#account]

```sh
peal account export                       # peal-data-2026-11-09.json, in this folder
peal account export --output ~/peal-data.json
peal account apps
```

- `peal account export` saves a copy of everything Peal keeps about you, as on the account settings page: your account, sessions, workspaces, invitations, connected applications, notices, preferences, the posts you wrote, and the content of the workspaces where you are the only member. It holds no password, token, key or card. The file is yours alone to read (mode 600), and `peal` never writes over a file unless you add `--force`. Peal emails your address each time a copy is taken, saying it came from the command line.
- `peal account apps` lists the applications that act for you, this command line and MCP clients among them, with what they may do and where. Revoke one from **Account settings**, in the web app: no application revokes another.
- Deleting your account is for **Account settings** too.

<Callout type="note" title="Why MCP clients cannot do this">
  Your export and your connected applications are open to you in the web app and
  to this command line, which you sign in at your own terminal and which writes
  to your own disk. No MCP tool hands them out: an MCP client passes what its
  tools answer to an AI model, and your export holds your sessions' addresses
  and everything you wrote. The instance refuses them to every OAuth client but
  `peal`.
</Callout>

## Settings [#settings]

| Variable             | What it does                                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `PEAL_API_URL`       | The instance's address, unless `--api-url` is given. Default: `http://localhost:3000`.                                                     |
| `PEAL_INSECURE_HTTP` | `true` lets the sign-in or the API key go over plain HTTP to a server that is not this machine, as `--insecure-http` does. Off by default. |
| `PEAL_API_KEY`       | A workspace API key to run with instead of a saved sign-in, which it wins over ([Run it with an API key](#api-key)).                       |
| `PEAL_WORKSPACE`     | The workspace commands act in, by slug or id, unless `--workspace` is given. With an API key, by id.                                       |
| `TZ`                 | The zone `peal analytics summary` runs days in, and the zone `--at` is read in, unless `--time-zone` is given.                             |
| `PEAL_CONFIG_DIR`    | The folder `credentials.json` is saved in.                                                                                                 |
| `XDG_CONFIG_HOME`    | Without `PEAL_CONFIG_DIR`, the sign-in goes in its `peal` folder.                                                                          |
| `APPDATA`            | Without either, on Windows, the sign-in goes in its `peal` folder.                                                                         |
| `HOME`               | Otherwise, the sign-in goes in `~/.config/peal`.                                                                                           |

`peal --help` lists the commands, and `peal <command> --help` describes one.
