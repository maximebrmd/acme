The web app, the command line and the MCP endpoint are built on the same HTTP API, so anything they do, your own code can do too.

<Callout type="warning" title="Not stable yet">
  The API changes with every commit until the first release. Expect endpoints to
  be added, renamed and removed.
</Callout>

## One contract [#contract]

The API is defined once, in the `peal-contract` package. The server implements that definition, the clients derive their types from it, and the [API reference](/reference) in these docs is generated from it, so the three cannot drift apart.

## Base URL [#base-url]

Requests go to the address you open Peal at, and every endpoint's path starts with `/api`: the web app forwards `/api/*` to the server. In these docs, `https://api.example.com` stands for that address; replace it with your own.

```bash
curl -i https://api.example.com/api/health
```

## Authentication [#authentication]

Apart from the health checks and the documents platforms read about Peal, every endpoint needs one of these:

- **An API key**, for scripts and integrations: send it as `Authorization: Bearer peal_…`. A key belongs to one workspace and holds some of the permissions of the member who created it, never more: a key without `post:schedule` neither schedules nor publishes. Members who may manage keys (owners and admins) create one with `POST /api/workspaces/{workspaceId}/api-keys` while signed in, and see the key only in that answer. A key may send 600 requests a minute.
- **An OAuth access token**, which the [command line](/cli) and [MCP clients](/mcp) obtain when you sign them in, sent the same way. It acts as you, limited to what you agreed to: `workspace:read` reads, `workspace:write` does what your role allows but what puts posts out, and `workspace:publish` schedules and publishes ([What each permission allows](/agents#scopes)). Every endpoint that needs `post:schedule` needs `workspace:publish` from an OAuth token, and answers 403 without it.
- **The session cookie** of the web app, for the web app itself. A request that changes something with it must come from the web app's own origin.

With a session or an OAuth token, `GET /api/me` tells who you are, and lists your workspaces, with your role and permissions in each. An API key belongs to a workspace, not to a person, and gets 403 there.

## Workspaces [#workspaces]

A workspace's resources live under `/api/workspaces/{workspaceId}/`: `channels`, `posts`, `media`, `assistant`, `analytics`, `billing`, `webhooks` and `api-keys`; `DELETE /api/workspaces/{workspaceId}` deletes the workspace itself, with everything in it ([Workspaces and your account](/settings#delete-workspace)). Each endpoint's reference names the permission it needs, such as `post:schedule` or `channel:connect`.

| Status | Meaning                                                                        |
| ------ | ------------------------------------------------------------------------------ |
| 401    | No credentials, or credentials that no longer work.                            |
| 403    | The credentials work, but do not allow this request, or the account is banned. |
| 404    | No such resource, or a workspace the caller does not belong to.                |

`POST /api/workspaces/{workspaceId}/posts/send` creates a post and sends it in one request, now or at an instant; `POST /api/workspaces/{workspaceId}/media/import` has the server fetch an image or a video from a public HTTPS address into the workspace's media. Sent with an `Idempotency-Key` header, a `send` request is safe to send again: within 24 hours, the same key with the same body answers the post the first request made, and another body answers 409 `IdempotencyKeyReused`. [Posting from an AI agent](/agents#api) shows both.

Errors answer with a JSON body whose `_tag` names the error, such as `PostContentInvalid` or `ConnectFailed`, with the details the reference lists. The writing assistant's endpoints also answer 429 once the workspace has used its requests for the day, 503 when the instance has no AI provider, and 502 when the provider gave no answer the assistant could use. On an instance that bills, connecting a channel, scheduling a post or starting an upload the workspace's plan has no room for answers 402 `PlanLimitReached`, which names the `limit` (`channels`, `members`, `scheduledPosts`, `assistantRequests` or `mediaStorage`, in bytes) and what the plan `allowed` ([Plans and billing](/billing#limits)); `GET /api/workspaces/:workspaceId/billing` shows the plan, its allowances and the workspace's usage.

## What a channel takes [#capabilities]

Each platform has its own rules: how long a post may be and how its length is counted, which images and videos it takes, and options of its own, such as a YouTube video's title. Rather than learn them from each platform's documentation, ask Peal, which answers the rules it checks when a post is scheduled:

- `GET /api/workspaces/{workspaceId}/platforms/capabilities` describes every platform, whether or not the workspace has a channel there.
- `GET /api/workspaces/{workspaceId}/channels/{channelId}/capabilities` describes one channel: its platform's capabilities, and under `account` what the account itself narrows, read from the platform at that moment. A TikTok account offers only some audiences, may have turned comments, Duets or Stitches off, and has a longest video. When the platform cannot be asked, `account` is `unread` with the reason, and the platform's capabilities are answered alone.

Both need `channel:read`, so an API key or an application you let read only may call them. A description holds:

| Field       | What it says                                                                                                                                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `version`   | The version of the description, 1 today. It goes up when a field changes meaning or leaves; fields, platforms, lookups and restrictions are added under the same version, so skip what you do not know.                                                                                                                  |
| `text`      | Every limit on the text (`limits`: all apply, each `maximum` counted in its `unit`, the last one being Peal's own), the most hashtags, mentions and different links, and the characters refused. `peal-contract/post-text` counts each unit as the server does.                                                          |
| `media`     | Whether a post needs an image or a video, how many it takes, whether images and videos go together, alt text, and for each file type its size, duration, pixels, sides and aspect ratio (width divided by height). `formats` is null where Peal knows none of the rules yet.                                             |
| `options`   | The fields a draft's `options` take on that platform: each one's `type`, the `values` of a choice, whether it is `required` to schedule, its `maxLength`, what the platform does when it is left out (`ifLeftOut`), and the `lookup` that answers its values; then `constraints`, the rules between two fields.          |
| `lookups`   | What the platform tells about an account, for the options that refer to it (below).                                                                                                                                                                                                                                      |
| `analytics` | Whether Peal reads the counts of each post published there (`perPost`). A platform's description says so when any of its channels has counts, and lists every lookup it has; a channel's says it for that channel. On LinkedIn, a company page has counts and the lookup of pages to mention, and a profile has neither. |

A limit that is null is one Peal does not check: the platform may still apply it, and refuse the post when it goes out.

### Lookups [#lookups]

Some options take values only the account knows. A lookup asks the platform for them, with the channel's token:

- `GET /api/workspaces/{workspaceId}/channels/{channelId}/lookups` lists the lookups a channel has, with the input each takes and the options it fills.
- `POST /api/workspaces/{workspaceId}/channels/{channelId}/lookups/{name}` runs one, and answers a page of `items` tagged by the lookup's name (`_tag`). When `nextCursor` is not null, send it back as `cursor` for the next page.

| Lookup                   | Platform                         | Input                                                              | Items                                                                                                             |
| ------------------------ | -------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `youtubeVideoCategories` | YouTube                          | `regionCode` (two capital letters, `US` when left out), `language` | The categories a video can be filed under in that country: `id`, which the `categoryId` option takes, and `title` |
| `youtubePlaylists`       | YouTube                          | `limit` (25 when left out, 50 at most), `cursor`                   | The channel's playlists: `id`, `title` and `privacy`                                                              |
| `tiktokCreator`          | TikTok                           | none                                                               | One item: the creator's posting settings, whose `privacyLevels` the `privacyLevel` option takes                   |
| `linkedinOrganizations`  | LinkedIn (company page channels) | `vanityName` (required), the name in the page's address            | The page of that name, if any: `name` and `urn`, which an entry of the `mentions` option takes, and `vanityName`  |
| `pinterestBoards`        | Pinterest                        | `limit` (25 when left out, 50 at most), `cursor`                   | The account's boards: `id`, which the `boardId` option takes, `name` and `privacy`                                |
| `pinterestBoardSections` | Pinterest                        | `boardId` (required), `limit`, `cursor`                            | The sections of that board: `id`, which the `boardSectionId` option takes, and `name`                             |

A lookup changes nothing, and needs `channel:read`. Each run is a request to the platform, counted against what it allows this instance, so run one when a post needs it rather than on a timer. A name the channel does not have, as its platform or its kind of LinkedIn channel lacks it, answers 404 `LookupNotFound`, and an input the lookup does not take, or one without a field it needs, 422 `LookupInputInvalid`. A page may come empty and still name a next one. A channel that is turned off or must be reconnected answers 409 `ChannelCannotPost`; a platform that does not answer, 502 `PlatformUnreachable`; one that asks to slow down, 429 `PlatformRateLimited`, with `retryAfterSeconds` when it said how long.

## Webhooks [#webhooks]

Rather than asking the API again and again, have Peal call your server when something happens in a workspace: a post went out or failed, a channel must be reconnected, a file is ready. Members who may manage webhooks (owners and admins), and API keys given that permission, add endpoints under `/api/workspaces/{workspaceId}/webhooks`. [Webhooks](/webhooks) lists every event with its schema, and tells how deliveries are signed, retried and verified.

## Your account [#me]

What belongs to you rather than to a workspace lives under `/api/me`: who you are (`GET /api/me`), your [notifications](/notifications#api) under `/api/me/notices`, and which of them are emailed, under `/api/me/notification-preferences`. The notification endpoints answer 403 to API keys, which belong to a workspace, and to OAuth tokens bound to one workspace, such as an MCP client's.

A copy of your data (`GET /api/me/export`), deleting your account (`DELETE /api/me`) and your connected applications (`/api/me/connected-apps`) answer only your own session in the web app: API keys, OAuth tokens and staff acting as you get 403 ([Workspaces and your account](/settings#api)).

## OpenAPI document [#openapi]

The server publishes its OpenAPI 3.1 document at `/openapi.json` on its own address, such as `http://localhost:3000/openapi.json` for a server running from source; the web app does not forward it. Use it to generate a client in another language or to import the API into an HTTP tool.

## Reference [#reference]

The [API reference](/reference) has a page for each endpoint, grouped by tag, with its parameters, request and response schemas, and code samples.
