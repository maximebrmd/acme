A webhook is a request Peal sends to an address of yours when something happens in a workspace: a post went out or failed, a channel must be reconnected, a file is ready. A product that publishes through the [API](/api-overview), or an automation, learns it at once, without asking again and again.

Peal signs every request as the [Standard Webhooks](https://www.standardwebhooks.com) specification says ([its text](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)), so the libraries written for it verify Peal's deliveries as they are.

## Who manages them [#access]

A workspace's webhooks are under **Settings**, then **Webhooks**, in the web app, in the `webhooks` group of the [API](#api), under `peal webhooks` on the [command line](/cli), and in the [MCP](/mcp) tools `list_webhooks` and `list_webhook_deliveries`, which read, and `create_webhook`, which adds an endpoint.

| Permission       | What it allows                                                              | Who holds it      |
| ---------------- | --------------------------------------------------------------------------- | ----------------- |
| `webhook:read`   | List the endpoints and read their deliveries                                | Owners and admins |
| `webhook:manage` | Add, change, turn off and delete endpoints, rotate secrets, send and resend | Owners and admins |

An API key does what the permissions it was given allow, and an OAuth client what you let it do: a client allowed to read only lists endpoints and deliveries, and changes nothing. Staff acting as a member cannot change a workspace's webhooks.

Every plan includes webhooks, and an instance that does not bill has them too.

## Endpoints [#endpoints]

An endpoint is an address, the events it wants, a description, and whether it is on. A workspace has 10 endpoints at most, whatever its plan.

- **The address** is an HTTPS URL on the default port (443), on a public host, without a user name or a password, 2048 characters at most. Peal checks that the host resolves to public addresses when you save it, and again before every request: an address that later points inside a private network is sent nothing. Peal follows no redirect, so an answer in the 300s is a failure: give the final address.
- **The events** are the [event types](#events) the endpoint subscribes to, one at least. It is sent those, and nothing else.
- **The description**, up to 200 characters, says what the endpoint is for.
- **On or off.** While an endpoint is off, Peal sends it nothing, its deliveries still waiting fail, and what happens meanwhile is not kept for it: turning it back on does not replay it.

## The signing secret [#secret]

Peal generates a secret for each endpoint: `whsec_` followed by 32 random bytes in base64. It is shown once, when the endpoint is created, and Peal stores it encrypted: copy it then, into your server's secrets.

Rotating the secret answers a new one, shown once too. For 24 hours, each delivery then carries two signatures, one per secret, so you change your server's secret without missing a delivery. After that the old secret signs nothing more.

## What Peal sends [#request]

Each delivery is a `POST` to the endpoint's address, with `content-type: application/json` and three headers:

| Header              | What it holds                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webhook-id`        | The event's id. It is the same on every attempt of a delivery, and when the event is sent again: [deduplicate](#ordering) with it.                  |
| `webhook-timestamp` | When this attempt was made, in seconds since the epoch.                                                                                             |
| `webhook-signature` | One signature per valid secret, separated by spaces. Each is `v1,` followed by the base64 of an HMAC-SHA256, as [Verify a delivery](#verify) tells. |

```http
POST /peal HTTP/1.1
Host: hooks.example.com
Content-Type: application/json
User-Agent: Peal-Webhooks
webhook-id: 019a6f40-2f6b-7a1c-9d2e-5b4c3a2f1e03
webhook-timestamp: 1794301203
webhook-signature: v1,Mfm1tWLUX4U95AK/DHjduW4e8bHrj/HztAOACn91BF4=
```

The body is a JSON object:

| Field       | Type    | What it holds                                                                  |
| ----------- | ------- | ------------------------------------------------------------------------------ |
| `id`        | string  | The event's id, as in `webhook-id`                                             |
| `type`      | string  | What happened, such as `post.published`. It tells what `data` holds.           |
| `version`   | integer | The version of `data`: 1                                                       |
| `timestamp` | string  | When it happened, as an ISO 8601 instant in UTC. Not when the request is sent. |
| `data`      | object  | The event's own fields, [below](#events)                                       |

The order of the fields in the body is not part of the contract.

### What a payload never holds [#thin]

Payloads carry ids, states, codes, instants and permalinks. They never carry what a post says, nor its images or videos.

The endpoint is a third party to the people who wrote the post: an address someone chose, which Peal cannot check beyond its being public. Keeping payloads thin keeps a workspace's content behind API credentials and their permissions, where each read is checked. When your server needs the post, it reads it through the API with a key of its own: `GET /api/workspaces/{workspaceId}/posts/{postId}`.

### Versions [#versions]

Event types and their fields are a public contract. Peal adds event types, and fields to an event, without changing `version`: ignore the fields and the types you do not know. Nothing is renamed or removed. A change your code could not read would come as a new version, sent beside this one.

## Events [#events]

| Event                                                   | When                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------- |
| [`post.scheduled`](#post-scheduled)                     | A post was scheduled, or moved to another time                            |
| [`post.unscheduled`](#post-unscheduled)                 | A scheduled post was taken back to draft                                  |
| [`post.published`](#post-published)                     | A post went live on a channel                                             |
| [`post.failed`](#post-failed)                           | A post did not go out on a channel                                        |
| [`post.unconfirmed`](#post-unconfirmed)                 | Peal cannot tell whether a post went live on a channel                    |
| [`post.cancelled`](#post-cancelled)                     | A post was cancelled                                                      |
| [`channel.connected`](#channel-connected)               | An account was connected, or a channel authorized again                   |
| [`channel.disconnected`](#channel-disconnected)         | A channel was disconnected                                                |
| [`channel.reconnect_needed`](#channel-reconnect-needed) | A channel's authorization stopped working                                 |
| [`media.ready`](#media-ready)                           | A file was read, and can go in posts                                      |
| [`media.failed`](#media-failed)                         | A file was refused, or could not be read                                  |
| [`webhook.test`](#webhook-test)                         | Someone asked for a test event. Sent whatever the endpoint subscribes to. |

A post goes out on each of its channels separately, so `post.published`, `post.failed` and `post.unconfirmed` name one channel each: a post on three channels brings three events. These fields say which:

| Field       | Type           | What it holds                                                                           |
| ----------- | -------------- | --------------------------------------------------------------------------------------- |
| `targetId`  | string         | The post on that channel: the target's id, as the API's `targets` list it               |
| `channelId` | string         | The channel                                                                             |
| `platform`  | string or null | The channel's platform, such as `mastodon`; null once the channel was disconnected      |
| `round`     | integer        | How many times the post was sent there: 1, and one more for each time it was sent again |

Every event's `data` has `workspaceId`, the workspace it happened in.

### post.scheduled [#post-scheduled]

A post was scheduled, or moved to another time.

| Field         | Type   | What it holds                                                                 |
| ------------- | ------ | ----------------------------------------------------------------------------- |
| `workspaceId` | string | The workspace                                                                 |
| `postId`      | string | The post                                                                      |
| `scheduledAt` | string | When it goes out, as an instant in UTC                                        |
| `timeZone`    | string | The IANA time zone it was scheduled in, such as `Europe/Paris`                |
| `targets`     | array  | The channels it goes out on, each with `targetId`, `channelId` and `platform` |

```json title="post.scheduled"
    "scheduledAt": "2026-11-10T09:00:00.000Z",
    "timeZone": "Europe/Paris",
    "targets": [
      {
        "targetId": "019a6f3e-8c2b-7d02-8a11-6e2f9b0c7d15",

  }
```


### post.failed [#post-failed]

The post did not go out on the channel.

| Field         | Type           | What it holds                                                  |
| ------------- | -------------- | -------------------------------------------------------------- |
| `workspaceId` | string         | The workspace                                                  |
| `postId`      | string         | The post                                                       |
| `targetId`    | string         | The post on that channel                                       |
| `channelId`   | string         | The channel                                                    |
| `platform`    | string or null | The channel's platform; null once the channel was disconnected |
| `round`       | integer        | How many times the post was sent there                         |
| `failedAt`    | string         | When it failed, as an instant in UTC                           |
| `reason`      | string         | Why, one of the codes below                                    |

| `reason`              | What happened                                                                                                                     |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `contentRejected`     | The platform refused the post's text or format.                                                                                   |
| `channelDisconnected` | The channel was disconnected from the workspace before the post went out. Nothing was sent.                                       |
| `channelDisabled`     | The channel was turned off before the post went out. Nothing was sent.                                                            |
| `mediaRemoved`        | One of its images or videos was deleted, or was no longer ready, before the post went out. Nothing was sent.                      |
| `mediaRejected`       | The platform refused one of its images or videos.                                                                                 |
| `missed`              | The server was down at the scheduled time, and the post was too late to send when it came back.                                   |
| `notPublished`        | A member checked an unconfirmed post on the platform and did not find it.                                                         |
| `rateLimited`         | The platform kept limiting Peal until the attempt gave up.                                                                        |
| `tokenExpired`        | The platform refused the channel's authorization: the channel must be reconnected.                                                |
| `unavailable`         | The platform could not be reached. Nothing was sent.                                                                              |
| `appNotAudited`       | The platform takes only some posts from the server's app until it approves it. Nothing was sent.                                  |
| `quotaExceeded`       | A daily allowance of uploads on the platform stayed used up until the attempt gave up.                                            |
| `appBillingLimit`     | The platform refused the server's app until its operator pays for it. Nothing was sent.                                           |
| `planLimit`           | The workspace's plan had no room for the post when it was due: too many channels, or the month's posts used up. Nothing was sent. |

[Notifications](/notifications#events) tells what to do about each.

```json title="post.failed"

  "type": "post.failed",
  "version": 1,
  "timestamp": "2026-11-10T09:00:04.000Z",
  "data": {
    "workspaceId": "7b1f6c1e-2d4a-4f0b-9c3e-5a8d2e6f1b90",
    "postId": "019a6f3e-8c2a-7b1e-9f40-3d5a1c2b4e01",
    "targetId": "019a6f3e-8c2b-7d03-b5c2-0f4e8a1d3c26",
    "channelId": "019a5d12-9b0e-7e44-9d1f-2c3b4a5d6e7f",
    "platform": "bluesky",
    "round": 1,
    "failedAt": "2026-11-10T09:00:04.000Z",
    "reason": "tokenExpired"
  }
}
```

### post.unconfirmed [#post-unconfirmed]

Peal cannot tell whether the post went live on the channel, and never sends it again on its own: someone checks the platform, then [confirms it or posts it again](/scheduling#follow-up). Once a member says what they found, a `post.published`, or a `post.failed` with the reason `notPublished`, follows for the same `round`; a repost brings the events of the next round.

| Field         | Type           | What it holds                                                  |
| ------------- | -------------- | -------------------------------------------------------------- |
| `workspaceId` | string         | The workspace                                                  |
| `postId`      | string         | The post                                                       |
| `targetId`    | string         | The post on that channel                                       |
| `channelId`   | string         | The channel                                                    |
| `platform`    | string or null | The channel's platform; null once the channel was disconnected |
| `round`       | integer        | How many times the post was sent there                         |
| `attemptedAt` | string         | When the attempt was made, as an instant in UTC                |
| `reason`      | string         | Why Peal cannot tell, one of the codes below                   |

| `reason`             | What happened                                                            |
| -------------------- | ------------------------------------------------------------------------ |
| `noResponse`         | The request may have reached the platform, and no answer came back.      |
| `unreadableResponse` | An answer came back that Peal could not read.                            |
| `interrupted`        | The server stopped during the call, so whether it went out is not known. |
| `adapterFailure`     | Peal's own code failed during the call, after the request may have left. |

```json title="post.unconfirmed"
{
  "id": "019a6f40-2f6b-7a1c-9d2e-5b4c3a2f1e05",
  "type": "post.unconfirmed",
  "version": 1,
  "timestamp": "2026-11-10T09:00:21.000Z",
  "data": {
    "workspaceId": "7b1f6c1e-2d4a-4f0b-9c3e-5a8d2e6f1b90",
    "postId": "019a6f3e-8c2a-7b1e-9f40-3d5a1c2b4e01",
    "targetId": "019a6f3e-8c2b-7d02-8a11-6e2f9b0c7d15",
    "channelId": "019a5d10-41f7-7c3a-a2b9-8d6e0f1a2b3c",
    "platform": "linkedin",
    "round": 1,
    "attemptedAt": "2026-11-10T09:00:01.000Z",
    "reason": "noResponse"
  }
}
```

### post.cancelled [#post-cancelled]

The post was cancelled. `targets` are the channels it will not go out on; a channel it had already reached keeps its own event. A channel Peal was sending to at that moment ends with its own event: `post.published`, `post.failed` or `post.unconfirmed` if the platform was called, or a `post.cancelled` naming it alone if it was not.

| Field         | Type   | What it holds                                                                        |
| ------------- | ------ | ------------------------------------------------------------------------------------ |
| `workspaceId` | string | The workspace                                                                        |
| `postId`      | string | The post                                                                             |
| `cancelledAt` | string | When it was cancelled, as an instant in UTC                                          |
| `targets`     | array  | The channels it will not go out on, each with `targetId`, `channelId` and `platform` |

```json title="post.cancelled"
{
  "id": "019a6f40-2f6b-7a1c-9d2e-5b4c3a2f1e06",
```

### media.failed [#media-failed]

The file was refused, or Peal could not read it. A file that could not be read stays in the library, and is not ready for posts.

| Field         | Type   | What it holds               |
| ------------- | ------ | --------------------------- |
| `workspaceId` | string | The workspace               |
| `mediaId`     | string | The media                   |
| `reason`      | string | Why, one of the codes below |

| `reason`       | What happened                                                          |
| -------------- | ---------------------------------------------------------------------- |
| `sizeMismatch` | The stored file is not the size the upload declared. It was refused.   |
| `typeMismatch` | The stored file is not the type the upload declared. It was refused.   |
| `unreadable`   | The file is damaged, or not in a format Peal reads.                    |
| `timedOut`     | Reading the file took longer than Peal allows.                         |
| `tooLarge`     | The store served more bytes than Peal stores for the file's kind.      |
| `toolFailed`   | The program that reads files could not run, or printed nothing usable. |
| `unavailable`  | The instance has nothing to read this kind of file with.               |

```json title="media.failed"
{
  "id": "019a6f40-2f6b-7a1c-9d2e-5b4c3a2f1e0b",
  "type": "media.failed",

  "timestamp": "2026-11-09T16:31:20.000Z",
  "data": {

    "reason": "typeMismatch"
  }
}
```

## Delivery and retries [#delivery]

Your server has 15 seconds to answer. Any answer in the 200s is a success. Anything else is a failure: another status, the 300s included, no answer in time, or a connection that could not be made or broke.

A failed delivery is tried again, 8 attempts in all, over about a day:

| Attempt | When                              |
| ------- | --------------------------------- |
| 1       | At once                           |
| 2       | 5 seconds after the first failed  |
| 3       | 5 minutes after the second failed |
| 4       | 30 minutes after the third failed |
| 5       | 2 hours after the fourth failed   |
| 6       | 5 hours after the fifth failed    |
| 7       | 8 hours after the sixth failed    |
| 8       | 8 hours after the seventh failed  |

After the eighth, the delivery has failed for good. You can still [send it again](#log) by hand.

Peal turns an endpoint off on its own in two cases, and then tells the members who manage webhooks, with a notification and an email:

- **It answers `410 Gone`.** The delivery fails at once, without another attempt, and the endpoint is turned off: the answer says it wants nothing more.
- **Every attempt has failed for 5 days.** One success in between starts the count again.

Turn the endpoint back on once it answers: it gets its 5 days again.

## Order and duplicates [#ordering]

Deliveries can arrive out of order, and more than once. Each event is delivered on its own, with its own retries, so an event whose first attempt failed arrives after the ones that came later; and an attempt your server answered too late, or whose answer was lost, is made again.

- **Deduplicate on `webhook-id`.** Keep the ids you have handled, and answer a success for one you already have.
- **Do not rely on arrival order.** Use the instants in `data` (`publishedAt`, `failedAt`, `scheduledAt` and the like) and the event's `timestamp`, and read the post or the channel through the API when you need its current state.

## The delivery log [#log]

Each endpoint has a log of its deliveries, newest first, kept 30 days. For each one it shows:

- the event's type and id;
- its status: pending, succeeded or failed, and for a failed one, why: every attempt failed, the endpoint answered `410 Gone`, the endpoint was turned off before it got through, or the instance can no longer read the endpoint's secret;
- the status your server answered the last attempt with, or why no answer came: none in time, a connection that failed, or an address Peal no longer sends to;
- how long the last attempt took, how many attempts were made, and when the next one is.

For an answer that was not a success, the log keeps the start of what your server said, to help you tell what went wrong: one line, 256 characters at most. Peal keeps nothing else of an answer, and nothing of a successful one.

Two actions help while you build:

- **Send a test event** sends the endpoint a [`webhook.test`](#webhook-test) event.
- **Send again** sends a delivery's event to the endpoint once more, as a new delivery of the same event: same `webhook-id`, same body, a new timestamp and a new signature. A server that deduplicates will see it as one it already handled.

A workspace sends 30 test events and deliveries again an hour at most, counted together: past it, both answer `TooManyWebhookSends` (429) until the hour is over.

Both need the endpoint to be on.

## Verify a delivery [#verify]

Anyone who learns the address can send it requests, so verify each one before acting on it. The signature covers the event's id, the attempt's timestamp and the body, joined with full stops:

```text
<webhook-id>.<webhook-timestamp>.<body>
```

It is an HMAC-SHA256 of that text, keyed with the bytes the secret holds in base64 after `whsec_`, written in base64 after `v1,`. During a [rotation](#secret), the header holds two of them, separated by a space: accept the request when either matches.

Verify the body as it arrived, byte for byte. A body parsed as JSON and written out again is no longer the text that was signed.

Without a library, the check is short. This one is Node's, with a comparison in constant time and five minutes of tolerance on the timestamp:

```js verify.mjs
import { createHmac, timingSafeEqual } from "node:crypto";

const tolerance = 5 * 60;

// `rawBody` is the request body as received, a string or a Buffer.
export const verify = (secret, headers, rawBody) => {
  const id = headers["webhook-id"];
  const timestamp = headers["webhook-timestamp"];
  const signatures = headers["webhook-signature"];

  if (!id || !timestamp || !signatures) {
    return false;
  }

  // Too old or too far ahead: a request someone kept to send again.
  const age = Math.abs(Date.now() / 1000 - Number(timestamp));

  if (!(age <= tolerance)) {
    return false;
  }

  const key = Buffer.from(secret.replace(/^whsec_/, ""), "base64");
  const expected = createHmac("sha256", key)
    .update(`${id}.${timestamp}.`)
    .update(rawBody)
    .digest();

  // One signature per valid secret: any of them may match.
  return signatures.split(" ").some((signature) => {
    const [version, mac = ""] = signature.split(",");
    const given = Buffer.from(mac, "base64");

    return (
      version === "v1" &&
      given.length === expected.length &&
      timingSafeEqual(given, expected)
    );
  });
};
```

## Security [#security]

- **Verify every request before acting on it**, on the bytes that arrived, and answer an error to one that does not verify.
- **Refuse old timestamps.** A `webhook-timestamp` more than a few minutes from your clock is a request someone kept to send again. The libraries allow five minutes.
- **Deduplicate on `webhook-id`**, so a delivery made twice is handled once.
- **Answer fast, work later.** Answer a success as soon as the request is verified and stored, and do the work after: an answer that takes more than 15 seconds counts as a failure, and the delivery comes again.
- **Keep the secret secret.** Hold it where your server keeps its other secrets, never in code or in logs, and [rotate it](#secret) if it may have leaked.
- **Avoid secrets in the address.** Peal shows an endpoint's address to the members who manage webhooks. The signature is what proves a request is Peal's.
- **Do not filter on Peal's address.** Requests come from the addresses of the Peal server. On your own instance those are yours to know; Peal Cloud does not promise to keep its own fixed.
- **Confirm before anything that cannot be undone.** A payload says what happened when it was sent. Read the post or the channel through the API before you act on it for good.

## Through the API [#api]

| Endpoint                                                                                     | What it does                                                      |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `GET /api/workspaces/{workspaceId}/webhooks`                                                 | Lists the endpoints, oldest first                                 |
| `POST /api/workspaces/{workspaceId}/webhooks`                                                | Adds an endpoint, and answers its `secret` once                   |
| `GET /api/workspaces/{workspaceId}/webhooks/{endpointId}`                                    | Shows one                                                         |
| `PATCH /api/workspaces/{workspaceId}/webhooks/{endpointId}`                                  | Changes its address, description or events, or turns it on or off |
| `DELETE /api/workspaces/{workspaceId}/webhooks/{endpointId}`                                 | Deletes it, with its secret and its log                           |
| `POST /api/workspaces/{workspaceId}/webhooks/{endpointId}/secret`                            | Rotates its secret, and answers the new one once                  |
| `POST /api/workspaces/{workspaceId}/webhooks/{endpointId}/test`                              | Sends it a test event                                             |
| `GET /api/workspaces/{workspaceId}/webhooks/{endpointId}/deliveries`                         | Lists its deliveries, newest first, 30 a page                     |
| `POST /api/workspaces/{workspaceId}/webhooks/{endpointId}/deliveries/{deliveryId}/redeliver` | Sends a delivery's event again                                    |

The two `GET` lists and the endpoint itself need `webhook:read`; everything else needs `webhook:manage`.

```bash
curl https://api.example.com/api/workspaces/$WORKSPACE_ID/webhooks \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://hooks.example.com/peal",
    "description": "Order system",
    "eventTypes": ["post.published", "post.failed", "post.unconfirmed"]
  }'
```

The answer holds the `endpoint` and its `secret`. Later answers never hold the secret again.

Errors come in the API's format, each with a `code` in snake case beside its name, such as `webhook_url_refused` for `WebhookUrlRefused` ([Errors](/api-conventions#errors)). An API key's requests count towards its [rate limit](/api-conventions#rate-limits).

| ------ | ------------------------- | ----------------------------------------------------------------------------- |

| 404    | `WebhookDeliveryNotFound` | The endpoint has no delivery with this id, or its log no longer keeps it.     |
| 409    | `TooManyWebhookEndpoints` | The workspace already has 10 endpoints.                                       |
| 409    | `WebhookEndpointDisabled` | A test or a resend was asked of an endpoint that is off.                      |

## Self-hosting [#self-hosting]

Webhooks need no setting of their own. Signing secrets are encrypted with the keys in [`PEAL_TOKEN_KEYS`](/environment-variables#channels), as the tokens of connected channels are. Without it, the instance starts, and adding an endpoint or rotating a secret answers 503 `WebhooksNotConfigured`.

Deliveries leave from the server, so it must be able to reach your receivers over HTTPS. They only go to public addresses: an endpoint on `localhost` or inside your private network is refused, on your own instance too.
