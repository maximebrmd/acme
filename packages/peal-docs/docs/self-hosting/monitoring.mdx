Watch your instance from a second machine, so you hear about it when the server's own alerting is down, and export its telemetry to an OpenTelemetry collector.

## Watching it from outside [#uptime]

Grafana's alerts come from the server they watch: when that server, its network or Grafana stops, they stop too. Watch the instance from another machine as well, one that shares nothing with it, and alerts by a way of its own.

Check what people reach, through your edge:

| Check                                     | Passes when                                                     |
| ----------------------------------------- | --------------------------------------------------------------- |
| `GET /api/ready`                          | It answers `204 No Content`: the server and its database answer |
| A page of the web app, such as `/sign-in` | It answers `200`                                                |
| The certificate                           | It has time left                                                |

Count a redirect as a failure, so a sign-in page in front of the instance never passes for it.

### Grafana's heartbeat [#heartbeat]

Have Grafana show that its alerting works. With these set, a rule that always fires posts to `PEAL_HEARTBEAT_URL` every 5 minutes or so, with the token as a bearer token:

| Setting                  | Value                                                 |
| ------------------------ | ----------------------------------------------------- |
| `PEAL_GRAFANA_HEARTBEAT` | `./config/production/grafana/alerting/heartbeat.yaml` |
| `PEAL_HEARTBEAT_URL`     | The checker's push address                            |
| `PEAL_HEARTBEAT_TOKEN`   | The checker's token                                   |

When the posts stop, Grafana, Prometheus or the way out is down, and the other alerts may not reach you either: the checker says so. With [Gatus](https://github.com/TwiN/gatus), make it an external endpoint with a heartbeat interval of 15 minutes, and set `PEAL_HEARTBEAT_URL` to its push address, `https://<gatus>/api/v1/endpoints/<group>_<name>/external?success=true`. [Environment variables](/self-hosting/environment-variables#compose) lists these settings.

Peal's own servers are watched this way: [Deployment](https://github.com/peal-social/peal/blob/main/packages/peal-infra/DEPLOYMENT.md#uptime) describes the uptime server, whose Ansible and Gatus configuration are in `packages/peal-infra/ansible`.

## Telemetry [#telemetry]

Set `OTEL_EXPORTER_OTLP_ENDPOINT` to an OpenTelemetry collector's OTLP/HTTP address, such as `http://otel-collector:4318`, and the server exports its logs, metrics and traces there, as JSON. [Environment variables](/self-hosting/environment-variables#telemetry) lists the other OpenTelemetry settings it reads.

### Web app errors [#web-errors]

The web app reports its errors to the server, at `POST /api/client-errors`: what nothing caught in a browser, promises rejected without a handler, the error pages its boundaries show, and the pages its own server failed to render. A browser sends each error once, and ten at most a page.

A report names nobody. It sends no cookie, and holds the error's message and stack, the page's path without its query or fragment and with its ids replaced, the page's route, the release and the browser's user agent. The server replaces any email address, id, API key, token or link's query the report still quotes, and drops control characters.

The server takes 30 reports a minute from each address, which it reads from the header `AUTH_IP_HEADERS` names, and 16 KiB at most each. It logs each one at error level, with the event name `peal.client_error` and OpenTelemetry's attribute names (`exception.message`, `exception.stacktrace`, `url.path`, `http.route`, `user_agent.original`, and `peal.client_error.kind` and `peal.web.release`). Find them here:

| Where      | What                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| Metrics    | `peal.client_errors`, by kind; the reports it drops, in `peal.client_errors.dropped`, by reason                 |
| Prometheus | `peal_client_errors_total` and `peal_client_errors_dropped_total`                                               |
| Loki       | `{service_name="peal-server"} \| event_name="peal.client_error"`                                                |
| Grafana    | The production stack's **Web app errors** dashboard, which warns when more than 20 reports arrive in 10 minutes |

The alert on the server's own error logs leaves them out. Set `PEAL_RELEASE` on the web app to name the release its reports come from: the production stack sets it to `PEAL_VERSION`.
