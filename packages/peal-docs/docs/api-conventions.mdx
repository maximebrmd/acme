Every endpoint of the [API](/api-overview) follows the rules on this page, so a client written for one handles them all. The [API reference](/reference) says what each endpoint takes and answers; this page says what they share.

## Requests and answers [#requests]

Requests go to the address you open Peal at, under `/api`. Bodies are JSON, sent with `Content-Type: application/json`, and so are answers, apart from those with no body (204).

Every answer carries an `X-Request-Id` header, whatever answered it and whether or not it succeeded. Send your own `X-Request-Id` and Peal keeps it, when it is 8 to 128 characters out of letters, digits, `.`, `_`, `:` and `-`; otherwise the server issues one, a UUIDv7. The id is on every line the server logs for the request (`peal.request_id`), in the body of every error (`requestId`) and in the workspace's [activity log](/settings#activity). Log it on your side, and quote it when you ask for help.

```bash
curl -i https://api.example.com/api/workspaces/$WORKSPACE_ID/channels \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "X-Request-Id: nightly-sync:2026-11-16:0042"
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: nightly-sync:2026-11-16:0042
RateLimit-Policy: "default";q=600;w=60
RateLimit: "default";r=599;t=42
```

The API only adds to what it answers ([Versioning](#versioning)): ignore the fields, the values and the errors your client does not know.

## Authentication [#authentication]

Apart from the health checks, the changelog and the [discovery documents](#discovery), every endpoint of the API needs a credential, sent as `Authorization: Bearer …`. The exceptions answer someone who is no member, by other means: the pages of a [connect link](/embedding) or a [review link](/review), which answer the link's token; the platforms' data deletion callbacks, which the platform signs; and what the web app's own pages send before anyone signs in (its error reports, the captcha's site key, the sign-in routes under `/api/auth`). The credentials:

| Credential            | Acts as                                            | Allowed                                                                                                             |
| --------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| An API key, `peal_…`  | The key itself, in the one workspace it belongs to | The permissions chosen when it was created, such as `post:read` or `post:schedule` ([API keys](/settings#api-keys)) |
| An OAuth access token | The member who signed the application in           | What the member's role allows, within the scopes they granted ([What each permission allows](/agents#scopes))       |

The web app's session cookie is for the web app. [Authentication](/api-overview#authentication), in the overview, describes each credential.

Each endpoint's reference names the permission it needs. An OAuth token needs the scope that carries it too: `workspace:read` to read, `workspace:write` to change something, and `workspace:publish` for whatever needs `post:schedule`. What reaches an ad network takes `workspace:ads` too: beside `workspace:write` for `ads:manage`, beside `workspace:publish` for `ads:spend` ([Ads](/ads#access)).

| Status | Code              | When                                                                                          |
| ------ | ----------------- | --------------------------------------------------------------------------------------------- |
| 401    | `unauthenticated` | No credential, or one that no longer works: a key revoked or expired, a token past its time.  |
| 403    | `forbidden`       | The credential works but does not allow the request. `reason` says why ([below](#forbidden)). |
| 404    | `not_found`       | No such resource, or a workspace the caller does not belong to.                               |

## Errors [#errors]

Every error is a JSON object with the same four fields, then the error's own:

| Field       | What it holds                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `code`      | The error's name for programs, in snake case, such as `post_not_found`. It never changes once published: branch on it.                           |
| `_tag`      | The same name as clients generated from the contract match on it, such as `PostNotFound`. It never changes either.                               |
| `message`   | One or two sentences in English, for the person reading a log or a terminal. Its wording may change: never parse it.                             |
| `requestId` | The request's id, as its `X-Request-Id` header gives it.                                                                                         |
| others      | What the error says of itself, as the reference lists for each: the `status` a post has, the `limit` a plan reached, the `violations` of a post. |

Two families of routes answer differently, as their own clients expect: the sign-in service's routes under `/api/auth`, and the [MCP endpoint](/mcp), which answers JSON-RPC errors. Their answers carry `X-Request-Id` too.

### A request that cannot be read [#invalid-request]

A request that does not match what its endpoint takes answers 400 `invalid_request`, and nothing was done. `issues` lists what was found wrong, 20 problems at most: each has a `path`, which starts with the part of the request (`path`, `query`, `headers` or `body`) and goes down to the value, and a `message`. `field` is the first problem's path, dotted. Reading may stop at the first problem, so fixing what is listed can show another.

```bash
curl -i "https://api.example.com/api/workspaces/$WORKSPACE_ID/media?limit=500" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Request-Id: 019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37
```

```json
{
  "_tag": "InvalidRequest",
  "code": "invalid_request",
  "message": "The request does not match what the endpoint takes: `issues` says what and where. Nothing was done.",
  "requestId": "019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37",
  "field": "query.limit",
  "issues": [
    {
      "path": ["query", "limit"],
      "message": "Expected a value between 1 and 100"
    }
  ]
}
```

A value of the right shape that cannot be used where it was sent, such as a cursor taken from another list, answers 400 `bad_request`.

### A request that is not allowed [#forbidden]

A 403 says why in `reason`, names the `permission` the request takes when one is missing, and the `scope` to ask for when an OAuth application lacks it. Its `message` says how to get what is missing.

| `reason`            | Why                                                                                    | What to do                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `missingScope`      | The member may do this, but did not give the application the scope it takes (`scope`). | The member connects the application again and allows it; `peal login` for the command line. |
| `missingPermission` | The member's role, or the API key, lacks `permission`.                                 | An owner or an admin changes the role, or creates a key that has it.                        |
| `personRequired`    | Only a person in their own session does this, in the web app.                          | Nothing a key or an application can do.                                                     |
| `wrongWorkspace`    | The key or the token belongs to another workspace.                                     | Use it there, or use a credential of this workspace.                                        |
| `suspended`         | The account is suspended.                                                              | Write to the people who run the server.                                                     |
| `untrustedOrigin`   | A browser sent the session's cookie from another site.                                 | Send an API key or an OAuth token instead.                                                  |

A token that lacks a scope also gets the challenge OAuth clients read, in `WWW-Authenticate`:

```bash
curl -i -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/019a6c3f-1b72-7d3c-8e90-4f5a6b7c8d02/cancel \
  -H "Authorization: Bearer $PEAL_ACCESS_TOKEN"
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
WWW-Authenticate: Bearer error="insufficient_scope", scope="workspace:publish"
X-Request-Id: 019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68
```

```json
{
  "_tag": "Forbidden",
  "code": "forbidden",
  "message": "This application was not given the scope workspace:publish (schedule and publish posts), which this request takes (permission post:schedule). Its user connects it to Peal again and allows it; for Peal's command line, run peal login again and approve it.",
  "requestId": "019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68",
  "reason": "missingScope",
  "permission": "post:schedule",
  "scope": "workspace:publish"
}
```

### What to do with an error [#handling]

| Answer                   | What it means                                                           | What a client does                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400                      | The request is wrong.                                                   | Fix it as `issues` or `message` say. Sending it again unchanged fails again.                                                                                  |
| 401                      | The credential does not work.                                           | Renew the access token with the refresh token, or use a key that works.                                                                                       |
| 402 `plan_limit_reached` | The workspace's plan has no room.                                       | Tell the person: `planWithRoom` and `billingUrl` say where to go. Do not retry.                                                                               |
| 403                      | The credential does not allow it.                                       | Read `reason`. Do not retry until the scope or the permission is given.                                                                                       |
| 404                      | Nothing there for this caller.                                          | Check the ids and the workspace. Do not retry.                                                                                                                |
| 409                      | What the request acts on is not in a state that allows it.              | Read it again, then decide: a post already scheduled needs no second request.                                                                                 |
| 413, 422                 | The content was refused.                                                | Fix it as the error's fields say: `violations`, `channelIds`, `mediaIds`, `reason`.                                                                           |
| 429 `too_many_requests`  | The credential passed its [rate limit](#rate-limits). Nothing was done. | Wait as `Retry-After` says, then send the request again.                                                                                                      |
| 429, another code        | A limit of one feature, such as the assistant's daily requests.         | Wait as the error says (`resetsAt`), or a moment for `media_import_busy`.                                                                                     |
| 500 `internal_error`     | The server failed, and recorded it.                                     | Retry a read. For a write, read what it acts on first: it may have been applied. Resend `posts.send` only with the same `Idempotency-Key`. Quote `requestId`. |
| 502, 503                 | The server, or a service it needs, cannot answer for now.               | Retry with a growing delay, a few times, under the same `Idempotency-Key` where the endpoint takes one.                                                       |

## Ids and instants [#ids]

Ids are strings. Posts, their targets, channels and media have UUIDv7 ids, such as `019a6c3f-1b72-7d3c-8e90-4f5a6b7c8d02`; workspaces and users have random UUIDs; API keys and applications have ids of another shape. Treat every id as an opaque string: compare it, store it, send it back, and read nothing from it. Ids are written in lowercase.

### Instants and time zones [#instants]

- Answers give instants in ISO 8601, in UTC, such as `2026-11-16T08:00:00.000Z`. Send them the same way.
- Scheduling takes an instant and the IANA time zone it was chosen in, such as `Europe/Paris`, which Peal keeps with the post. An offset such as `+01:00` is not a time zone, and answers 422 `invalid_time_zone`.
- A time up to a minute in the past counts as now; an earlier one answers 422 `schedule_in_past`.
- Analytics take calendar days, such as `2026-11-16`, with the time zone the days run in.

## Paging [#paging]

Lists that can grow without end are read a page at a time, newest first. The query takes `limit`, the size of a page, and `cursor`; the answer is an object with the page's `items` and a `nextCursor`. Pass `nextCursor` as `cursor` to read the next page, and stop when it is `null`. A cursor is an opaque string, good for the list it came from, with the same filters: elsewhere it answers 400 `bad_request`.

| List                                     | A page holds | At most |
| ---------------------------------------- | ------------ | ------- |
| `GET …/posts/drafts`                     | 20           | 50      |
| `GET …/media`                            | 30           | 100     |
| `GET …/webhooks/{endpointId}/deliveries` | 30           | 100     |
| `GET …/activity`                         | 30           | 100     |
| `GET /api/me/notices`                    | 20           | 100     |

Paths starting with `…` are under `/api/workspaces/{workspaceId}`.

```bash
curl "https://api.example.com/api/workspaces/$WORKSPACE_ID/activity?limit=2" \
```

The lists a workspace keeps short answer whole, as an array: its channels, members, pending invitations, API keys and webhook endpoints.

## Idempotency [#idempotency]

A request whose answer was lost, to a timeout or a dropped connection, may or may not have been applied. Sending it again must not post twice.

`POST …/posts/send`, which creates a post and sends it, takes an `Idempotency-Key` header: any text of your choosing, 255 characters at most, such as a UUID, new for each post.

- Within 24 hours, the same key with the same body answers the post the first request made, as it now stands, and makes no other.
- The same key with another body answers 409 `idempotency_key_reused`, and makes nothing.
- Once that post was deleted, the key answers 404 `post_not_found`.

Keys are kept per workspace. [Posting from an AI agent](/agents#api) shows a whole request.

`POST …/posts/bulk` and `POST …/posts/import` take the same header, for the whole request, and each of their items or rows may carry a key of its own ([Posting through the API](/posting-api)); creating a customer's workspace through the partner API takes one too ([Embedding Peal](/embedding)).

`POST …/inbox/comments/{commentId}/replies`, which answers a comment in public, takes the header too: within 24 hours, the same key with the same comment and text answers the reply the first request made, however it stands, and writes no other; with another comment or text it answers 409 `idempotency_key_reused`. Without a key, a second request is refused (409 `reply_pending`) only while the first reply is on its way or unconfirmed.

`POST …/ads/boosts`, which spends money, requires the header: the same key with the same request answers the boost it made and never makes another, and with another request answers 409 `boost_key_reused` ([Ads](/ads#api-boost)).

The other writes take no key. Whether one is safe to send again depends on what it does:

| Request                                                                           | Sent again                                                                                                                                                                                        |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reads (`GET`)                                                                     | Safe.                                                                                                                                                                                             |
| `PUT`, `PATCH` and `DELETE`                                                       | Safe: they set a resource to what the request says, or remove it. A second `DELETE` answers 404.                                                                                                  |
| Scheduling, moving, unscheduling or cancelling a post, confirming a target        | Safe: they act on one post, by its id, which goes out once however often it is scheduled. A repeat changes nothing more, or answers 409 with the `status` the post has.                           |
| Creating a draft, importing media, adding a webhook endpoint, creating an API key | Makes another one. None of them puts anything out: list what the workspace has before sending again, and delete a duplicate.                                                                      |
| Inviting someone                                                                  | Replaces the pending invitation to that address, and emails it again.                                                                                                                             |
| Reposting a target (`POST …/posts/{postId}/targets/{targetId}/repost`)            | Not safe: each repost sends the post again on that channel. Read the post first: only a target that failed or is unconfirmed can be reposted, and any other answers 409 `target_status_conflict`. |

### Unconfirmed outcomes [#unconfirmed]

Peal has the same problem with the platforms. When a platform's answer is lost, Peal looks the post up there where the platform allows it; when it cannot tell whether the post went out, the target is `unconfirmed` rather than sent again, since a second attempt could show the post twice. Do the same: never repost an unconfirmed target blindly. Have someone look on the platform, then record what they found with `…/targets/{targetId}/confirm`, or repost ([Follow up on a post](/scheduling#follow-up)).

Each publishing attempt, in `GET …/posts/{postId}/attempts`, says how it ended in `result`, and carries in `refusalCode` the code behind a refusal: the platform's own, as it gave it, or Peal's when Peal refused before calling the platform; `null` when there is none. The platforms' codes are theirs and change with them: show them, log them, and branch on `result`.

## Rate limits [#rate-limits]

Each API key may send 600 requests a minute, a [partner key](/embedding) too, across every workspace it acts in, and so may each application for each member it acts for, whichever of its access tokens it sends. The count is shared between the API and the [MCP endpoint](/mcp), and kept in fixed windows of one minute that start on the minute. Sessions of the web app are not counted. On your own server, `PEAL_API_REQUESTS_PER_MINUTE` sets another number ([Environment variables](/environment-variables#core)).

Every answer to a counted credential says where it stands, in the headers of the IETF draft "RateLimit header fields for HTTP":

| Header             | Example                | What it says                                                                          |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------------- |
| `RateLimit-Policy` | `"default";q=600;w=60` | The policy: `q` requests every `w` seconds.                                           |
| `RateLimit`        | `"default";r=412;t=23` | What is left: `r` requests, for `t` more seconds, after which the count starts again. |
| `Retry-After`      | `23`                   | On a 429 only: how many seconds to wait.                                              |

A 429 `platform_rate_limited` is another thing: a platform asked Peal to slow down, as a [lookup](/api-overview) can find, and this count is untouched. The hosted pages of connect links and review links, which take no key, have limits of their own by address.

Past the limit, the request answers 429 `too_many_requests`, and nothing was done:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
RateLimit-Policy: "default";q=600;w=60
RateLimit: "default";r=0;t=17
Retry-After: 17
X-Request-Id: 019a7b33-41c7-7d50-a2e9-6b8c0d1e2f3a
```

```json
{
  "_tag": "TooManyRequests",
  "code": "too_many_requests",
  "message": "This credential sent more than `limit` requests in `windowSeconds` seconds: nothing was done. Wait `retryAfterSeconds` seconds, as the `Retry-After` header says, then send the request again. Every answer to a key or a token carries the `RateLimit-Policy` and `RateLimit` headers, which say how many requests are left.",
  "requestId": "019a7b33-41c7-7d50-a2e9-6b8c0d1e2f3a",
  "limit": 600,
  "windowSeconds": 60,
  "retryAfterSeconds": 17
}
```

Wait `retryAfterSeconds`, then send the request again. A client that reads `RateLimit` slows down before it is refused. The MCP endpoint answers the same status and headers, with a JSON-RPC error. When the server cannot keep the count, it lets the request through.

Some features have a limit of their own, which this one does not replace:

| Limit                                                  | Error                      | See                                                |
| ------------------------------------------------------ | -------------------------- | -------------------------------------------------- |
| The writing assistant's requests per workspace and day | `assistant_quota_exceeded` | [Ask the writing assistant](/scheduling#assistant) |
| Imports running at once                                | `media_import_busy`        | [Media](/media)                                    |
| Test events and resends of webhooks per hour           | `too_many_webhook_sends`   | [The delivery log](/webhooks#log)                  |
| Pending invitations of a workspace                     | `too_many_invitations`     | [Invitations](/settings#invitations)               |
| What a plan allows, on a server that bills             | `plan_limit_reached`       | [Plans and billing](/billing#limits)               |

## Versioning [#versioning]

The API has no version in its path, and one version: it only grows. Fields, operations, values of an enumeration and errors are added; none is renamed, removed or made stricter. A client written today keeps working, provided that it ignores what it does not know:

- a field it does not read, in any answer or webhook payload;
- a value it does not know where a field lists its values, such as a new post status or failure reason: treat it as "something else", never as a failure to decode;
- an error code it does not know: fall back on the HTTP status, and show `message`.

A check holds the API to this. Every change to the contract is compared with the last released OpenAPI document, the one the SDKs were generated from (their release 0.3.0 today), and the project's tests fail on any change that could break a client: an operation, a field or a value removed or renamed, a parameter that became required, a type that changed.

A break is made only when decided on. It is then recorded with its reason, listed in the [changelog](#changelog) under `breaking`, and announced by a [deprecation](#deprecations) first wherever an endpoint goes away.

Webhook payloads follow the same rule, with a `version` of their own ([Versions](/webhooks#versions)).

## Deprecations [#deprecations]

An endpoint that is deprecated keeps answering as it always did. It says so in three places:

- the OpenAPI document marks its operation `deprecated`, which generated clients and editors show;
- every answer from it carries the headers below;
- the [changelog](#changelog) lists it, by operation, in the release that deprecated it.

| Header        | What it says                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `Deprecation` | Since when the endpoint is deprecated, as RFC 9745 writes it: `@` followed by seconds since 1970, such as `@1803859200`. |
| `Sunset`      | When it stops answering, once that is decided, as an HTTP date (RFC 8594), such as `Wed, 01 Sep 2027 00:00:00 GMT`.      |
| `Link`        | Where the deprecation is explained, with what to call instead, when there is such a page: `rel="deprecation"`.           |

`Sunset` and `Link` are there only when there is something to say: a deprecated endpoint without `Sunset` has no end decided. Have your client log any answer that carries `Deprecation`.

No endpoint is deprecated today.

| Field          | What it holds                                                                                        |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| `date`         | The day of the release.                                                                              |

| `operations`   | The operations it added, by operation id, such as `activity.list`.                                   |

## Discovery [#discovery]
