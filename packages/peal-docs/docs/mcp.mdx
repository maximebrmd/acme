Peal serves the Model Context Protocol (MCP), so an AI assistant, or any other MCP client, can work in a workspace for you: read its posts, media, analytics, billing and members, write drafts, schedule and publish posts when you allow it, follow up on posts that went out, and invite people. The client signs in as you, in a browser, and acts in the one workspace you pick, with no more than your role allows. An agent that runs with nobody to sign in connects with an [API key](#api-key) instead. [Posting from an AI agent](/agents) walks through a whole post.

## The endpoint [#endpoint]

The endpoint is `/api/mcp` at the address you open Peal at, such as `https://peal.example.com/api/mcp`. It speaks Streamable HTTP, in the protocol revisions 2026-07-28, 2025-11-25 and 2025-06-18.

`peal mcp`, from the [command line](/cli#mcp), prints the endpoint and a configuration most MCP clients take:

```json
{
  "mcpServers": {
    "peal": {
      "type": "http",
      "url": "https://peal.example.com/api/mcp"
    }
  }
}
```

Give the client this address, or this configuration, as its documentation says for a remote server over HTTP.

A client can read what it needs before it connects from the endpoint's server card, at `/api/mcp/server-card`, such as `https://peal.example.com/api/mcp/server-card`: the endpoint's address, the protocol revisions it speaks and the header that carries the credential. It needs no credential, and pages of any origin may read it ([Discovery](/api-conventions#discovery)).

## Sign the client in [#sign-in]

Peal signs MCP clients in with OAuth. You give the client no key: on its first request, Peal answers that it needs a token, and tells it where to ask for one.

1. The client registers itself with Peal, then opens a browser on Peal's sign-in page. Sign in if you are not signed in yet.
2. **Pick a workspace.** The client acts in that one workspace only. To use it in another, connect it again and pick the other one.
3. Peal shows what the client asks for, and where it sends you back afterwards. When it asks to publish, that has a line of its own, with a box you may untick to let it write drafts only ([What the client may do](#scopes)). Check both, then choose **Allow**, or **Deny**. Peal does not check who made a client that registered itself, and says so: allow one only if you trust it and started the connection yourself.

Back in the client, its tools work. Peal remembers your answer for that client and workspace, so connecting it again skips the question.

<Callout type="note" title="If the client cannot register">
  Most MCP clients register themselves before they sign in, which a Peal server
  allows only when its administrator turns it on (`MCP_DYNAMIC_REGISTRATION`,
  see [Self-hosting](/self-hosting#mcp)). `peal mcp` warns when it is off.
</Callout>

## Connect with an API key [#api-key]

An agent that runs on a server, with nobody there to sign in, sends a workspace's [API key](/settings#api-keys) instead of an OAuth token, in the `Authorization` header:

```json
{
  "mcpServers": {
    "peal": {
      "type": "http",
      "url": "https://peal.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer ${PEAL_API_KEY}"
      }
    }
  }
}
```

How a client reads a header from its environment depends on the client: see its documentation, and keep the key out of files you share. Send the key in that header only, never in the address: an address ends up in logs and histories.

- The connection acts in the key's workspace, with the key's permissions, and no scope: a key without `post:schedule` writes drafts at most. Create a key with only what the agent needs.
- `whoami` answers the key in `apiKey`, with its id and name, never the key itself; `user` and the workspace's `role` are `null`, since a key is nobody, and `permissions` lists what the key may do.
- The tools that only a person uses refuse a key: `list_members`, `list_invitations`, `invite_member` and `revoke_invitation`.
- What the key does is in the workspace's [activity log](/settings#activity), under the key's id and name.
- Revoking the key, under **API keys** in the workspace's settings, stops the agent at once.

## What the client may do [#scopes]

The consent page lists what the client asks for:

| Permission                                                                                                                      | Scope               | What it allows                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Know that it is you                                                                                                             | `openid`            | Your account's id                                                                                                                                                          |
| See your name and picture, see your email address                                                                               | `profile`, `email`  | Your profile                                                                                                                                                               |
| Stay connected while you are away, until you disconnect it                                                                      | `offline_access`    | Renew its access without you                                                                                                                                               |
| Read the workspace: posts, channels, media and analytics                                                                        | `workspace:read`    | Read, and change nothing                                                                                                                                                   |
| Do what your role allows in the workspace, such as writing drafts and managing media, without scheduling or publishing anything | `workspace:write`   | Anything your [role](/scheduling#roles) allows, reading included, but what puts posts out: nothing it does reaches a platform                                              |
| Let it schedule and publish posts to your connected accounts, where everyone can see them                                       | `workspace:publish` | What your role allows of what puts posts out, and reading: scheduling, moving, publishing and reposting a post, unscheduling it, cancelling it, and confirming how it went |

Publishing is a permission of its own. The consent page shows it on its own line, with a box that starts ticked: untick it, and the client gets the rest of what it asked for, and no more. Without it, a client that may write still writes drafts, which you review and schedule yourself; one that may only read still reads.

A client connected before publishing had its own permission holds the writing one alone: it publishes nothing, and no longer unschedules, reposts or confirms, until you connect it again and allow publishing. A connection keeps the permissions it was given until then.

A client that has none of the three workspace permissions can do nothing. Its access lasts 15 minutes at a time, and the client renews it on its own. Every request checks that you still belong to the workspace and are not banned.

## Tools [#tools]

Each tool acts as you, in the workspace the client signed in to, through the same checks as the web app: your role decides what it may do, and a client is refused what you did not allow it, with a message naming the permission it lacks: every change for a client you let read only, and whatever puts posts out for one you did not let publish. To grant more, connect it again and allow it there.

`find_tools` takes an `area` (`account`, `posts`, `media`, `reports`, `people`, `webhooks` or `connect`), a `query`, both or neither. "Needs publishing" means the permission to schedule and publish (`workspace:publish`), and a role that schedules posts: owner, admin or editor. What `schedule_post`, `publish_post`, `create_post`, `create_posts` and `repost_target` send is public on the platforms, and Peal cannot take it back once it is out.

Before a post is scheduled, it is checked against every channel's platform: text length, media types, sizes and counts, required options, and what the account itself refuses. When anything is wrong, nothing is scheduled, and the refusal lists every violation at once, each with its channel, and its field or media ([How refusals read](/agents#refusals)). `validate_post` answers the same list beforehand, and makes nothing.

`create_post` and `create_posts` also refuse a post whose content (the text the channel receives and the same media, in the same order) already goes to one of its channels less than 23 hours from its time, naming the post that has it: a call made twice by mistake makes no second post. `allowDuplicate: true` lets it through, for when you mean to post the same twice. Scheduling a draft with `schedule_post` is not checked ([Duplicate posts](/posting-api#duplicates)).

Annotations are hints a client may show you; the permission checks are the server's.

Each tool is written by hand, with a description of what it changes; none is generated from an endpoint of the API, and the API has endpoints no tool calls. A client that would rather not read every description calls `find_tools` first, and then reads only the tools it chose.

### What no tool hands out [#account-data]

No tool exports your data or lists the applications that act for you. An MCP client passes whatever its tools answer to an AI model, and your export holds your sessions' addresses, your invitations and everything you wrote: the instance refuses both to every OAuth client but the [command line](/cli#account), which you sign in at your own terminal and which saves them in your own files. Account settings, in the web app, show them too.

## Limits [#limits]

- A Peal instance serves MCP clients only when its address is HTTPS, or `localhost` for development. Elsewhere, the endpoint refuses every request.
- The endpoint refuses requests sent from web pages (with an `Origin` header): connect a client that runs on your computer or on a server.
- A connection may send 600 requests a minute, counted with the requests the same key or application sends to the API. Past it, the endpoint answers 429 with a `Retry-After` header ([Rate limits](/api-conventions#rate-limits)).
- Every answer carries an `X-Request-Id` header: quote it when you ask for help ([Requests and answers](/api-conventions#requests)).
- **Account settings**, in the web app, list the clients you allowed and disconnect them; `peal account apps` lists them from the [command line](/cli#account). Leaving the workspace stops every client that acts in it.
