The web app, the command line and the MCP endpoint are built on the same HTTP API, so your own code can do anything they do. This page says where requests go, how to authenticate, and what each group of endpoints holds.

[API conventions](/developers/conventions) describes what every endpoint shares: request ids, the format of errors and every error code, paging, idempotency, rate limits, and how the API changes over time.

<Callout type="note" title="The API only grows">
  Fields, operations, values and errors are added; none is renamed, removed or
  made stricter. Write clients that ignore what they do not know
  ([Versioning](/developers/conventions/versioning#versioning)).
</Callout>

## One contract [#contract]

The API is defined once, in the `peal-contract` package. The server implements that definition, the clients derive their types from it, and the [API reference](/reference) in these docs is generated from it, so the three cannot drift apart.

## Base URL [#base-url]

Requests go to the address you open Peal at, and every endpoint's path starts with `/api`: the web app forwards `/api/*` to the server. In these docs, `https://api.example.com` stands for that address; replace it with your own.

```bash
curl -i https://api.example.com/api/health
```

## Authentication [#authentication]

Apart from the health checks and the documents platforms read about Peal, every endpoint needs one of these credentials:

| Credential         | Sent as                                | For                                                                                                           | What it may do                                                                                                                                                                                                                                                             |
| ------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API key            | `Authorization: Bearer peal_…`         | Scripts and integrations                                                                                      | It belongs to one workspace and holds some of the permissions of the member who created it, never more: a key without `post:schedule` neither schedules nor publishes. It may send 600 requests a minute ([Rate limits](/developers/conventions/rate-limits#rate-limits)). |
| Partner key        | `Authorization: Bearer peal_partner_…` | A product that uses Peal for its own customers                                                                | It belongs to a partner account, creates and reads the workspaces that account owns under `/api/partner`, and acts inside each of them, and in no other workspace, with the permissions it was given ([Embedding Peal](/developers/embedding)).                            |
| OAuth access token | `Authorization: Bearer …`              | The [command line](/developers/cli) and [MCP clients](/developers/mcp), which obtain it when you sign them in | It acts as you, limited to the scopes you agreed to (below).                                                                                                                                                                                                               |
| Session cookie     | The web app's cookie                   | The web app itself                                                                                            | A request that changes something with it must come from the web app's own origin.                                                                                                                                                                                          |

Members who may manage keys (owners and admins) create one with `POST /api/workspaces/{workspaceId}/api-keys` while signed in, and see the key only in that answer.

An OAuth token is limited to its scopes ([What each permission allows](/developers/agents#scopes)):

| Scope               | What it allows                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace:read`    | Reading.                                                                                                                                        |
| `workspace:write`   | What your role allows, except what puts posts out.                                                                                              |
| `workspace:publish` | Scheduling and publishing. Every endpoint that needs `post:schedule` needs `workspace:publish` from an OAuth token, and answers 403 without it. |
| `workspace:ads`     | Nothing alone: with `workspace:write` it manages ad accounts, and with `workspace:publish` it spends on [ads](/guides/engage/ads#access).       |

### Check who you are [#whoami]

With a session or an OAuth token, `GET /api/me` tells who you are, and lists your workspaces, with your role and permissions in each. An API key belongs to a workspace, not to a person, and gets 403 there.

Any credential, a key or a partner key included, asks `GET /api/credential` who it is and what it may do: an API key's name, workspace, permissions and expiry, a partner key's partner, scopes and permissions, never the key itself ([SDKs](/developers/sdks#credential)).

<CodeGroup>

```bash curl
curl https://api.example.com/api/credential \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```ts TypeScript
import { PealClient } from "peal-sdk";

const peal = new PealClient({ token: process.env.PEAL_API_KEY });

const credential = await peal.credential.get();
```

</CodeGroup>

## Workspaces [#workspaces]

A workspace's resources live under `/api/workspaces/{workspaceId}/`: `channels`, `posts`, `media`, `assistant`, `analytics`, `billing`, `usage`, `webhooks`, `activity` and `api-keys`. `DELETE /api/workspaces/{workspaceId}` deletes the workspace itself, with everything in it ([Workspaces and your account](/guides/workspace#delete-workspace)). Each endpoint's reference names the permission it needs, such as `post:schedule` or `channel:connect`.

| Status | Meaning                                                                        |
| ------ | ------------------------------------------------------------------------------ |
| 401    | No credentials, or credentials that no longer work.                            |
| 403    | The credentials work, but do not allow this request, or the account is banned. |
| 404    | No such resource, or a workspace the caller does not belong to.                |

The requests a script uses most:

| Request                                           | What it does                                                                                    | Shown in                                           |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `POST /api/workspaces/{workspaceId}/posts/send`   | Creates a post and sends it in one request, now or at an instant                                | [Posting from an AI agent](/developers/agents#api) |
| `POST /api/workspaces/{workspaceId}/media/import` | Has the server fetch an image or a video from a public HTTPS address into the workspace's media | [Posting from an AI agent](/developers/agents#api) |
| `POST …/posts/validate`                           | Checks a post without making it                                                                 | [Posting through the API](/developers/posting)     |
| `send?wait=30`, `GET …/posts/{postId}/outcome`    | Waits for the outcome of a post that goes out now                                               | [Posting through the API](/developers/posting)     |
| `POST …/posts/bulk`                               | Sends up to 50 posts in one request                                                             | [Posting through the API](/developers/posting)     |
| `POST …/posts/import`                             | Imports posts from a CSV file                                                                   | [Posting through the API](/developers/posting)     |
| `GET …/posts/search`                              | Lists posts with filters                                                                        | [Posting through the API](/developers/posting)     |

Sent with an `Idempotency-Key` header, a `send` request is safe to send again: within 24 hours, the same key with the same body answers the post the first request made, and another body answers 409 `IdempotencyKeyReused`. A post made in one call whose content already goes to one of its channels less than 23 hours from its time answers 409 `DuplicatePost`, unless it says `allowDuplicate: true`.

### Errors and plan limits [#workspace-errors]

Errors answer with a JSON body in one format: a stable `code`, such as `post_content_invalid` or `connect_failed`, the same name as `_tag` (`PostContentInvalid`) for clients generated from the contract, a `message` for people, the `requestId`, and the details the reference lists. [Errors](/developers/conventions/errors#errors) describes it, and [Error codes](/developers/conventions/errors#error-codes) lists every code. Some answers come from one feature:

| Answer                 | When                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 429                    | The writing assistant's endpoints, once the workspace has used its requests for the day.                                                                                                                                                                                                                                            |
| 503                    | The writing assistant's endpoints, when the instance has no AI provider.                                                                                                                                                                                                                                                            |
| 502                    | The writing assistant's endpoints, when the provider gave no answer the assistant could use.                                                                                                                                                                                                                                        |
| 402 `PlanLimitReached` | On an instance that bills, connecting a channel, scheduling a post or starting an upload the workspace's plan has no room for. It names the `limit` (`channels`, `members`, `scheduledPosts`, `assistantRequests` or `mediaStorage`, in bytes) and what the plan `allowed` ([Plans and billing](/guides/workspace/billing#limits)). |

`GET /api/workspaces/:workspaceId/billing` shows the plan, its allowances and the workspace's usage, and `GET /api/workspaces/:workspaceId/usage` what it used day by day, in UTC days ([Usage](/guides/workspace/billing#usage)).

## Partner accounts [#partner]

A partner account owns one workspace for each customer of a product built on Peal. [Embedding Peal](/developers/embedding) walks through the whole flow.

- `/api/partner` answers its partner keys only: `GET /api/partner` reads the account and what it holds, and `/api/partner/workspaces` creates, lists, finds by `externalId`, changes and deletes its workspaces.
- A partner key then calls `/api/workspaces/{workspaceId}/…` for a workspace its account owns, and gets 404 for any other.
- `POST /api/workspaces/{workspaceId}/connect-links` answers a hosted, single-use link where the owner of a social account connects it without a Peal account.

## What a channel takes [#capabilities]

Each platform has its own rules: how long a post may be and how its length is counted, which images and videos it takes, and options of its own, such as a YouTube video's title. Peal answers the rules it checks when a post is scheduled, so you do not have to learn them from each platform's documentation:

- `GET /api/workspaces/{workspaceId}/platforms/capabilities` describes every platform, whether or not the workspace has a channel there.
- `GET /api/workspaces/{workspaceId}/channels/{channelId}/capabilities` describes one channel: its platform's capabilities, and under `account` what the account itself narrows, read from the platform at that moment. A TikTok account offers only some audiences, may have turned comments, Duets or Stitches off, and has a longest video. When the platform cannot be asked, `account` is `unread` with the reason, and the platform's capabilities are answered alone.

Both need `channel:read`, so an API key or an application you let read only may call them.

<CodeGroup>

```bash curl
curl https://api.example.com/api/workspaces/$WORKSPACE_ID/channels/$CHANNEL_ID/capabilities \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```ts TypeScript
const capabilities = await peal.capabilities.channel({
  workspaceId,
  channelId,
});
```

```bash CLI
peal channels capabilities <channel-id> --json
```

</CodeGroup>

A description holds:

| Field       | What it says                                                                                                                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`   | The version of the description, 1 today. It goes up when a field changes meaning or leaves; fields, platforms, lookups and restrictions are added under the same version, so skip what you do not know.                                                                                                                         |
| `text`      | Every limit on the text (`limits`: all apply, each `maximum` counted in its `unit`, the last one being Peal's own), the most hashtags, mentions and different links, and the characters refused. `peal-contract/post-text` counts each unit as the server does.                                                                 |
| `media`     | Whether a post needs an image or a video, how many it takes, whether images and videos go together, alt text, and for each file type its size, duration, pixels, sides and aspect ratio (width divided by height). `formats` is null where Peal knows none of the rules yet.                                                    |
| `options`   | The fields a draft's `options` take on that platform: each one's `type`, the `values` of a choice, whether it is `required` to schedule, its `maxLength`, what the platform does when it is left out (`ifLeftOut`), and the `lookup` that answers its values; then `constraints`, the rules between two fields.                 |
| `lookups`   | What the platform tells about an account, for the options that refer to it ([Lookups](#lookups)).                                                                                                                                                                                                                               |
| `analytics` | Whether Peal reads the counts of each post published there (`perPost`), which ones (`postCounts`: likes, reposts, replies, and quotes, impressions, clicks, reach and saves where the platform gives them), and which numbers of the account it reads day by day (`accountNumbers`: followers, following, posts, views, reach). |

A limit that is null is one Peal does not check: the platform may still apply it, and refuse the post when it goes out.

In `analytics`, a number left out is one the platform does not give: it is never zero. A platform's description says so when any of its channels has counts, and lists every lookup it has; a channel's says it for that channel. On LinkedIn, a company page has counts and the lookup of pages to mention, and a profile has neither; on X, only where the server's operator turned its reads on.

### Lookups [#lookups]

Some options take values only the account knows. A lookup asks the platform for them, with the channel's token:

- `GET /api/workspaces/{workspaceId}/channels/{channelId}/lookups` lists the lookups a channel has, with the input each takes and the options it fills.
- `POST /api/workspaces/{workspaceId}/channels/{channelId}/lookups/{name}` runs one, and answers a page of `items` tagged by the lookup's name (`_tag`). When `nextCursor` is not null, send it back as `cursor` for the next page.

<CodeGroup>

```bash curl
curl -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/channels/$CHANNEL_ID/lookups/youtubeVideoCategories \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "regionCode": "FR" }'
```

```ts TypeScript
const categories = await peal.lookups.run({
  workspaceId,
  channelId,
  name: "youtubeVideoCategories",
  regionCode: "FR",
});
```

```bash CLI
peal channels lookup <channel-id> youtubeVideoCategories --region FR
```

</CodeGroup>

| Lookup                   | Platform                         | Input                                                              | Items                                                                                                             |
| ------------------------ | -------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `youtubeVideoCategories` | YouTube                          | `regionCode` (two capital letters, `US` when left out), `language` | The categories a video can be filed under in that country: `id`, which the `categoryId` option takes, and `title` |
| `youtubePlaylists`       | YouTube                          | `limit` (25 when left out, 50 at most), `cursor`                   | The channel's playlists: `id`, `title` and `privacy`                                                              |
| `tiktokCreator`          | TikTok                           | none                                                               | One item: the creator's posting settings, whose `privacyLevels` the `privacyLevel` option takes                   |
| `linkedinOrganizations`  | LinkedIn (company page channels) | `vanityName` (required), the name in the page's address            | The page of that name, if any: `name` and `urn`, which an entry of the `mentions` option takes, and `vanityName`  |
| `pinterestBoards`        | Pinterest                        | `limit` (25 when left out, 50 at most), `cursor`                   | The account's boards: `id`, which the `boardId` option takes, `name` and `privacy`                                |
| `pinterestBoardSections` | Pinterest                        | `boardId` (required), `limit`, `cursor`                            | The sections of that board: `id`, which the `boardSectionId` option takes, and `name`                             |

A lookup changes nothing, and needs `channel:read`. Each run is a request to the platform, counted against what it allows this instance, so run one when a post needs it rather than on a timer. A page may come empty and still name a next one.

<Accordion>
  <AccordionItem title="How Peal paces lookups">
    - A channel's lookups reach its platform 30 times a minute at most, past
    which a run answers 429 `PlatformRateLimited` with `retryAfterSeconds`. -
    The same lookup with the same input on the same channel is answered from its
    last answer for a minute, without asking the platform again. - An instance's
    lookups reach each platform a set number of times a day (UTC) for all its
    workspaces together, so that lookups never spend what publishing needs. Past
    it, a lookup answers 429 `PlatformRateLimited` with `retryAfterSeconds`
    until the next day. - What a platform says of itself rather than of an
    account, as YouTube's video categories for a region and a language, is kept
    for a day.
  </AccordionItem>
  <AccordionItem title="Errors a lookup answers">
    | Status | Error | When | | ------ | --------------------- |
    ---------------------------------------------------------------------------------------------------------
    | | 404 | `LookupNotFound` | A name the channel does not have, as its
    platform or its kind of LinkedIn channel lacks it. | | 422 |
    `LookupInputInvalid` | An input the lookup does not take, or one without a
    field it needs. | | 409 | `ChannelCannotPost` | The channel is turned off or
    must be reconnected. | | 502 | `PlatformUnreachable` | The platform does not
    answer. | | 429 | `PlatformRateLimited` | The platform asks to slow down,
    with `retryAfterSeconds` when it said how long; or Peal's pacing, above. |
  </AccordionItem>
</Accordion>

## Webhooks [#webhooks]

Peal can call your server when something happens in a workspace, so you need not ask the API again and again: a post went out or failed, a channel must be reconnected, a file is ready. Members who may manage webhooks (owners and admins), and API keys given that permission, add endpoints under `/api/workspaces/{workspaceId}/webhooks`. [Webhooks](/developers/webhooks) lists every event with its schema, and tells how deliveries are signed, retried and verified.

## The activity log [#activity]

`GET /api/workspaces/{workspaceId}/activity` lists the requests that asked to change something in the workspace: who asked, through which key or application, which operation, and how it was answered. It needs `activity:read`, which owners hold ([The activity log](/guides/workspace#activity)).

## Your account [#me]

What belongs to you rather than to a workspace lives under `/api/me`:

| Request                            | What it holds                                             |
| ---------------------------------- | --------------------------------------------------------- |
| `GET /api/me`                      | Who you are                                               |
| `/api/me/notices`                  | Your [notifications](/guides/workspace/notifications#api) |
| `/api/me/notification-preferences` | Which notifications are emailed                           |
| `GET /api/me/overview`             | What needs attention in each of your workspaces           |
| `GET /api/me/agenda`               | What goes out across them                                 |
| `GET /api/me/report`               | How it did                                                |

The last three answer as far as your role in each workspace may read ([Across your workspaces](/guides/workspace#across-workspaces)). These endpoints answer 403 to API keys, which belong to a workspace, and to OAuth tokens bound to one workspace, such as an MCP client's.

A copy of your data (`GET /api/me/export`), deleting your account (`DELETE /api/me`) and your connected applications (`/api/me/connected-apps`) answer only your own session in the web app: API keys, OAuth tokens and staff acting as you get 403 ([Workspaces and your account](/guides/workspace#api)).

## OpenAPI document [#openapi]

The OpenAPI 3.1 document of the API is public at `/api/openapi.json`, at the address you open Peal at, such as `https://api.example.com/api/openapi.json`. Use it to generate a client in another language or to import the API into an HTTP tool. The server also answers it at `/openapi.json` on its own address, such as `http://localhost:3000/openapi.json` for a server running from source, which the web app does not forward.

The API catalogue at `/.well-known/api-catalog` (RFC 9727) points programs to that document, to the [MCP endpoint](/developers/mcp) and to where each gets a credential ([Discovery](/developers/conventions/discovery#discovery)). `GET /api/changelog` lists what each release of the API added ([Changelog](/developers/conventions/versioning#changelog)).
