A workspace that posts every day repeats itself: the same channels, the same sign-off, the same campaign names. Peal keeps those for it. Tags file posts, signatures end them, channel sets start them, and a channel's default options fill in what it always takes. All of them belong to the workspace: every member reads them, and those who may edit posts change them.

## Who can do what [#roles]

| Role        | Tags, signatures, channel sets and default options |
| ----------- | -------------------------------------------------- |
| Owner       | Read and change                                    |
| Admin       | Read and change                                    |
| Editor      | Read and change                                    |
| Contributor | Read and change                                    |
| Viewer      | Read                                               |

Changing them takes the right to edit posts. Through the API that is `post:update`, and reading them `post:read`.

## Tags [#tags]

A tag is a name and a colour: a campaign, a client, a theme. A post has up to 10 tags, and a workspace keeps up to 100.

In a workspace's **Settings**, choose **Tags** to add one: give it a name of 40 characters at most, which no other tag of the workspace has whatever its case, and choose its colour among the nine of the palette. Rename it, give it another colour or delete it there. Deleting a tag takes it off its posts, which keep everything else.

In the composer, under **Tags**, tick the tags of the post, or add a new one. A post that went out is tagged on its page: tags say nothing to the platforms, so they change whatever the post's status.

Tags show on the calendar, as a dot of each tag's colour on the post, and in the list of drafts. Above the calendar, **Tags** shows only the posts filed under one of the tags you tick, and **Channels** only those that go to one of the channels you tick; with both, a post must match both. The calendar says how many posts the filters hide, and **Clear filters** shows them all again.

## Signatures [#signatures]

A signature is a block of text a workspace ends its posts with: a sign-off, a disclosure, a set of hashtags. A workspace keeps up to 50, of 2,000 characters at most each.

In **Settings**, choose **Signatures** to add one. Give it a name, its text, and say what it is for: the whole workspace, one platform, or one channel.

- **In the composer**, **Signature** lists the workspace's signatures. Choosing one puts it under the text for all channels, or under one channel's own text, after a blank line.
- **By default**: tick **Add to new posts by default**. A new post then shows **Add the default signature when the post is saved**, ticked: when you save it, the workspace's default signature goes under its text, and the composer shows the text as saved. A platform's or a channel's own default replaces the workspace's there: the post gets a text of its own on that channel, signed with it. Untick the box for a post that should go without. There is one default for the workspace, one per platform and one per channel.

Once added, a signature is text of the post like the rest:

- it counts against each platform's limit when the post is scheduled, so a post that fit without it may be refused with it;
- it is never added under a text that already ends with it, so saving twice, or adding it by hand to a post that has it, adds nothing;
- it goes under the last part of a post in several parts (a [thread](/scheduling#threads)), the parts before it staying as they are;
- changing or deleting the signature later leaves the posts that hold it as they are.

Posts made through the API, MCP or the command line take a signature only when they ask for one: nothing is added to a text unasked.

## Channel sets [#sets]

A channel set is a selection of the workspace's channels kept under a name, such as "Launch" or "Client A", with the [options](/scheduling#options) posts take on some of them. A set holds up to 50 channels, and a workspace keeps up to 50 sets.

In the composer, **Use a channel set** offers the workspace's sets when a post starts: choosing one ticks its channels and fills in the options it keeps. Tick the channels of a post, fill in their options, then choose **Save selection as a set** to keep them. **Settings**, **Channel sets** lists the sets, and lets you rename one, change its channels or delete it.

A set keeps the channels it was given. When one of them is disconnected later:

- the set still lists it, marked as no longer connected;
- a post that uses the set goes to the set's other channels, and Peal says which channel was left out, in the composer and in the API's answer (`warnings`): never silently;
- a post whose set has no connected channel left, and that names no other channel, is refused;
- saving the set again takes the disconnected channel out of it.

## Default options for a channel [#defaults]

Some channels always take the same [options](/scheduling#options): the same Pinterest board, the same YouTube audience. A channel's default options are what a new post takes on that channel when it gives none there.

Defaults are a starting point, not a way round a platform's rules: they may be unfinished, and a post that takes them is checked when it is scheduled exactly as a post that wrote them itself. Options are taken in this order: the post's own, then a channel set's, then the channel's defaults. Only a new post takes them: a draft you change keeps what you give it.

Set them through the API, MCP or the command line:

```sh
peal channels defaults set 0190f3a0-0000-7000-8000-00000000c004 \
  --options '{"platform":"youtube","privacy":"unlisted"}'
```

## Duplicate a post [#duplicate]

On a post's page, or from its entry on the calendar, **Duplicate** makes a new draft that says what the post says: its text, its media, its channels with their own text and options, and its tags. The copy has no time, and you are its author. What the workspace no longer has is left out: a channel disconnected since, media deleted since.

To send the same post at several times, duplicate it and schedule each copy.

## Through the API [#api]

Everything above is in the [HTTP API](/api-overview), under `/api/workspaces/{workspaceId}`, in the [MCP tools](/mcp#tools) and on the [command line](/cli).

| What                    | Endpoints                                                                           |
| ----------------------- | ----------------------------------------------------------------------------------- |
| Tags                    | `GET`, `POST …/tags`, `PATCH`, `DELETE …/tags/{tagId}`, `PUT …/posts/{postId}/tags` |
| Signatures              | `GET`, `POST …/signatures`, `PUT`, `DELETE …/signatures/{signatureId}`              |
| Channel sets            | `GET`, `POST …/channel-sets`, `PUT`, `DELETE …/channel-sets/{channelSetId}`         |
| Default options         | `GET`, `PUT`, `DELETE …/channels/{channelId}/default-options`                       |
| Duplicate               | `POST …/posts/{postId}/duplicate`                                                   |
| Posts filed under a tag | `GET …/posts/search?tagId=…`                                                        |

A post names what it takes when it is made. This one goes to the channels of the set "Launch", takes each channel's default signature, and is filed under a tag:

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/posts/send" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "channelIds": [],
    "channelSets": ["Launch"],
    "content": { "text": "We are live.", "media": [], "overrides": [] },
    "defaultSignatures": true,
    "tagIds": ["0190f3a0-0000-7000-8000-00000000a001"],
    "when": { "_tag": "now" }
  }'
```

- `channelSets` names sets by id or by name, whatever the case; `channelIds` may then be empty. The post goes to the sets' connected channels and to the channels it lists.
- `defaultSignatures` puts each channel's default signature under its text, and `signatureId` one signature on every channel.
- `tagIds` files the post. Updating a draft without `tagIds` keeps its tags.

When a set lists a channel that is no longer connected, the post is made without it and the answer says so:

```json
{
  "id": "0190f3a0-0000-7000-8000-00000000d010",
  "status": "scheduled",
  "warnings": [
    {
      "_tag": "channelsDropped",
      "channelSetId": "0190f3a0-0000-7000-8000-00000000b001",
      "channelSetName": "Launch",
      "channelIds": ["0190f3a0-0000-7000-8000-00000000c001"]
    }
  ]
}
```

`POST …/posts/validate` takes the same fields and answers the same `warnings`, so a script knows before it sends. In a [CSV import](/posting-api#import), the `channels` column takes a set's id, or its name when the name has no space, comma or semicolon.

A [partner key](/embedding) uses the sets, signatures and tags of each workspace its partner owns, as that workspace's own key does.
