Peal reaches every outside service through a port with a self-hostable default. A self-hosted instance runs two programs of its own, the server and the web app, and needs Postgres, an S3-compatible object store and a way to send email. Everything else is optional and stays off until you configure it.

<Callout type="warning" title="Before the first release">
  Peal has not been released yet, and there are no published images to run:
  build them from the repository, as [With Docker Compose and Caddy](#compose)
  shows. This page describes the self-hosting model the code follows, and every
  value shown is an example.
</Callout>

## Services [#services]

| Service        | Needed   | What Peal uses it for                                                                                    | Options                                                                                |
| -------------- | -------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Postgres       | Yes      | All data, and the durable jobs that publish posts and refresh platform tokens. Peal needs no Redis.      | Any Postgres server                                                                    |
| Object storage | Yes      | Uploaded media                                                                                           | Any S3-compatible API                                                                  |
| Email          | Yes      | Confirming email addresses, resetting passwords, invitations, and notifications about posts and channels | Resend, or any SMTP server                                                             |
| Billing        | Optional | Plans and subscriptions                                                                                  | Stripe. Without a key, billing is off and no plan limits apply.                        |
| Captcha        | Optional | Bot protection on sign-up and password resets                                                            | Cloudflare Turnstile. Without its keys, the captcha is off.                            |
| AI             | Optional | The writing assistant in the composer                                                                    | Anthropic's API, or any OpenAI-compatible endpoint. Without one, the assistant is off. |
| Telemetry      | Optional | Logs, metrics and traces                                                                                 | Any OpenTelemetry (OTLP) collector. Nothing is exported unless an endpoint is set.     |

Peal's own deployment stores media on Cloudflare R2, and its development stack runs SeaweedFS for storage and Mailpit for email. A self-hosted instance can use any of these, or any other store and mail server that speaks the same protocols.

## What to run [#run]

- **The server** (`peal-server`): the HTTP API under `/api`, sign-in under `/api/auth`, the MCP endpoint at `/api/mcp`, and the jobs that publish posts, email notifications and refresh tokens. Its image listens on port 3000 and runs as an unprivileged user.
- **The web app** (`peal-web`): every page, on Node. It forwards `/api/*` and the OAuth discovery documents (`/.well-known/oauth-*`) to the server at `PEAL_API_URL`, so people, the command line and MCP clients all use one address: `PUBLIC_URL`.

Run one server process per instance: MCP clients on older protocol revisions keep their sessions in its memory. Each process that runs needs its own `HOSTNAME`.

In production (`NODE_ENV=production`, which the server's image sets), the server refuses to start without these, and its error names the variable missing:

| Variable                                                                                   | What it is                                                          |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| `DATABASE_URL`                                                                             | The Postgres database                                               |
| `PUBLIC_URL`                                                                               | The address people open Peal at, such as `https://peal.example.com` |
| `BETTER_AUTH_SECRET`                                                                       | The secret that signs sessions: `openssl rand -base64 32`           |
| `AUTH_IP_HEADERS`                                                                          | The header your edge puts the client's address in                   |
| `MAIL_FROM`, and `SMTP_URL` or `RESEND_API_KEY`                                            | Who emails come from, and how they leave                            |
| `PEAL_S3_ENDPOINT`, `PEAL_S3_BUCKET`, `PEAL_S3_ACCESS_KEY_ID`, `PEAL_S3_SECRET_ACCESS_KEY` | The media store                                                     |

The web app needs `PEAL_API_URL`. To connect channels, the server also needs `PEAL_TOKEN_KEYS`. [Environment variables](/environment-variables) lists every setting, with its default.

## With Docker Compose and Caddy [#compose]

The repository's `packages/peal-docker` folder holds a stack you can run as it is. `compose.production.yaml` runs Postgres, the server, the web app and a telemetry stack (an OpenTelemetry collector, Loki, Tempo, Prometheus and Grafana), each restarted when it stops, with every port on `127.0.0.1`. `compose.self-host.yaml` adds Caddy in front of them: it gets a certificate from Let's Encrypt, and it is the only service reachable from outside, on ports 80 and 443.

1. Point your domain at the server in DNS, and open ports 80 and 443.
2. Copy `self-host.env.example` out of the repository, such as to `/srv/peal/peal.env`, let only root read it, and fill it in: the domain, the secrets it says how to generate, email and the media store.
3. From `packages/peal-docker`, build the images, then start the stack:

```sh
docker compose --project-name peal --file compose.production.yaml \
  --file compose.self-host.yaml --env-file /srv/peal/peal.env build
docker compose --project-name peal --file compose.production.yaml \
  --file compose.self-host.yaml --env-file /srv/peal/peal.env up --detach --wait
```

The server applies its migrations as it starts, so an upgrade is a newer checkout and the same two commands. Compose gives the server its 75 seconds to stop.

Caddy (`self-host/Caddyfile`) sends `/api/*` and `/.well-known/oauth-*` to the server and everything else to the web app, and waits 150 seconds for an answer, longer than the writing assistant and the web app's forwarding wait. Set `AUTH_IP_HEADERS=x-forwarded-for`, as the example file does.

Grafana listens on `127.0.0.1:13000` only: reach it through an SSH tunnel, such as `ssh -L 13000:127.0.0.1:13000 you@your-server`, and sign in as `admin` with `GRAFANA_ADMIN_PASSWORD`. Its alert rules come provisioned, and notify no one until you add a contact point.

To back the database up, set `PEAL_POSTGRES_ARCHIVE_MODE=on` and the `PGBACKREST_REPO1_*` settings the example file lists. Postgres then archives its write-ahead log to that bucket with pgBackRest, which the stack's Postgres image ships. Create the backup repository once with `docker compose … exec --user postgres postgres pgbackrest stanza-create`, then take backups on a schedule with `… pgbackrest backup --type=full`. Peal's own servers do so with the Ansible in `packages/peal-infra`, whose README and restore runbook show every command. [Environment variables](/environment-variables#compose) lists the stack's settings.

## Watching it from outside [#uptime]

Grafana's alerts come from the server they watch: when that server, its network or Grafana stops, they stop too. Watch the instance from another machine as well, one that shares nothing with it, and alerts by a way of its own:

- Check what people reach, through your edge: `GET /api/ready`, which answers `204 No Content` when the server and its database do, a page of the web app such as `/sign-in`, which answers `200`, and how long the certificate has left. Count a redirect as a failure, so a sign-in page in front of the instance never passes for it.
- Have Grafana show that its alerting works. With `PEAL_GRAFANA_HEARTBEAT=./config/production/grafana/alerting/heartbeat.yaml`, `PEAL_HEARTBEAT_URL` and `PEAL_HEARTBEAT_TOKEN` set, a rule that always fires posts to that address every 5 minutes or so, with the token as a bearer token. When the posts stop, Grafana, Prometheus or the way out is down, and the other alerts may not reach you either: the checker says so. With [Gatus](https://github.com/TwiN/gatus), make it an external endpoint with a heartbeat interval of 15 minutes, and set `PEAL_HEARTBEAT_URL` to its push address, `https://<gatus>/api/v1/endpoints/<group>_<name>/external?success=true`.

Peal's own servers are watched this way: [Deployment](/deployment#uptime) describes the uptime server, whose Ansible and Gatus configuration are in `packages/peal-infra`.

## In front of Peal [#reverse-proxy]

Run a reverse proxy that terminates TLS, such as Caddy, in front of the web app, and expose only the proxy. Send every request to the web app, which forwards the server's paths, or send `/api/*` and `/.well-known/oauth-*` straight to the server and everything else to the web app.

Sign-in is rate limited by the client's address, which the server reads from the header `AUTH_IP_HEADERS` names. Name only a header your edge sets and replaces whatever the client sent:

- behind Cloudflare, `cf-connecting-ip`;
- behind Caddy, which replaces `X-Forwarded-For` unless told to trust the proxies before it, `x-forwarded-for`;
- behind proxies that append to `X-Forwarded-For`, `x-forwarded-for`, with their addresses in `AUTH_TRUSTED_PROXIES`, so the client's address is read from the right, past them.

The web app passes these headers on as they come, so with no proxy in front of it there is no address to trust, and rate limits cannot tell clients apart.

Let requests last at least 90 seconds through everything between browsers and the server, a tunnel included: the writing assistant waits that long for its AI provider. The web app's own forwarding of `/api/*` waits up to 120 seconds.

The server answers two probes:

- `GET /api/health` answers `204 No Content` as soon as the server is up, whatever the state of its database, which suits a container health check. The server's image checks it.
- `GET /api/ready` answers `204 No Content` when the database answers as well, and `503 Service Unavailable` with a `DatabaseUnavailable` error when it does not, so a load balancer can hold traffic back until then.

## Database [#database]

At startup, the server applies the database migrations it has not applied yet, one server at a time, and only listens once they are done. Each part of Peal keeps its tables in a Postgres schema of its own (`assistant`, `auth`, `channels`, `legal`, `media`, `notifications`, `publishing`); the job runner's tables (`cluster_*`) are in `public`.

The server runs its durable jobs from the same database, and holds them with session advisory locks for as long as it runs. Connect it to Postgres directly, or through a pooler in session mode: a pooler in transaction mode gives each statement another connection, which loses those locks. Each server process opens up to 10 connections, and up to 5 more for sign-in (`AUTH_DB_POOL_MAX`).

A daily cleanup deletes the records of jobs that finished more than 30 days ago (`PEAL_CLUSTER_RETENTION`). Jobs still waiting are always kept.

## Stopping [#stopping]

When it stops, the server waits up to 60 seconds for the calls to the platforms in flight to answer. Give it at least 75 seconds before it is killed, with `docker stop --time 75` or `stop_grace_period: 75s` in Compose. A call cut short is checked when the server starts again: on Bluesky by reading the post back, on Mastodon by sending it again under the same key, which Mastodon keeps for an hour. When that cannot settle it, the post is marked to check, and someone has to look on the platform.

## Email [#email]

Set `MAIL_FROM` to the sender, as `Peal <noreply@example.com>` or an address your mail service may send from, and one way to send:

- `RESEND_API_KEY`, to send through Resend's API;
- otherwise `SMTP_URL`, such as `smtp://user:password@mail.example.com:587`, or `smtps://…:465` for TLS from the first byte.

Peal sends the email that confirms an address, password resets, invitations to a workspace, and [notifications](/notifications) about posts and channels, each in the reader's language. Members choose which notifications also reach them by email. When the mail service turns an email away for now, an account email is tried again for a few seconds, then dropped, as people can ask for another; a notification's email is tried again for about five hours. With `AUTH_REQUIRE_EMAIL_VERIFICATION=false`, people can sign in before they confirm their address.

## Media storage [#media-storage]

To keep media in the EU on Cloudflare R2, create the bucket in R2's EU jurisdiction (in the dashboard, or `wrangler r2 bucket create <name> --jurisdiction eu`), which cannot be changed later, and reach it at the `.eu.` endpoint, `https://<account>.eu.r2.cloudflarestorage.com`, in `PEAL_S3_ENDPOINT`. Wrangler's other bucket commands need `--jurisdiction eu` too. The same goes for a backup bucket, whose endpoint is a host without a scheme.

Browsers send media straight to the bucket, with requests the server signs, so the bucket must let the web app's origin send them: a CORS rule that allows `PUT` from that origin with the `Content-Type` and `If-None-Match` headers. With the server's variables set, and `PUBLIC_URL` and `TRUSTED_ORIGINS` naming the web app's origins, this command puts the rule on the bucket, keeping its other rules, and prints the same policy for Cloudflare R2's dashboard (R2 › the bucket › Settings › CORS policy):

```sh
bun nx run peal-server:media-cors
```

Running it again changes nothing. Its access key must be allowed to change the bucket's settings; the server's own key needs only to read and write objects.

Large videos go up in parts. An upload left unfinished keeps its parts in the store, so add a lifecycle rule that aborts incomplete multipart uploads after a day, where your store supports one.

Once a file is stored, the server reads it: an image's dimensions with sharp, a video's dimensions, duration and codec with ffprobe, which the server's image ships. A video uploaded to a server without ffprobe stays uploaded, marked as unread, until it is completed again on a server that has it.

Pages show media through short-lived signed links. If the bucket is also served publicly, as through an R2 custom domain, set `PEAL_MEDIA_PUBLIC_BASE_URL` to that address, and links to media use it instead.

## Channels [#channels]

The server encrypts the tokens of connected accounts, and the signing secrets of [webhooks](/webhooks#self-hosting), with the keys in `PEAL_TOKEN_KEYS`. Without it, the server starts, and connecting an account or adding a webhook endpoint fails. Create a key with:

```sh
echo "k1:$(openssl rand -base64 32)"
```

The value lists `keyId:key` entries separated by commas, such as `k2:<key>,k1:<key>`. The first key encrypts and every listed key decrypts: to rotate, put a new key first and keep the old ones. A malformed value stops the server at startup. Keep the keys secret, and keep a copy: without them, every channel must be reconnected.

The server reaches the platforms itself, over HTTPS, so it needs to reach the internet: to connect accounts, and to publish, on each account's Mastodon server, on the Bluesky server that holds each account, through Bluesky's video service, `https://video.bsky.app`, for videos, on LinkedIn (`www.linkedin.com`, `api.linkedin.com` and the upload addresses LinkedIn gives), on X (`api.x.com`), on TikTok (`open.tiktokapis.com`), on Pinterest (`api.pinterest.com` and the upload addresses Pinterest gives) and on Meta's APIs. It only calls servers on public addresses, on the default HTTPS port, which keeps people from pointing it at your private network. The platforms send people back to `PUBLIC_URL/connect/<platform>/callback`, through their browser: they never call the server themselves, apart from Bluesky reading Peal's client description, and Meta's data deletion requests, below.

To publish an image or a video, the server reads it from the media store, whole, into memory, then uploads it: a Bluesky video can take up to 300 MB. LinkedIn and X take videos in parts of 4 MiB, and TikTok in parts of 10 MB, so the server holds one part at a time; a Pinterest video is sent as it is read, and never held whole. Give the server the memory for the largest files your members post.

### Addresses to register [#platform-addresses]

Each platform's app is given addresses on your server: where the platform sends people back after they sign in and, for Meta, where its servers call yours. One command prints them all for your `PUBLIC_URL`, each beside the setting it goes in, from the paths the server itself answers and sends. From the repository:

```sh
PUBLIC_URL=https://peal.example.com bun nx run peal-server:platform-addresses
```

Or on a running server, which answers for its own `PUBLIC_URL`, with the stack's files and settings as in [With Docker Compose and Caddy](#compose):

```sh
docker compose --project-name peal --file compose.production.yaml \
  --file compose.self-host.yaml --env-file /srv/peal/peal.env \
  exec server bun packages/peal-server/scripts/platform-addresses.ts
```

Register what it prints, copied, rather than addresses written by hand: a platform refuses a sign-in whose redirect address differs from the one registered by a single character, a trailing slash included. Run it again after changing `PUBLIC_URL`, and after an upgrade that adds a platform. With `--json`, it prints the same list for a program to read.

The addresses it marks as called by the platform's servers, Meta's two callbacks and Bluesky's client documents, must answer the internet with no sign-in in front of them: let them through any login page or allow list you put before the server. The others are opened by people's browsers.

### Bluesky [#bluesky]

A production server connects Bluesky accounts only with keys of its own, which identify it to Bluesky. `PUBLIC_URL` must be HTTPS, without a port. Create a key, from the repository:

```sh
bun nx run peal-server:bluesky-key
```

Put the line it prints in `BLUESKY_CLIENT_KEYS`. Entries are separated by commas: to rotate, put a new key first, and keep the old ones until the sessions they signed for have been refreshed. Nothing is registered with Bluesky: its servers read Peal's client description, and its public keys beside it, at the addresses [the command](#platform-addresses) prints for Bluesky.

Without keys, a server running from source on `localhost` uses Bluesky's development client, whose sessions last two weeks, and any other server cannot connect Bluesky.

### LinkedIn [#linkedin]

A server connects LinkedIn members once you register an app for it on LinkedIn's developer portal, which asks for a LinkedIn page to own it:

1. Add the **Sign In with LinkedIn using OpenID Connect** and **Share on LinkedIn** products. Both are granted at once, without review.
2. Under **Auth**, add the address [the command](#platform-addresses) prints for LinkedIn as an authorized redirect URL.
3. Put the app's client id in `LINKEDIN_CLIENT_ID` and its primary client secret in `LINKEDIN_CLIENT_SECRET`.

These apps get no refresh token: members reconnect their channel every 60 days, and are told a week before. Peal calls LinkedIn's API in the version `LINKEDIN_API_VERSION` names, a recent one unless set; LinkedIn retires each version a year after its release, and a retired one fails every post.

### LinkedIn company pages [#linkedin-pages]

Posting to company pages takes LinkedIn's **Community Management API**, which LinkedIn reviews, and grants only to an app that has no other product: it cannot be added to the app above. A server that has the first app alone keeps connecting profiles, unchanged.

1. Create a second app on LinkedIn's developer portal, for the same LinkedIn page, with no product on it. LinkedIn asks that a super admin of that page verify the app.
2. Request the **Community Management API** on it. LinkedIn grants it to registered legal organizations, for commercial uses, and checks a business email address, the organization, and its website; a personal email address does not pass. Its terms keep what the API serves for your own organization's clients: read them with the use you make of your server in mind.
3. LinkedIn first grants the **Development tier**, for building: 500 calls a day for the app and 100 for each member, and no batch read, which Peal does not use. Ask for the **Standard tier** before real use: LinkedIn then asks for a screen recording of each use, here connecting a page, posting to it, and reading its posts' statistics, and for your privacy policy.
4. Under **Auth**, add the same redirect URL, `PUBLIC_URL/connect/linkedin/callback`.
5. Put the app's client id in `LINKEDIN_PAGES_CLIENT_ID` and its primary client secret in `LINKEDIN_PAGES_CLIENT_SECRET`.

Peal asks members for `w_organization_social`, `r_organization_social` and `rw_organization_admin`, lists the pages each one administers, and posts to those they choose with their own access, which lasts 60 days. LinkedIn gives refresh tokens to approved partners only: when your app gets them, Peal renews a page's access by itself for a year after the sign-in; otherwise the page is reconnected every 60 days, like a profile. Pages are the only LinkedIn channels whose posts Peal reads counts on, and finds after a lost answer.

### X [#x]

A server connects X accounts once you register an app for it in X's developer console:

1. Under the app's user authentication settings, turn on OAuth 2.0, as a **Web App, Automated App or Bot**, with **Read and write** permissions.
2. Add the address [the command](#platform-addresses) prints for X as a callback URI, exactly. X refuses `localhost`: in development, use `http://127.0.0.1` and its port.
3. Put the OAuth 2.0 client id in `X_CLIENT_ID` and its client secret in `X_CLIENT_SECRET`.

X bills each request of the API to the app, from credits bought ahead ([pricing](https://docs.x.com/x-api/getting-started/pricing)), and a post with a link costs about 13 times one without. Buy credits and set a spending limit in X's console. Once the credits run out (X answers `402`) or the limit is reached (`usage-capped`), X refuses every post of the app until you add credits or raise the limit: the posts are not at fault, so Peal keeps them waiting and tries each again every half hour: they go out once you have paid. A post still refused a day after its time fails with the reason "the platform refused this server's app until its operator pays for it". Peal logs an error at the first refusal, then once an hour while it lasts, whatever the number of posts waiting (`event.name` `peal.app_refused`), which the alert "A platform refuses the server's app until it is paid for" reports, and counts every refused attempt in the metric `peal.publishing.app_refusals`.

Peal counts each workspace's posts on X, and how many held a link, by calendar month (UTC), in `billing.metered_posts`, so you can see who spends what; plans do not limit them yet. The counts go with the workspace's export and its deletion.

X's access lasts two hours. Peal renews it when it posts, and renews that of an account that has not posted for 30 days, so X keeps it connected without a rotation every two hours.

For LinkedIn as for X, one of the two settings without the other stops the server at startup; without both, **Channels** does not offer the platform.

### TikTok [#tiktok]

A server connects TikTok creators once you register an app for it on TikTok for Developers:

1. Add the **Login Kit** product, with the address [the command](#platform-addresses) prints for TikTok as its redirect URI for the web. TikTok takes HTTPS redirect URIs only: in development, use an HTTPS tunnel.
2. Add the **Content Posting API**, with **Direct Post** on, and the **Display API**, for analytics. Add the scopes `user.info.basic`, `user.info.profile`, `video.publish` and `video.list`.
3. Put the app's client key in `TIKTOK_CLIENT_KEY` and its client secret in `TIKTOK_CLIENT_SECRET`.

Until TikTok audits the app, it takes up to five creators a day, whose accounts must be private, and only posts they alone see: other posts fail with their reason, "the platform takes only private posts from this server's app". Ask for the audit from the app's page once you have tried it. Peal shows the creator's nickname, the audiences their account offers, the interactions they allow and TikTok's consent before scheduling, as TikTok's guidelines ask.

TikTok fetches photos only from a URL prefix or a domain you verified for the app, under **URL properties**: serve the media store at a public address (`PEAL_MEDIA_PUBLIC_BASE_URL`), verify it, and set `TIKTOK_MEDIA_URL_PREFIX` to it. TikTok then fetches videos too, as its guidelines prefer for media already on a server. Without it, Peal sends videos in parts of 10 MB, holding one part at a time, and refuses TikTok posts with photos when they are scheduled. The server calls `open.tiktokapis.com` and the upload addresses TikTok gives.

### Threads, Instagram and Facebook Pages [#meta]

One app in Meta's developer dashboard connects all three, through three use cases, each with its own credentials:

- **Facebook Login** (Facebook Pages, and Instagram through a Page): the permissions `pages_show_list`, `pages_read_engagement` and `pages_manage_posts` for Facebook Pages, and `instagram_basic`, `instagram_content_publish` and `instagram_manage_insights` for Instagram (insights only for analytics: a member may decline them). Set `META_APP_ID` and `META_APP_SECRET` from the app's basic settings.
- **Instagram** ("Manage messaging and content on Instagram", the Instagram API with Instagram Login): the permissions `instagram_business_basic`, `instagram_business_content_publish` and `instagram_business_manage_insights`. Set `INSTAGRAM_APP_ID` and `INSTAGRAM_APP_SECRET` from its **Business login settings**, which show an Instagram app id and secret apart from the main ones.
- **Threads**: `threads_basic` and `threads_content_publish`. Set `THREADS_APP_ID` and `THREADS_APP_SECRET` from its Threads settings.

A platform whose settings are missing is not offered. Instagram is offered with either of its settings; with both, members connect with Instagram first, and through a Facebook Page as the other way:

| Way in                                        | Needs                                   | Access                                | Gives                                                                                                                                        |
| --------------------------------------------- | --------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Instagram Login (`INSTAGRAM_APP_ID`)          | A professional account, no Page         | 60 days, renewed by Peal a week ahead | Publishing (images, reels, carousels), insights; calls `graph.instagram.com`                                                                 |
| Facebook Login through a Page (`META_APP_ID`) | A professional account linked to a Page | The Page's, which does not expire     | The same, plus what only that API has (product tags, collaborators, hashtag search), which Peal does not use yet; calls `graph.facebook.com` |

In the dashboard, give each use case the addresses [the command](#platform-addresses) prints for it:

| Use case       | Settings the addresses go in                                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Facebook Login | Its valid OAuth redirect URIs, two of them, for Facebook Pages and for Instagram; its data deletion request URL; its deauthorize callback URL |
| Instagram      | Its business login's OAuth redirect URIs; its data deletion request URL; its deauthorize callback URL                                         |
| Threads        | Its redirect callback URL; its data deletion request URL; its deauthorize callback URL                                                        |

When one of its users asks Meta to delete what Peal holds about them, Meta calls the data deletion address with a request signed with that use case's secret. Peal checks the signature, deletes, in every workspace, the channels that person connected through it and their tokens, and the accounts their sign-in still offers a member to choose from, and answers with a confirmation code and the page where its status shows, `PUBLIC_URL/data-deletion/<code>`. The same request sent again, as Meta may retry it, gets the same answer and deletes nothing more. An Instagram request names the account by its app-scoped id or its own: Peal takes either.

When someone removes Peal from their account, Meta calls the deauthorize address the same way: Peal marks the channels that person connected through it to be reconnected, in every workspace, and tells the members who manage them; it deletes nothing. A channel connected again since the request was made is left as it is.

Meta fetches the images and videos it publishes from links to the media store, valid for two hours: the store must answer Meta's servers on the internet, through presigned links or `PEAL_MEDIA_PUBLIC_BASE_URL`. The server calls `graph.facebook.com`, `graph.instagram.com`, `api.instagram.com` and `graph.threads.com`, and signs every call through Facebook Login with the main app's secret, so you may turn on **Require App Secret** in the app's advanced settings. Calls with an Instagram Login token carry no proof.

While the app is in development mode, only people with a role on it can connect their accounts: add yourself, Instagram testers and Threads testers, under App roles. Serving other people needs Meta's App Review of each permission and Business Verification, for each use case. Instagram accounts must be professional ones (business or creator), and, through Facebook Login, linked to a Facebook Page. Each account publishes at most 100 posts in 24 hours through Meta's API, which Peal checks before each one.

### YouTube [#youtube]

A server connects YouTube channels once you make an OAuth client for it in a Google Cloud project:

1. In the Google Cloud console, create a project, and turn on the **YouTube Data API v3** under APIs and services.
2. Under **Google Auth Platform**, set up the consent screen for **External** users, and add the scopes `https://www.googleapis.com/auth/youtube.upload` and `https://www.googleapis.com/auth/youtube.readonly`.
3. Under **Clients**, create a **Web application** client, with the address [the command](#platform-addresses) prints for YouTube as an authorized redirect URI.
4. Put the client id in `YOUTUBE_CLIENT_ID` and its secret in `YOUTUBE_CLIENT_SECRET`.

One of the two settings without the other stops the server at startup; without both, **Channels** does not offer YouTube. Members sign in with Google and pick the channel, a brand account's included, on Google's account chooser: one connection is one channel. Peal asks to upload videos and to read the channel and its videos, nothing more, and renews its access, which lasts an hour, when it uploads or reads counts, and once a month for a channel it does nothing with. Disconnecting a channel revokes that access at Google, unless another workspace still connects the same channel.

While the project's consent screen is in **Testing**, only the test users you list can sign in, and Google ends their access seven days after they connect: their channels must then be reconnected, and Peal tells the workspace. Publish the consent screen, and have Google verify the app for its scopes, to serve anyone for good.

The server calls `oauth2.googleapis.com` and `www.googleapis.com`, and uploads each video there in parts of 8 MiB, holding one at a time; an upload cut off, even by a restart, resumes where YouTube stands. Uploads draw on the project's **Video Uploads** quota, 100 a day unless Google grants more, which resets at midnight Pacific Time: Peal counts them for the whole server, and an upload past `YOUTUBE_DAILY_UPLOADS`, or one YouTube refuses for its quota or the channel's daily limit, waits for the next day. Processing polls and analytics draw on the project's other quota, 10,000 units a day.

Until November 2026, Google kept the videos of API projects it had not audited private. It no longer does, but a channel's settings or Google's restrictions can still keep a video private: Peal compares what YouTube answers with the visibility the member chose, and says so on the post's page.

### Pinterest [#pinterest]

A server connects Pinterest accounts once you register an app for it on Pinterest's developer site:

1. On `developers.pinterest.com`, under **My apps**, connect an app, with a link to your privacy policy. Pinterest reviews the request and grants **Trial access**.
2. In the app's settings, add `PUBLIC_URL/connect/pinterest/callback` as a redirect URI, such as `https://peal.example.com/connect/pinterest/callback`: Pinterest takes the exact address only.
3. Put the app id in `PINTEREST_APP_ID` and its secret key in `PINTEREST_APP_SECRET`.

One of the two settings without the other stops the server at startup; without both, **Channels** does not offer Pinterest. Members sign in on Pinterest and allow Peal to read their boards and Pins, to create Pins and to read their account: Peal asks for `boards:read`, `boards:write`, `pins:read`, `pins:write` and `user_accounts:read`, and nothing about secret boards. Access lasts 30 days, and Peal renews it a week ahead with a refresh token Pinterest keeps good for 60 days after each renewal. Pinterest's API revokes no member's access: disconnecting a channel deletes Peal's tokens, and the member removes the app in their Pinterest settings.

With **Trial access**, an app makes 1,000 calls a day in all, and the boards and Pins it creates are seen by their creator alone, in Pinterest's Sandbox: set `PINTEREST_SANDBOX=true`, so that the server calls `api-sandbox.pinterest.com`. The Sandbox creates no video Pin and gives no analytics. To publish for real, ask Pinterest for **Standard access** from the app's page, with a video of your server signing a member in through Pinterest and creating a Pin; once granted, unset `PINTEREST_SANDBOX`, and have members connect their accounts again, as a Sandbox token works nowhere else. Standard access allows each account 100 writes and 60 analytics reads a minute.

The server calls `api.pinterest.com` (or the Sandbox), and sends each video to the address Pinterest names for it, an object store's. Pinterest fetches a Pin's images from links to the media store, valid for two hours: the store must answer Pinterest's servers on the internet, through presigned links or `PEAL_MEDIA_PUBLIC_BASE_URL`. Pinterest's developer guidelines ask that each Pin be chosen by the member who publishes it, which scheduling a post is, and limit what an app may keep of what it reads: Peal keeps a Pin's id and its counts, for the workspace that published it.

### Google Business Profile [#google-business]

A server connects Business Profile locations once Google has given one of your Google Cloud projects access to the Business Profile APIs, which it does on request:

1. In the Google Cloud console, create a project, or pick one, and note its project number.
2. Ask Google for access with the [GBP API contact form](https://support.google.com/business/contact/api_default), choosing **Application for Basic API Access**, from an email address that owns or manages a Business Profile. Google asks that the profile be verified and active for 60 days or more, and that the business have a website. It answers by email once it has reviewed the request.
3. Look at the project's quota for the Business Profile APIs: 300 requests a minute means access is granted, 0 that it is not yet. A quota increase does not replace the request.
4. Under APIs and services, enable the **Google My Business API**, which makes the posts and shows in the console only once access is granted, the **My Business Account Management API** and the **My Business Business Information API**, which list accounts and locations.
5. Under **Google Auth Platform**, set up the consent screen for **External** users, and add the scope `https://www.googleapis.com/auth/business.manage`.
6. Under **Clients**, create a **Web application** client, with `PUBLIC_URL/connect/googleBusiness/callback` as an authorized redirect URI, such as `https://peal.example.com/connect/googleBusiness/callback`.
7. Put the client id in `GOOGLE_BUSINESS_CLIENT_ID` and its secret in `GOOGLE_BUSINESS_CLIENT_SECRET`.

One of the two settings without the other stops the server at startup; without both, **Channels** does not offer Google Business Profile. The client is its own, apart from YouTube's, as Google gives access, counts quota and reviews apps project by project. A project that has both products serves both: give the same client id and secret under both names, with both redirect URIs on the client.

Members sign in with Google and choose among the verified locations of the accounts they own or manage, 200 at most a sign-in: one connection is one location. Peal lists accounts and locations when a member connects, makes posts, and reads a location's posts back when Google's answer to one was lost. It changes nothing else on a profile, and reads no reviews. It renews its access, which lasts an hour, whenever it posts, and at least once a month for a location it posts nothing to, so Google never drops it; disconnecting a location revokes that access at Google, unless another workspace still connects the same location.

While the project has no access, Google answers every call with 429: connecting fails as the platform not answering, and the server's log says to check the project. While the consent screen is in **Testing**, only its test users sign in, and Google ends their access after seven days, as for YouTube.

The server calls `oauth2.googleapis.com`, `mybusinessaccountmanagement.googleapis.com`, `mybusinessbusinessinformation.googleapis.com` and `mybusiness.googleapis.com`. Google fetches each photo from a link to the media store, valid for two hours: the store must answer Google's servers on the internet, through presigned links or `PEAL_MEDIA_PUBLIC_BASE_URL`. Every call draws on the project's 300 requests a minute; past them, a post waits and goes out a little later.

Google's [policies for these APIs](https://developers.google.com/my-business/content/policies) bind you as the project's owner. Among them: act only for businesses whose owners or managers signed in themselves, tell them of a change to their profile within 48 hours (Peal tells a post's author in the app once it is live, and by email if they chose so), let a business leave, which disconnecting a channel does, and store what the APIs answer only within the limits Google sets. Of that, Peal keeps a location's name and address, which label its channel, and each post's name and address on Google, until the channel is disconnected or the workspace deleted: read the policies, and decide whether that suits your use.

## Writing assistant [#ai]

The composer's writing assistant rewrites a post in a tone, shortens it to fit a platform, translates it, or suggests hashtags. It is off until `PEAL_AI_PROVIDER` names a provider: until then, the web app hides it, and its endpoints answer `AssistantUnavailable`.

- **Anthropic**: set `PEAL_AI_PROVIDER=anthropic` and `PEAL_AI_API_KEY`. The assistant asks `claude-opus-5-5` unless `PEAL_AI_MODEL` names another model, on Anthropic's API unless `PEAL_AI_BASE_URL` names a proxy.
- **Any OpenAI-compatible endpoint**, such as a model server you run: set `PEAL_AI_PROVIDER=openai-compatible`, `PEAL_AI_BASE_URL` to the address `/chat/completions` follows, such as `http://127.0.0.1:8000/v1`, and `PEAL_AI_MODEL` to one of its models. Add `PEAL_AI_API_KEY` if it asks for one.

A provider named without the settings it needs stops the server at startup, and the error names the variable missing. The server calls the provider directly, not through the guard that keeps platform calls on public addresses, so the endpoint may run on the same machine or your private network.

Each workspace may send the assistant `PEAL_AI_DAILY_REQUESTS` requests per UTC day, 100 unless set; `0` lets none through. With [billing](#billing) on, each plan sets its own instead. Without it, every workspace gets that many: on an instance where anyone may sign up, each new workspace adds to what your provider can bill. A request the provider could not be reached for does not count. One that gets no answer within 90 seconds fails and counts, as the provider may have run it.

What members send is the post's text, up to 5,000 characters, and answers are capped at 4,096 tokens. The text is sent as data, with instructions the text cannot change. The server never logs or traces the text or the answer, saves neither, and sends the provider no trace context: its logs and traces name the provider, the model, the token counts and the kind of failure only.

## Billing [#billing]

Billing is off until `STRIPE_SECRET_KEY` is set: there are no plans, nothing is limited, and the workspaces' billing page says so. With a key, every workspace starts on the free plan, and a Stripe subscription moves it to Starter, Pro, Business or Agency, monthly or yearly. [Plans and billing](/billing) lists them, with what each limits, the trial, ordering, cancelling and withdrawing.

Posts count in the calendar month (UTC) they go out in, once scheduled: drafts and cancelled posts do not, a post taken back to draft gives its place back, and one posted again on a channel counts once. Members count with the invitations still pending when inviting. Pages or Instagram accounts ticked together need room for all of them, or none is connected. Media count by the bytes stored, uploads in progress included. A limit applies when something is added, so a workspace on a smaller plan than it needs keeps what it has, but schedules nothing while it has more channels than its plan allows.

1. In Stripe, create a product for each paid plan, with a monthly and a yearly EUR price, both tax-exclusive, and give them the lookup keys `peal_<plan>_monthly` and `peal_<plan>_yearly` (`peal_starter_monthly`, `peal_pro_yearly`…), or another prefix set in `STRIPE_LOOKUP_KEY_PREFIX`. Their amounts are those of [Plans and billing](/billing#plans): Peal shows them before checkout, so keep them equal: when it starts, a server that bills checks that each price exists, is active, costs what Peal publishes at the right interval, and is tax-exclusive, and stops with the list of what differs otherwise. If Stripe does not answer, it starts and logs a warning.
2. Add a webhook endpoint for `PUBLIC_URL/api/auth/stripe/webhook` with the `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted` and `checkout.session.completed` events, and set `STRIPE_WEBHOOK_SECRET` to its signing secret. Leave this path open to Stripe if something guards the rest of `/api/auth`.
3. Turn on Stripe Tax: checkout always has it add the VAT, as the prices are tax-exclusive and Peal shows them VAT included. Turn on the customer portal, where members update their payment method and download invoices, without retention offers, and with plan switching (subscription updates) and cancellation turned off: plans change and end on the billing page only, where each change takes an order. Set the web app's `PEAL_TERMS_URL` to your terms of service, which the billing page links to before an order, and `PEAL_CONTACT_URL` to where people write for more than the largest plan.
4. Make Stripe's side match your tax and invoicing duties, which Peal leaves to Stripe. In Stripe Tax: your origin address, a registration for each place you collect tax in (for an EU seller, the home country and the One-Stop Shop), and the product tax code of each plan's product (software as a service, `txcd_10103001` for business use or `txcd_10103000` for personal use). Checkout then asks every customer for a billing address and offers a field for a business's tax id, which Stripe prints on the invoice and uses for the reverse charge. In the invoice settings: your legal mentions (company identifiers, VAT number, footer), a numbering scheme, and emailing customers their invoices and receipts. In the customer portal: the invoice history, so members download their invoices from **Billing**.
5. Set `SITE_APP_URL` when you build the marketing site, so its footer links to the app's pages to cancel a contract and to withdraw from one ([environment variables](/environment-variables)).

Owners and admins order, cancel and withdraw from the workspace's billing page, in their own session; staff impersonating them, API keys and OAuth clients cannot. A checkout starts only for an order placed there in the last 30 minutes, which records the request to start at once. A subscription's state comes only from its webhook events, checked against the signing secret: an event sent twice is recorded once, and an older one never replaces a newer one. A subscription stays paid for while Stripe retries a failed payment; unpaid, paused or cancelled, the workspace is back on the free plan. A trial is set to end, cancelled, with its trial, even if a payment method is added, so it never turns into a charge: its workspace is then on the free plan, and a paid plan ordered during the trial ends the trial once it is paid for. A workspace with a subscription Stripe may still bill, unpaid and paused ones included, cannot be deleted, nor the account of its only member, until the subscription is cancelled. The `billing.reminders` job reminds, every hour, the trials that end within three days and the yearly plans that renew within 45 days, always more than a month ahead.

Anyone cancels a contract or withdraws from one without signing in, from **Cancel your contract** and **Withdraw from contract here** at the foot of every page of the web app (`/cancel` and `/withdraw`), which a server that does not bill does not show. `POST /api/contract-requests` records each request with the moment it came, which is the one that counts whenever it is applied, and acknowledges it by email; it takes 5 requests an hour from an address (read from `AUTH_IP_HEADERS`), a Turnstile token when Turnstile is on, and writes to one email address 5 times a day at most. A request that gives the contract number is applied at once; one whose address manages a workspace's billing is applied from the link in its acknowledgement; the others wait in the staff console ([Staff console](/staff#contract-requests)). The `billing.contract-requests` job takes up, every five minutes, what the mail or Stripe could not take. Requests are kept with their workspace, then 5 years after it is deleted, as those no contract was found for are from their receipt.

## Captcha [#captcha]

With `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`, signing up and asking for a password reset need a Cloudflare Turnstile token: the forms show the widget, and the server checks each token with Cloudflare before going on. Signing in relies on its rate limits. Add your public address to the widget's hostnames in Cloudflare. Cloudflare's test keys let you try it without a real widget.

## The command line and MCP clients [#mcp]

The [command line](/cli) signs in with a code that people approve at `PUBLIC_URL/device`, and needs nothing more.

[MCP clients](/mcp) sign in with OAuth, which needs `PUBLIC_URL` on HTTPS, or `localhost` for development. On a plain HTTP address elsewhere, such as `http://192.168.1.20:3001`, the server starts, logs a warning, and its MCP endpoint refuses every request.

Most MCP clients register themselves before they sign in, which the server allows only with `MCP_DYNAMIC_REGISTRATION=true`. Anyone may then register a client, under any name: the consent page tells people that Peal has not checked it, and where it sends them back to.

## Staff accounts [#staff]

Staff, Better Auth's admin role, run the server from the [staff console](/staff) at `/admin`: they find accounts and workspaces, ban accounts or sign them out, send a confirmation again, and act as a member for an hour, each action recorded in an audit log. Better Auth's own admin endpoints are off, but for stopping an impersonation. Staff cannot delete an account: only its owner can, from [their account settings](/settings#delete-account), which deletes what Peal keeps about them. Make an account staff in the database, then sign in again:

```sql
UPDATE auth."user" SET role = 'admin' WHERE email = 'you@example.com';
```

While impersonating, staff cannot connect channels, publish, manage API keys or billing, change workspaces, or let an application act for the member. They can read the member's notifications, but not mark them read or change the member's email preferences. They can ask the writing assistant in the member's workspaces, which counts toward those workspaces' daily requests.

## Legal retention [#legal-retention]

French law has a host keep the data that identifies whoever contributed content, so that a judicial authority can ask for it (loi n° 2004-575, Article 6, V, and décret n° 2021-1362). Peal can do it, and does not by default: `PEAL_LEGAL_RETENTION` is `false` unless you set it.

**Who must turn it on.** You, if both are true:

- you are established in France, or offer your Peal to people there;
- your Peal stores content for other people: customers, clients, the public, anyone but your own organisation.

Set `PEAL_LEGAL_RETENTION=true` then. Not keeping the data is an offence (the same Article 6, V, B). If you are not sure the law applies to you, ask a lawyer before you open your server to others.

**Who must leave it off.** Everyone else: a team that runs Peal for its own posts, or an operator with no tie to France. Data protection law (GDPR, Article 5(1)(c)) forbids keeping this data without an obligation to.

**What it keeps**, in the `legal` schema, which nothing else in the server reads:

- each request that creates, changes or deletes posts or media, through the web app, an API key, the command line or an MCP client: when, from which address (read as sign-in reads it, from `AUTH_IP_HEADERS`), over which protocol and how it signed in, kept {{keep-legal-connections-en}}. Never what the request carried;
- when an account closes, its holder's name and email address, kept {{keep-legal-identity-en}}, and how they signed in (each sign-in method's identifier, never the password or its hash) and their Stripe customers, kept {{keep-legal-account-en}}.

A daily job (`legal.retention`, at 03:47 UTC) deletes each record once its time is up. Staff read these records only by answering a legal request in the [staff console](/staff#legal-requests), and each answer is recorded and kept {{keep-legal-disclosures-en}}. Each user's export lists their connections and what closing their account would leave. Your own privacy notice should say that you keep them.

**Off**, the server writes nothing to the `legal` schema, and closing an account erases everything.

**Turning it off after it was on** keeps nothing more, and deletes nothing at once: what the server already holds stays until its time is up, as the law had you keep it for that long, and the daily job goes on deleting it. Meanwhile staff with the legal role can still answer a request about it, and each user's export still lists the connections kept about them.

## Deletions and backups [#erasure-ledger]

A backup holds what was deleted after it was taken. Restoring one brings back the accounts and workspaces their users deleted since, and the law has you delete them again before anyone can use them. Peal keeps what that takes outside the database, which a restore would rewind too: each time a workspace is deleted or an account closed, the server writes a small entry in the object store, under `erasures/`, with the ids and the time and nothing else (no name, address or content). The entry is written before the deletion is final, so none goes unrecorded: when the store cannot be reached, the deletion is refused and can be tried again.

After any restore, and before you start the server, apply the ledger again:

```sh
docker compose … run --rm --no-deps server packages/peal-server/src/replay-erasures.ts
```

From a checkout, `bun nx run peal-server:erasures:replay` does the same. It deletes again whatever the restore brought back, prints what it did by id, and can be run again without harm: what is gone stays gone. It cancels nothing at Stripe and emails no one, as both were done when the deletion first ran. A deletion that was refused, such as a post going out, makes it exit with an error: keep the server stopped until it passes. An entry the server never confirmed, because it stopped in the middle of a deletion, is listed and left alone; `--apply-unconfirmed` applies those too, once you have decided each was asked for.

The ledger lives in the media bucket by default. Nothing there is served: the server signs no link to `erasures/`. If your media bucket is public (`PEAL_MEDIA_PUBLIC_BASE_URL`), name a private bucket with `PEAL_ERASURE_LEDGER_BUCKET`, on the same store and reachable with the same key: the server warns at startup until you do. Do not use your backups' bucket, as a server that can write there can delete the backups.

Entries are kept {{keep-erasure-ledger-en}}, a little longer than the backups hold deleted data ({{keep-backups-en}} with the stack's four weekly full backups): a daily job (`workspace.erasure-ledger-retention`, at 04:17 UTC) drops older ones. Keep your backups shorter than that. Where the store has lifecycle rules, add one as a second guard, on the ledger's bucket or its prefix alone: with Cloudflare R2, `wrangler r2 bucket lifecycle add <bucket> expire-erasures erasures/ --expire-days 42`. A rule that names the wrong prefix would delete your media: check it before you save it.

## Privacy declaration [#privacy-declaration]

Each user can download a copy of their data (**Account**, **Your data**, or `peal account export`). With it comes what the GDPR, Article 15, has a controller tell: for each category of data, what it is for, on which legal basis, how long it is kept and where it came from; who receives it; and the rights over it. Peal writes most of it from one registry in its code, which its own privacy policy's retention table is written from too, so the two cannot disagree.

What depends on you, Peal cannot know, and never guesses. Declare it in a JSON file, as `self-host/privacy-declaration.example.json` shows, and name the file with `PEAL_PRIVACY_DECLARATION` (the Compose stack mounts it; a server run another way reads `PEAL_PRIVACY_DECLARATION_FILE`):

- `controller`: who decides what the data is processed for, that is you: `name`, and if you wish `address`, `contact` (where privacy requests go) and `dataProtectionOfficer`;
- `policyUrl`: where your privacy policy is;
- `supervisoryAuthority`: the data protection authority you answer to, `name` and `url`;
- `recipients`: every provider that processes your users' data for you (hosting, media storage, email, payments, bot protection, AI, alerts), each with its `name`, the `service` it gives, the `country` it processes the data in, and the `safeguard` of a transfer outside the European Economic Area, or `null`;
- `retention`: only if you run another stack than this repository's, how long yours keeps `technicalLogs` and `backups`, in English (`en`) and French (`fr`). The registry otherwise states the production stack's: logs {{keep-logs-en}}, traces {{keep-traces-en}}, metrics {{keep-metrics-en}}, and deleted data gone from backups within {{keep-backups-en}}.

Every part is optional. What you leave out reads as not declared in each export, which then tells users less than the law has you tell them: fill it in before you open your server to others. The server reads the file when it starts, and stops on one it cannot read: restart it after changing the file (`docker compose restart server`), or exports keep the old declaration.

## Telemetry [#telemetry]

Set `OTEL_EXPORTER_OTLP_ENDPOINT` to an OpenTelemetry collector's OTLP/HTTP address, such as `http://otel-collector:4318`, and the server exports its logs, metrics and traces there, as JSON. [Environment variables](/environment-variables#telemetry) lists the other OpenTelemetry settings it reads.

### Web app errors [#web-errors]

The web app reports its errors to the server, at `POST /api/client-errors`: what nothing caught in a browser, promises rejected without a handler, the error pages its boundaries show, and the pages its own server failed to render. A report names nobody. It sends no cookie, and holds the error's message and stack, the page's path without its query or fragment and with its ids replaced, the page's route, the release and the browser's user agent; the server replaces any email address, id, API key, token or link's query the report still quotes, and drops control characters. A browser sends each error once, and ten at most a page.

The server takes 30 reports a minute from each address, which it reads from the header `AUTH_IP_HEADERS` names, and 16 KiB at most each. It logs each one at error level, with the event name `peal.client_error` and OpenTelemetry's attribute names (`exception.message`, `exception.stacktrace`, `url.path`, `http.route`, `user_agent.original`, and `peal.client_error.kind` and `peal.web.release`), and counts it in `peal.client_errors`, by kind; the reports it drops, in `peal.client_errors.dropped`, by reason. In Prometheus they are `peal_client_errors_total` and `peal_client_errors_dropped_total`, and in Loki `{service_name="peal-server"} | event_name="peal.client_error"`.

The production stack's Grafana shows them on its **Web app errors** dashboard, and warns when more than 20 reports arrive in 10 minutes; its alert on the server's own error logs leaves them out. Set `PEAL_RELEASE` on the web app to name the release its reports come from: the production stack sets it to `PEAL_VERSION`.
