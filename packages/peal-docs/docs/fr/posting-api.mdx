Un script ou un agent qui publie par l’[API HTTP](/api-overview) peut vérifier une publication avant de l’envoyer, attendre le résultat d’une publication qui part maintenant, envoyer jusqu’à 50 publications en une requête, importer des publications depuis un fichier CSV, et lister les publications de l’espace de travail avec des filtres. Cette page montre chaque requête avec un exemple. La [référence de l’API](/reference) donne tous les champs.

## Avant de commencer [#start]

Tous les points d’accès de cette page se trouvent sous `/api/workspaces/{workspaceId}/posts`. Les exemples lisent l’identifiant de l’espace de travail dans `$WORKSPACE_ID` et une [clé d’API](/settings#api-keys), de la forme `peal_…`, dans `$PEAL_API_KEY`. Les identifiants sont inventés, et les réponses abrégées : une publication est toujours répondue en entier, comme la répond `GET …/posts/{postId}`.

| Requête                        | Ce qu’elle fait                                           | Demande                                      |
| ------------------------------ | --------------------------------------------------------- | -------------------------------------------- |
| `POST …/posts/validate`        | Vérifie une publication, sans rien créer                  | `post:read`, `channel:read`                  |
| `POST …/posts/send`            | Crée une publication et l’envoie, maintenant ou plus tard | `post:schedule`, `channel:read`              |
| `GET …/posts/{postId}/outcome` | Attend qu’une publication soit partie                     | `post:read`                                  |
| `POST …/posts/bulk`            | Crée et envoie jusqu’à 50 publications                    | `post:schedule`, `channel:read`              |
| `POST …/posts/import`          | Crée et envoie les publications d’un fichier CSV          | `post:schedule`, `post:read`, `channel:read` |
| `GET …/posts/search`           | Liste les publications de l’espace de travail, filtrées   | `post:read`, `channel:read`                  |

Une publication qui montre des médias demande aussi `media:read`. Un jeton d’accès OAuth a besoin du scope `workspace:publish` pour `send`, `bulk` et `import` ([Ce que permet chaque permission](/agents#scopes)).

Ce que publient `send`, `bulk` et `import` atteint le public des plateformes, et Peal ne peut pas le reprendre une fois parti. Avant son heure, annulez ou déprogrammez une publication.

## Vérifier une publication sans la créer [#validate]

`POST …/posts/validate` prend ce que prend `send`, ou un brouillon, qui n’a pas de `when`. Il n’écrit rien. Il répond 200, que la publication puisse passer ou non, avec `valid` et tout ce qui la ferait refuser, d’un coup.

```bash
curl -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/validate \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "channelIds": ["0190f3a0-0000-7000-8000-00000000c001"],
    "content": {
      "text": "Notre catalogue de printemps est sorti : https://example.com/printemps #printemps",
      "media": [],
      "overrides": []
    },
    "when": { "_tag": "at", "at": "2026-11-16T08:00:00Z", "timeZone": "Europe/Paris" }
  }'
```

```json
{
  "valid": true,
  "channels": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "platform": "bluesky",
      "text": "Notre catalogue de printemps est sorti : https://example.com/printemps #printemps",
      "textCounts": [
        { "length": 81, "maximum": 300, "unit": "graphemes" },
        { "length": 81, "maximum": 3000, "unit": "utf8Bytes" }
      ],
      "hashtags": { "count": 1, "maximum": null },
      "mentions": { "count": 0, "maximum": null },
      "links": { "count": 1, "maximum": null },
      "media": { "count": 0, "maximum": 4 },
      "parts": [],
      "violations": []
    }
  ],
  "violations": [],
  "unknownChannels": [],
  "unknownMedia": [],
  "schedule": "ok",
  "planLimit": null,
  "awaitsApproval": false,
  "duplicates": []
}
```

| Champ             | Ce qu’il contient                                                                                                                                                                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `valid`           | Vrai quand rien de ce qui suit ne refuse la publication                                                                                                                                                                                                     |
| `channels`        | Une entrée par canal de l’espace de travail que nomme la publication, dans l’ordre donné                                                                                                                                                                    |
| `violations`      | Ce qui ne va pas quel que soit le canal : aucun canal, ou un texte ou des options pour un canal où la publication ne va pas                                                                                                                                 |
| `unknownChannels` | Les canaux qu’elle nomme et qui ne sont pas à l’espace de travail                                                                                                                                                                                           |
| `unknownMedia`    | Les médias qu’elle montre et qui ne sont pas à l’espace de travail, ou pas prêts                                                                                                                                                                            |
| `schedule`        | `ok` ; `inPast`, une heure passée de plus d’une minute ; ou `invalidTimeZone`, quand le fuseau n’est pas un fuseau IANA. Null sans `when`.                                                                                                                  |
| `planLimit`       | La limite de l’abonnement de l’espace de travail que la publication dépasserait, telle que la dit `PlanLimitReached`. Null quand l’abonnement a de la place, sur une instance qui ne facture pas, ou sans `when`.                                           |
| `awaitsApproval`  | Si la publication, envoyée telle quelle, attendrait une [approbation](/review) avant d’être programmée, comme l’espace de travail le demande à cet appelant : elle serait créée, avec le statut `awaitingApproval`. Cela ne refuse rien. False sans `when`. |
| `duplicates`      | Les canaux qui ont déjà le même contenu par une autre publication proche de son heure, chacun avec cette publication ([Publications en double](#duplicates)). Aucun sans `when`, ou quand la requête autorise les doublons.                                 |

Chaque entrée de `channels` contient :

- `text` : le texte que reçoit le canal, c’est-à-dire celui qui lui est propre, ou celui de la publication ;
- les nombres ci-dessous portent sur les médias que reçoit le canal : les siens, quand son entrée lui en donne ([Des médias propres sur un canal](#channel-media)), ou ceux de la publication ;
- `textCounts` : la longueur de ce texte, comptée comme la compte la plateforme du canal, face à chacune de ses limites. Bluesky en a deux, en graphèmes et en octets ;
- `hashtags`, `mentions`, `links` et `media` : combien la publication en contient (`count`) et le maximum que prend la plateforme (`maximum`, null quand Peal ne lui connaît pas de limite). `links` compte les liens différents ;
- `parts` : les parties qui suivent la première d’un [fil](/scheduling#threads), dans l’ordre, chacune avec son rang (`part`, à partir de 1), son texte (`text`) sur le canal et les mêmes décomptes ; aucune pour une publication seule. Une plateforme qui ne prend qu’une publication seule les liste quand même, et les refuse avec `tooManyParts` ;
- `violations` : chaque règle de la plateforme que la publication enfreint, dans n’importe laquelle de ses parties (texte, formats, tailles, nombre et durées des médias, options), et celles du compte lui-même quand sa plateforme les donne. Celle qui porte sur une partie suivante la désigne par `part`. Elles se lisent comme dans `PostContentInvalid` ([Comment lire les refus](/agents#refusals)).

Une publication qui serait refusée répond 200 aussi, avec `valid` à faux :

```json
{
  "valid": false,
  "channels": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "platform": "bluesky",
      "textCounts": [
        { "length": 342, "maximum": 300, "unit": "graphemes" },
        { "length": 342, "maximum": 3000, "unit": "utf8Bytes" }
      ],
      "parts": [],
      "violations": [
        {
          "_tag": "textTooLong",
          "channelId": "0190f3a0-0000-7000-8000-00000000c001",
          "platform": "bluesky",
          "length": 342,
          "maximum": 300,
          "unit": "graphemes"
        }
      ]
    }
  ],
  "unknownChannels": ["0190f3a0-0000-7000-8000-00000000c009"],
  "schedule": "inPast"
}
```

Sans `when`, la requête est celle d’un brouillon : ni l’heure, ni la place dans l’abonnement, ni les doublons ne sont vérifiés.

Une publication valide maintenant peut encore être refusée plus tard : un canal déconnecté, un mois rempli entre-temps.

## Publier maintenant et attendre le résultat [#wait]

`POST …/posts/send` répond dès que la publication est créée, pendant qu’elle se publie. Avec `wait`, un nombre de secondes de 0 à 60, une publication qui part maintenant est répondue une fois que chaque canal a son résultat :

```bash
curl -X POST "https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/send?wait=30" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 5f0c2b7e-3d1a-4e58-9a6b-2c4d8e1f7a90" \
  -d '{
    "channelIds": [
      "0190f3a0-0000-7000-8000-00000000c001",
      "0190f3a0-0000-7000-8000-00000000c002"
    ],
    "content": {
      "text": "Notre catalogue de printemps est sorti. À lire sur https://example.com/printemps",
      "media": [],
      "overrides": []
    },
    "when": { "_tag": "now" }
  }'
```

```json
{
  "id": "0190f3a0-0000-7000-8000-00000000b001",
  "status": "finished",
  "outcome": "partiallyPublished",
  "targets": [
    {
      "id": "0190f3a0-0000-7000-8000-00000000d001",
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "status": "published",
      "publishedAt": "2026-11-16T08:00:02.000Z",
      "permalink": "https://social.example/@peal_example/115512345678901234",
      "failureReason": null
    },
    {
      "id": "0190f3a0-0000-7000-8000-00000000d002",
      "channelId": "0190f3a0-0000-7000-8000-00000000c002",
      "status": "failed",
      "publishedAt": null,
      "permalink": null,
      "failureReason": "tokenExpired"
    }
  ]
}
```

- La réponse est 201 dans les deux cas : la publication a été créée.
- Quand chaque canal a son résultat avant la fin de l’attente, le `status` de la publication est `finished`, avec son `outcome`. Chaque cible est `published`, avec son `permalink`, ou `failed`, avec sa `failureReason`.
- Quand le temps est écoulé avant, la réponse est la publication dans son état du moment, avec des cibles encore `pending` ou `publishing`. Elle continue de se publier.
- Un [fil](/scheduling#threads) a son résultat sur un canal quand toutes ses parties y sont parties, ou que l’une a échoué : une cible reste `publishing` entre deux parties, et `parts.live` liste celles qui sont en ligne. Avec une attente entre deux parties plus longue que `wait`, le temps s’écoule avant.

`GET …/posts/{postId}/outcome` attend la suite. Il prend le même `wait`, et répond la publication une fois que chaque canal a son résultat, ou dans son état du moment quand le temps est écoulé : redemandez alors.

```bash
curl "https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/0190f3a0-0000-7000-8000-00000000b001/outcome?wait=30" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

Sans `wait`, il n’attend pas. Un brouillon, une publication annulée et une publication programmée pour après la fin de l’attente sont répondus aussitôt, comme une requête qui arrive alors que le serveur, ou l’espace de travail (10 à la fois), a autant de requêtes en attente qu’il en accepte : redemandez alors. Attendre ne change rien et ne retient rien : la publication part dans sa propre tâche dans tous les cas, et les [webhooks](/webhooks#events) disent toujours ce qu’elle est devenue sur chaque canal.

## Envoyer plusieurs publications en une requête [#bulk]

`POST …/posts/bulk` crée et envoie jusqu’à 50 publications, chacune comme le ferait `send`. Chaque élément est une publication, avec ses propres canaux, son contenu, ses options et son heure. Le même contenu à plusieurs heures, ce sont plusieurs éléments ; une publication qui part à une heure différente sur chaque canal aussi.

```bash
curl -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/bulk \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 9b2e4d6f-1a3c-4b5d-8e7f-0a1b2c3d4e5f" \
  -d '{
    "posts": [
      {
        "channelIds": ["0190f3a0-0000-7000-8000-00000000c001"],
        "content": {
          "text": "Notre catalogue de printemps est sorti. À lire sur https://example.com/printemps",
          "media": [],
          "overrides": []
        },
        "when": { "_tag": "at", "at": "2026-11-16T08:00:00Z", "timeZone": "Europe/Paris" }
      },
      {
        "channelIds": ["0190f3a0-0000-7000-8000-00000000c009"],
        "content": {
          "text": "Notre catalogue de printemps est sorti. À lire sur https://example.com/printemps",
          "media": [],
          "overrides": []
        },
        "when": { "_tag": "at", "at": "2026-11-16T17:00:00Z", "timeZone": "America/New_York" }
      }
    ]
  }'
```

```json
{
  "created": 1,
  "refused": 1,
  "items": [
    {
      "_tag": "created",
      "index": 0,
      "replayed": false,
      "post": {
        "id": "0190f3a0-0000-7000-8000-00000000b002",
        "status": "scheduled",
        "schedule": {
          "at": "2026-11-16T08:00:00.000Z",
          "timeZone": "Europe/Paris"
        }
      }
    },
    {
      "_tag": "refused",
      "index": 1,
      "refusal": {
        "_tag": "UnknownChannels",
        "channelIds": ["0190f3a0-0000-7000-8000-00000000c009"]
      }
    }
  ]
}
```

- Les éléments sont traités dans l’ordre, un à la fois, chacun pour lui-même. Un élément refusé n’empêche aucun des autres d’être créé, et rien n’est défait.
- La réponse est 200 dès que la requête elle-même a pu être lue, même si tous les éléments ont été refusés. `items` dit, pour chaque élément repéré par sa place dans la requête (`index`, à partir de 0), `created` avec sa publication, ou `refused` avec ce que `send` aurait répondu pour lui seul, sous forme de données : les violations de son contenu, des canaux ou médias inconnus, une heure passée, la limite de l’abonnement, un doublon.
- Une requête qui ne peut pas être lue du tout (mal formée, sans élément, plus de 50) répond 400, et ne crée rien.
- Les limites de l’abonnement valent sur toute la requête : une fois le mois plein, les éléments restants sont refusés.
- Chaque élément est comparé aux publications créées avant lui, éléments précédents de la requête compris, pour le même contenu sur le même canal ([Publications en double](#duplicates)).

Un en-tête `Idempotency-Key` permet de renvoyer toute la requête sans risque pendant 24 heures. Chaque élément est gardé sous la clé et sa place : la même requête renvoyée répond les publications qu’elle a créées, avec `replayed` à vrai, et crée celles qui ne l’avaient pas été la première fois si elles peuvent l’être désormais. Un élément modifié sous la même clé est refusé avec `IdempotencyKeyReused`. Un élément peut porter sa propre `idempotencyKey`, utilisée pour lui à la place de celle de l’en-tête.

## Importer des publications depuis un fichier CSV [#import]

Dans l’application web, [Importer depuis un fichier](/scheduling#import-screen) vérifie un fichier et l’importe par ce point de terminaison.

`POST …/posts/import` crée et envoie les publications que liste un fichier CSV, une par ligne. La première ligne du fichier nomme les colonnes, dans n’importe quel ordre :

| Colonne           | Obligatoire | Ce qu’elle contient                                                                                                                                                   |
| ----------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`            | oui         | Le texte de la publication                                                                                                                                            |
| `channels`        | oui         | Des identifiants de canaux, séparés par des espaces, des virgules ou des points-virgules                                                                              |
| `at`              | oui         | `now` ; un instant avec son décalage, comme `2026-11-20T09:00:00Z` ; ou une heure locale sans décalage, comme `2026-11-20 10:00`, lue dans le `time_zone` de la ligne |
| `time_zone`       | non         | Un fuseau IANA, comme `Europe/Paris`. UTC s’il est absent.                                                                                                            |
| `media`           | non         | Des identifiants de médias prêts de l’espace de travail                                                                                                               |
| `allow_duplicate` | non         | `true` ou `false` ([Publications en double](#duplicates))                                                                                                             |
| `idempotency_key` | non         | La clé d’idempotence propre à la ligne                                                                                                                                |

Une ligne est une publication seule, avec un même texte pour tous ses canaux : un [fil](/scheduling#threads), un texte propre à un canal ou les options d’une plateforme ne tiennent pas dans une cellule, et passent par `send` ou `bulk`. Un fichier qui nomme une autre colonne est refusé en entier.

Les cellules suivent la RFC 4180 : une cellule qui contient une virgule, un guillemet ou un saut de ligne s’écrit entre guillemets doubles, et un guillemet à l’intérieur est doublé. Un fichier contient au plus 100 lignes sous la première, et 1 000 000 de caractères.

```csv title="publications.csv"
text,channels,at,time_zone,media
Notre catalogue de printemps est sorti.,0190f3a0-0000-7000-8000-00000000c001 0190f3a0-0000-7000-8000-00000000c002,2026-11-20 10:00,Europe/Paris,0190f3a0-0000-7000-8000-00000000a001
"Derniers jours : les prix ""printemps"" s’arrêtent dimanche, à minuit.",0190f3a0-0000-7000-8000-00000000c001,2026-11-27T09:00:00Z,,
```

La requête est en JSON, avec le texte du fichier dans `csv`. Ici, `jq` l’écrit à partir du fichier :

```bash
jq -Rs '{ csv: ., dryRun: true }' publications.csv |
  curl -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/import \
    -H "Authorization: Bearer $PEAL_API_KEY" \
    -H "Content-Type: application/json" \
    -d @-
```

```json
{
  "created": 0,
  "dryRun": true,
  "rows": [
    { "_tag": "valid", "row": 1 },
    { "_tag": "valid", "row": 2 }
  ]
}
```

Le fichier est d’abord vérifié, ligne par ligne, comme `validate` vérifie une publication, et comme le fichier qu’il est : une ligne à laquelle une ligne précédente ne laisse plus de place dans son mois est refusée avec `PlanLimitReached`, une ligne qui dit ce que dit une ligne précédente, sur le même canal à moins de 23 heures d’elle, avec `DuplicatePost` (son `message` nomme cette ligne, puisqu’il n’y a pas encore de publication à nommer), et une ligne qui porte l’`idempotency_key` d’une ligne précédente avec une autre publication avec `IdempotencyKeyReused`. Si une seule ligne n’est pas valide, rien n’est créé. `dryRun: true` s’arrête là même quand toutes les lignes sont valides. Sinon, les lignes sont ensuite créées dans l’ordre, comme `bulk` crée ses éléments.

`rows` contient un résultat par ligne, repérée par sa place sous la première ligne, à partir de 1. Les lignes vides ne sont pas des lignes, et ne sont pas comptées. Les cellules suivent strictement la RFC 4180, pour qu’aucun texte ne soit jamais coupé : une cellule qui contient une virgule, un saut de ligne ou un guillemet s’écrit entre guillemets doubles, un guillemet à l’intérieur écrit deux fois, et une ligne finit après sa dernière cellule, sans virgule.

| `_tag`       | Signification                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `created`    | La publication de la ligne a été créée : `post` la contient, et `replayed` dit si sa clé d’idempotence a répondu une publication créée auparavant.                                                                                                                                                                                                                                                     |
| `valid`      | La ligne a été vérifiée, pas créée : un essai à blanc, ou une autre ligne a empêché l’import du fichier.                                                                                                                                                                                                                                                                                               |
| `refused`    | `refusal` contient ce que `send` aurait répondu pour elle. Une ligne qui était valide est refusée aussi quand quelque chose a changé depuis la vérification, ou quand elle répète une ligne précédente.                                                                                                                                                                                                |
| `unreadable` | `problems` nomme les cellules en cause : chaque colonne (`column`), `missing` quand la ligne en a besoin, ou `invalid` pour ce qu’elle contient. Une ligne qui a plus ou moins de cellules que la première ligne n’en nomme n’est pas lue du tout : `cells` dit combien étaient attendues (`expected`) et trouvées (`found`). Une virgule dans un texte qui n’est pas entre guillemets en produit une. |

```json
{
  "created": 0,
  "dryRun": false,
  "rows": [
    { "_tag": "valid", "row": 1 },
    {
      "_tag": "unreadable",
      "row": 2,
      "problems": [{ "column": "at", "problem": "invalid" }]
    }
  ]
}
```

La réponse est 200 dès que le fichier a pu être lu. Un fichier qui ne peut pas être lu du tout répond 422 `ImportUnreadable`, et rien n’est créé. `problem` dit pourquoi, et `column` quelle colonne quand il s’agit d’une colonne :

| `problem`           | Le fichier                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `empty`             | est vide                                                                                               |
| `unterminatedQuote` | a une cellule entre guillemets qui ne finit pas                                                        |
| `strayQuote`        | a un guillemet dans une cellule qui n’est pas entre guillemets, ou du texte après un guillemet fermant |
| `unknownColumn`     | nomme une colonne que Peal ne connaît pas                                                              |
| `repeatedColumn`    | nomme deux fois la même colonne                                                                        |
| `missingColumn`     | n’a pas une colonne dont il a besoin                                                                   |
| `tooManyRows`       | a plus de lignes qu’un import n’en prend                                                               |

```json
{ "_tag": "ImportUnreadable", "problem": "missingColumn", "column": "at" }
```

Un en-tête `Idempotency-Key` fonctionne comme sur `bulk`, ligne par ligne.

## Publications en double [#duplicates]

Une publication créée en un seul appel est refusée quand une autre publication de l’espace de travail envoie déjà le même contenu à l’un de ses canaux, à moins de 23 heures de son heure. La réponse est 409 `DuplicatePost`, et rien n’est créé :

```json
{
  "_tag": "DuplicatePost",
  "duplicates": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "postId": "0190f3a0-0000-7000-8000-00000000b001"
    }
  ]
}
```

`duplicates` nomme chaque canal qui a déjà le contenu, avec la première publication qui l’y envoie dans cet intervalle.

- **Le même contenu**, c’est le texte que reçoit le canal et les mêmes médias, dans le même ordre.
- **23 heures**, c’est la journée la plus courte qu’ait un fuseau horaire : une publication qui se répète chaque jour à la même heure locale n’est donc jamais refusée.
- **Seules comptent les publications qui partent ou sont parties**, y compris celles qui attendent une approbation, puisqu’elles partent une fois approuvées : ni les brouillons, ni les publications annulées, ni un canal où la publication a échoué.
- **Ce qui est vérifié** : `send`, chaque élément de `bulk`, chaque ligne d’`import`, les outils MCP `create_post` et `create_posts`, et `peal post`. Programmer un brouillon existant, déplacer une publication et republier sur un canal où elle a échoué ne sont jamais refusés.
- **Quand c’est voulu**, renvoyez la requête avec `allowDuplicate: true`, sur la publication ou sur l’élément de `bulk`, ou avec `allow_duplicate` à `true` sur la ligne du CSV.

Ce refus est distinct des clés d’idempotence. Une clé permet de renvoyer une même requête sans risque. Le refus des doublons rattrape la requête faite deux fois.

`validate` le dit à l’avance, dans `duplicates`.

## Lister les publications [#search]

`GET …/posts/search` liste les publications de l’espace de travail, quel que soit leur état, une page à la fois : 20 sauf si `limit` en décide autrement, 100 au plus. Tous les filtres donnés doivent être satisfaits.

| Paramètre    | Ce qu’il garde                                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`     | `draft`, `awaitingApproval` (elle attend une [approbation](/review), et garde son horaire), `scheduled`, `publishing`, `finished` ou `cancelled`                                |
| `outcome`    | Comment une publication terminée a fini : `published`, `partiallyPublished`, `unconfirmed`, `failed` ou `cancelled`                                                             |
| `channelId`  | Les publications qui ont une cible sur ce canal                                                                                                                                 |
| `platform`   | Les publications qui ont une cible sur un canal connecté de cette plateforme                                                                                                    |
| `from`, `to` | Les publications programmées de `from` (compris) à `to` (exclu). L’un comme l’autre écarte les publications sans heure.                                                         |
| `createdVia` | `web`, `apiKey` ou `application`                                                                                                                                                |
| `authorId`   | Les publications créées par cet utilisateur                                                                                                                                     |
| `sort`       | `createdDesc` (par défaut) ou `createdAsc`, par date de création ; `scheduledDesc` ou `scheduledAsc`, par instant programmé, qui ne listent que les publications avec une heure |
| `limit`      | Le nombre de publications par page, de 1 à 100                                                                                                                                  |
| `cursor`     | Le `nextCursor` de la page précédente                                                                                                                                           |

```bash
curl "https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/search?status=finished&outcome=failed&platform=bluesky&sort=scheduledDesc&limit=50" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```json
{
  "items": [
    {
      "id": "0190f3a0-0000-7000-8000-00000000b003",
      "status": "finished",
      "outcome": "failed",
      "schedule": {
        "at": "2026-11-12T08:00:00.000Z",
        "timeZone": "Europe/Paris"
      },
      "targets": [
        {
          "id": "0190f3a0-0000-7000-8000-00000000d003",
          "channelId": "0190f3a0-0000-7000-8000-00000000c001",
          "status": "failed",
          "permalink": null,
          "failureReason": "tokenExpired"
        }
      ]
    }
  ],
  "channels": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "platform": "bluesky"
    }
  ],
  "nextCursor": "eyJhZnRlciI6IjAxOTBmM2EwIn0"

```

- Chaque publication est répondue en entier, avec ses cibles, leur statut, leur adresse et la raison de leur échec.
- `channels` donne la plateforme de chaque canal que nomme la page et qui est encore connecté : un client nomme ainsi chaque cible sans autre requête.
- Pour la page suivante, passez `nextCursor` dans `cursor`, avec les mêmes filtres et le même tri. Il est null sur la dernière page.
- Un curseur marque l’endroit où sa page s’est arrêtée : les publications créées, déplacées ou supprimées entre-temps ne font ni répéter ni sauter une publication d’une page à l’autre.
- Un curseur d’un autre tri, ou qu’aucune page n’a donné, répond 400.

`GET …/posts?from=…&to=…` reste, pour les calendriers : il liste en une seule réponse les publications programmées entre deux instants, séparés de 62 jours au plus, par instant programmé. Les brouillons n’en font pas partie.

## Ajouter une publication à une file d’attente [#queues]

Une file d’attente est un emploi du temps hebdomadaire de créneaux dans un fuseau horaire ([Files d’attente](/fr/scheduling#queues)) : `GET`, `POST …/queues`, `GET`, `PUT`, `DELETE …/queues/{queueId}` les gardent, avec post:read pour lire et post:update pour modifier. `when: { "_tag": "queue", "queueId": "…" }` sur `send`, sur chaque élément de `bulk` et sur `validate` place une publication sur le prochain créneau libre de la file au lieu d’une heure ; sans `queueId`, sur la file par défaut de l’espace de travail. Le créneau est décidé dans la transaction qui enregistre la publication, sous le verrou de la file : des publications envoyées ensemble prennent des créneaux différents, et une requête renvoyée avec son `Idempotency-Key` n’en prend aucun. Une publication qui ne nomme ni canal ni groupe va sur les canaux et le groupe de canaux de la file, et les `warnings` de sa réponse nomment les canaux de la file déconnectés depuis (`queueChannelsDropped`).

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/posts/send" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"channelIds": [], "content": {"text": "Un conseil intemporel.", "media": [], "overrides": []}, "when": {"_tag": "queue"}}'
```

`POST …/posts/{postId}/queue`, avec `{ "queueId"?, "channelIds"? }`, place un brouillon sur le prochain créneau libre (sur `channelIds`, sinon ses propres canaux, sinon les canaux et le groupe de canaux de la file, comme une publication envoyée sur la file, avec les mêmes `warnings`), ou y déplace une publication programmée ou en attente d’approbation. Son propre créneau compte comme libre : une publication ajoutée de nouveau à sa file reste où elle est, sauf si un créneau avant le sien s’est libéré depuis, qu’elle prend alors. `GET …/queues/{queueId}/slots?count=…` montre les prochains créneaux, chacun avec la publication qui le prend, et `nextFree`, où irait une publication ajoutée maintenant : un conseil, rien n’est retenu.

- Une file sans créneau, ou dont tous les créneaux des 366 prochains jours sont pris, répond 409 `queue_has_no_room`, avec `reason` `noSlots` ou `full`.
- Une file qui n’est pas celle de l’espace de travail, ou une file par défaut qu’il n’a pas, répond 404 `queue_not_found`.
- La place de l’abonnement se compte dans le mois du créneau : `plan_limit_reached` quand il est plein, jamais un mois suivant.
- `validate` répond `queueSlot`, le créneau que la publication prendrait maintenant, auquel tout le reste a été vérifié, ou `queueNoRoom`.

Les publications portent la file qui les a placées (`queueId`, null une fois la file supprimée), et `GET …/posts/search?queueId=…` les liste.

Enregistrer les créneaux d’une file ne déplace aucune publication. `POST …/queues/{queueId}/reshuffle`, sans corps, place ses publications en attente (programmées ou en attente d’approbation, après maintenant) sur ses créneaux tels qu’ils sont maintenant, dans l’ordre de leurs heures, celles déplacées à la main comprises ([Replacer les publications en attente](/fr/scheduling#reshuffle)). Chaque déplacement est un `reschedule` (abonnement compté dans le nouveau mois, `post.scheduled` annoncé pour une publication programmée), sauf pour les approbations : une publication programmée passe par la règle d’approbation comme celle de l’appelant, et une publication en attente d’approbation continue d’attendre à sa nouvelle heure, quel que soit l’appelant, sa demande restant celle de qui l’a faite et `post.approval_requested` annoncé avec la nouvelle heure ; une publication sur son créneau n’est pas réécrite. Il faut `post:schedule`, ou `post:create` là où les publications attendent une approbation, et la réponse dit ce qui a été fait :

```json
{ "moved": 12, "unchanged": 3, "remaining": 0, "stoppedBy": null }
```

`remaining` compte les publications pas encore placées quand le déplacement s’est arrêté, et `stoppedBy` dit pourquoi : `planLimit` (un mois sans place), `full` (plus de créneau dans les 366 jours) ou `changed` (la file a été enregistrée, ou une publication y a été ajoutée sur un créneau pas encore atteint, entre-temps). Rappelez-le pour continuer ; appelé deux fois, le second appel ne déplace rien. Une file sans créneau répond 409 `queue_has_no_room` (`noSlots`).

## Répéter une publication [#recycling]

`POST …/recycling`, avec `{ "postId", "every": { "count", "unit" }, "count"?, "until"?, "variants"?, "queueId"? }`, répète une publication programmée, en cours d’envoi ou en ligne ([comment](/scheduling#recycling)) : `unit` vaut `days` (1 à 365), `weeks` (1 à 52) ou `months` (1 à 12) ; `count` est le nombre de publications en tout, la source comprise (2 à 100) ; `until` le dernier jour, en `YYYY-MM-DD` dans le fuseau de la source ; chaque variante est `{ "text", "overrides"? }`, 10 au plus. La réponse 201 donne la règle, dont `coming` liste les trois prochaines publications et la variante de chacune. Lancer, modifier, mettre en pause, reprendre et arrêter une règle demande post:schedule (ou post:create là où les publications attendent une approbation, pour la lancer), jamais un membre du personnel agissant comme un membre ; la lire, post:read.

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/recycling" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"postId": "'$POST_ID'", "every": {"count": 2, "unit": "weeks"}, "count": 6, "variants": [{"text": "Ouvert tout l’été, comme avant."}]}'
```

`GET …/recycling` liste les règles, de la plus ancienne à la plus récente (`status`, `limit`, `cursor`), `GET …/recycling/{ruleId}` en lit une, `PATCH` change son `count` ou son `until` (null le retire), ses `variants` (un tableau vide les retire) ou la met en pause (`paused`), `POST …/recycling/{ruleId}/resume` avec `{ "variants"? }` relance une règle en pause, ou terminée pour `planLimit`, `contentRejected`, `noChannels`, `queueFull` ou `sourceWithdrawn` (sa publication annulée ou remise en brouillon, une fois programmée de nouveau : 409 `post_not_recyclable` d’ici là, ou tant qu’une autre règle la répète, et 409 `too_many_recycling_rules` au-delà de 100), et `DELETE` l’arrête : les publications créées restent. Chaque publication créée par une règle porte `recyclingId` et `occurrence` (sa place, la source étant 1), et `GET …/posts/search?recyclingId=…` les liste. Chacune agit au nom de qui a lancé la règle, tel qu’il est alors : la règle d’une clé s’arrête une fois la clé révoquée. Changer, mettre en pause, reprendre ou arrêter une règle demande post:schedule, ou d’être la personne qui l’a lancée, agissant comme elle l’a lancée : dans l’application web, par la même application ou avec la même clé.

- Une publication qui ne peut pas se répéter répond 409 `post_not_recyclable`, avec `reason` : `draft`, `awaitingApproval`, `cancelled`, `repeating` (une autre règle la répète), `occurrence` (une règle l’a créée) ou `noChannels`.
- Des variantes qui enfreignent les règles des canaux de la source répondent 422 `recycling_variants_invalid`, chacune par sa place à partir de 1 avec ses violations (un texte de variante vide qui laisse sans texte un canal montrant des [médias propres](#channel-media) y est `empty`) ; une fin qui ne laisse aucune publication à créer, 422 `recycling_ends_too_soon`.
- 100 règles en cours répondent 409 `too_many_recycling_rules` ; une modification d’une règle terminée, 409 `recycling_rule_ended`.

## Publier depuis un flux [#feeds]

`POST …/feeds`, avec `{ "url", "channelIds"?, "channelSetId"?, "mode"?, "queueId"?, "template"? }`, suit un flux web ([comment](/fr/scheduling#feeds)) : il est lu une fois, et chaque élément qu’il contient alors est noté comme vu et jamais créé ; la réponse 201 donne le flux et `seen`, leur nombre. `mode` vaut `draft` (par défaut) ou `queue` (sur `queueId`, ou la file par défaut de l’espace de travail) ; `template` accepte `{title}`, `{link}` et `{summary}`, 1000 caractères au plus ; `attachPicture` importe l’image de chaque élément dans la médiathèque pour sa publication (la personne qui a ajouté le flux doit pouvoir importer des médias, media:upload), et le `pictureSkipped` d’un élément dit pourquoi une image a été laissée de côté. `POST …/feeds/preview` avec `{ "url", "template"? }` lit une adresse et répond son titre et ses trois éléments les plus récents, chacun avec le `text` qu’écrit le modèle, sans rien garder.

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/feeds" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://blog.example/feed.xml", "channelIds": ["'$CHANNEL_ID'"], "template": "Nouveau sur le blog : {title}\n\n{link}"}'
```

`GET …/feeds` liste les flux, du plus ancien au plus récent (`limit`, `cursor`), `GET …/feeds/{feedId}` en lit un (son `status`, `lastCheckedAt`, `nextCheckAt`, `failingSince` et `lastFailure`), `PATCH` change ce qu’il nomme (une nouvelle `url` est lue aussitôt, comme à l’ajout), le met en pause (`"status": "paused"`) ou le relance (`"active"`, lu aussitôt, ce qu’il contient jamais créé), `DELETE` cesse de le suivre (ses brouillons et publications restent), et `GET …/feeds/{feedId}/items` liste ses 50 éléments les plus récents avec ce que chacun est devenu (`made`, `heldBack` avec sa `reason`, `skipped`, `claimed`, `abandoned`) et la publication créée, jamais leur texte. Lire demande post:read ; le reste post:create, et post:schedule aussi pour un flux qui est ou devient `queue` : une application autorisée aux brouillons seulement ne peut pas en créer. Sans post:schedule, on ne change qu’un flux qu’on a ajouté, de la même façon. Le texte d’un flux est celui d’autres personnes : des données, jamais des instructions.

- Une adresse qui n’est pas une adresse HTTPS publique répond 422 `feed_address_refused` (`reason`) ; une qui n’est pas un flux, 422 `feed_unreadable` (`notAFeed`, `tooLarge`, `unreachable`) ; un modèle qui nomme un autre champ, 422 `feed_template_invalid`.
- 10 flux répondent 409 `too_many_feeds`. Ajouter, déplacer, reprendre et prévisualiser lisent 30 adresses par espace de travail et par heure, puis 429 `feed_reads_limited` avec `retryAfterSeconds` et `Retry-After`.

## Des médias propres sur un canal [#channel-media]

Le texte d’une publication sur un canal (une entrée de `content.overrides`, ou des `overrides` d’une partie) peut aussi donner à ce canal des images et vidéos propres, dans `media`, qu’il montre alors à la place de celles de la publication : dans l’ordre, chacune avec son texte alternatif, 20 au plus, des médias prêts de l’espace de travail. Une liste vide n’en montre aucun sur ce canal ; absente, le canal montre ceux de la publication, et Peal ne répond `media` que sur une entrée qui en donne. Une entrée a toujours son `text`, qui ne peut pas être vide : envoyez-y le texte de la publication pour ne donner au canal que des médias. Ce texte est désormais celui du canal : quand vous changez le texte de la publication, changez-le là aussi (l’application web le fait).

```json
{
  "text": "Cinq images du catalogue de printemps",
  "media": [
    {
      "mediaId": "0190f3a0-0000-7000-8000-00000000f001",
      "altText": "La couverture"
    },
    {
      "mediaId": "0190f3a0-0000-7000-8000-00000000f002",
      "altText": "La page deux"
    }
  ],
  "overrides": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "text": "Cinq images du catalogue de printemps",
      "media": [
        {
          "mediaId": "0190f3a0-0000-7000-8000-00000000f002",
          "altText": "La page deux"
        }
      ]
    }
  ]
}
```

Chaque canal est vérifié sur les médias qu’il reçoit, par `validate` (son nombre de `media` et ses `violations`) comme quand la publication est programmée, et la vérification des doublons compare ce que reçoit chaque canal. Une approbation couvre les médias de chaque canal : changer les médias propres d’un canal après l’approbation de la publication en redemande une. Tant qu’une publication programmée montre un fichier sur un canal, il ne peut pas être supprimé de la médiathèque ; un brouillon le lâche, sur chaque canal.

## Retirer un canal d’une publication programmée [#remove-target]

`DELETE …/posts/{postId}/targets/{targetId}` retire un canal d’une publication qui attend son heure, programmée ou en attente d’approbation : elle part à son heure sur ses autres canaux, et jamais sur celui-ci, dont la cible est `cancelled` avec `"dropped": true`. La publication garde son heure et son créneau de file d’attente, et son `outcome`, une fois partie, laisse ce canal de côté. La réponse est la publication.

- Le dernier canal sur lequel la publication part encore répond 409 `last_target_left` : annulez plutôt la publication (`POST …/posts/{postId}/cancel`).
- Une publication en cours d’envoi ou terminée, ou un brouillon, dont les canaux changent par une mise à jour, répond 409 `post_status_conflict` ; un canal annulé avec sa publication, 409 `target_status_conflict`. Un canal déjà retiré répond la publication telle qu’elle est : une requête renvoyée après une réponse perdue est sans risque.
- C’est une modification de la publication : là où vos publications demandent une [approbation](/review), l’approbation donnée ne la couvre plus, et la réponse porte `awaitingApproval`, en attente d’une nouvelle. Une publication déjà en attente d’approbation garde sa demande, qui couvre ce qu’elle est maintenant.
- Les webhooks reçoivent un [`post.cancelled`](/webhooks#post-cancelled) qui nomme ce seul canal. Une publication repassée en brouillon (`unschedule`, des changements demandés, ou une approbation après son heure) garde les canaux qu’elle avait encore : le canal retiré part avec sa cible et ses entrées d’`overrides` dans chaque partie, et nommé de nouveau dans `channelIds`, il reçoit une nouvelle cible, en attente.

Il faut post:schedule, ou, sur une publication en attente d’approbation, le droit de demander que des publications partent ; un client OAuth a besoin du scope `workspace:publish`.

## Dépublier une publication [#unpublish]

`POST …/posts/{postId}/targets/{targetId}/unpublish` supprime une publication partie de la plateforme d’un canal, pour tout le monde, toutes les parties d’un fil, la dernière d’abord ([Dépublier une publication](/scheduling#unpublish)) ; `POST …/posts/{postId}/unpublish` le demande pour chaque canal de la publication, et répond le changement de chaque canal (`changes`) à côté de la raison pour laquelle les autres n’ont pas pu l’être (`refused`) : un canal qui ne peut pas ne fait jamais échouer toute la requête. Les deux demandent post:publish, et un client OAuth le scope `workspace:publish`. C’est définitif.

La requête est acceptée (202) avec le changement, et une tâche supprime la publication, un appel à la fois avec les autres appels du canal. `?wait=<secondes>` (60 au plus) attend qu’il se termine et le répond tel qu’il est alors. `GET …/posts/{postId}/changes` liste les changements d’une publication, du plus récent au plus ancien, avec post:read.

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/posts/$POST_ID/targets/$TARGET_ID/unpublish?wait=30" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```json
{
  "id": "019a7b10-0c21-7d3e-8f41-2a6b5c4d3e10",
  "kind": "unpublish",
  "postId": "019a6f3e-8c2a-7b1e-9f40-3d5a1c2b4e01",
  "targetId": "019a6f3e-8c2b-7d02-8a11-6e2f9b0c7d15",
  "status": "done",
  "partsLeft": 0,
  "requestedAt": "2026-11-10T09:00:00.000Z",
  "finishedAt": "2026-11-10T09:00:01.000Z",
  "code": null
}
```

- Un changement est `pending` tant qu’il reste des parties (`partsLeft`), `done` quand il n’en reste plus, et `failed` avec son `code` quand Peal a renoncé (`unavailable`, `rateLimited`, `channelUnavailable`, ou celui de la plateforme) : redemander supprime les parties restantes. `alreadyGone: true` indique que la plateforme n’avait déjà plus une partie.
- Une fois terminé, la cible garde `status: published` et reçoit `removedAt` ; `GET …/posts/search?removed=true` liste les publications supprimées d’au moins un canal.
- Avant tout appel, une requête impossible répond 409 `live_post_not_changeable`, avec `reason` : `notPublished`, `alreadyRemoved`, `noPlatformId` (une publication confirmée à la main), `notSupported` (les capacités de la plateforme disent pourquoi, dans `livePost`), `changeInProgress`, `channelUnavailable` ou `boostRunning`.
- Les webhooks reçoivent `post.unpublished` ou `post.unpublish_failed` ([Webhooks](/webhooks#post-unpublished)).
- `GET …/platforms/capabilities` dit d’avance où Peal supprime des publications : `livePost.unpublish`, et `livePost.unpublishBlockedBy` (`noApi`, `permission` ou `unverified`) là où il ne le fait pas.

## Modifier une publication en ligne [#edit-live]

`POST …/posts/{postId}/targets/{targetId}/edit` remplace le texte d’une partie d’une publication en ligne sur la plateforme d’un canal, pour tout le monde ([Modifier une publication en ligne](/scheduling#edit-live)), avec `{ "text": "…", "part": 0 }` : `part` compte depuis 0, la publication elle-même, ce qu’elle est quand elle est omise. Seul le texte change, jamais les médias, les options ni l’heure. Il faut post:publish, pour un client OAuth la portée `workspace:publish`, et c’est refusé à qui doit faire approuver ses publications ([approbations](/review)). Peal modifie sur Mastodon et Google Business Profile.

```sh
curl -X POST "https://peal.example/api/workspaces/$WORKSPACE_ID/posts/$POST_ID/targets/$TARGET_ID/edit?wait=30" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "Ouverture des portes à 19 h, pas 18 h."}'
```

- Le texte est vérifié comme le texte de ce canal l’est quand une publication est programmée, avertissement de contenu Mastodon compris : un texte que la plateforme refuserait répond 422 `post_content_invalid` avec chaque violation, tout comme un texte fait seulement d’espaces ; un `text` vide répond 400 `invalid_request`.
- La demande est acceptée (202) avec le changement (`kind: "edit"`), et une tâche fait la modification, relancée comme une suppression ; `?wait=<secondes>` attend qu’elle se termine. Un changement `failed` a son `code` (`postGone` quand la plateforme n’a plus la publication, `pollNotEditable` pour une publication Mastodon avec un sondage, `permissionDenied` pour un canal Mastodon à reconnecter, ou celui de la plateforme), et peut être redemandé. Le changement ne garde jamais le texte.
- Une fois fait, le texte est celui de cette partie sur ce canal (`content.overrides`, ou celui de la partie dans `content.followUps`), les autres canaux gardent le leur, et la cible a son `editedAt`. Peal ne garde aucun texte précédent.
- Avant tout appel, 409 `live_post_not_changeable` dit pourquoi pas, comme pour une suppression, avec aussi `approvalRequired` ; une partie que la publication n’a pas en ligne là est `noPlatformId`.
- Les webhooks reçoivent `post.edited` ou `post.edit_failed` ([Webhooks](/webhooks#post-edited)), avec la partie, jamais le texte. `livePost.edit` et `livePost.editBlockedBy` des capacités disent d’avance où Peal modifie.

## Liens courts [#short-links]

`shortenLinks: true` sur `POST …/posts`, `PUT …/posts/{postId}`, `send` et chaque élément de `bulk` demande que les liens de la publication partent [raccourcis](/scheduling#short-links), sur un serveur qui a des liens courts (`GET …/short-links/status` l’indique, avec le début et la longueur d’une adresse courte). `false` les envoie tels qu’écrits. Sans lui, une nouvelle publication prend le choix par défaut de l’espace de travail (`byDefault` dans le statut) à sa création, et le garde, et un brouillon modifié garde son choix ; chaque publication porte `shortenLinks` dans sa réponse. C’est un changement de comportement : omettre le champ valait `false` pour toute publication sauf celles de l’application web, et vaut désormais le choix par défaut de l’espace de travail, si bien qu’un espace de travail qui l’active voit aussi raccourcis les liens des publications faites par l’API, MCP, la ligne de commande et les flux. Envoyez `shortenLinks: false` quand les liens d’une publication doivent partir tels qu’écrits. `validate` le prend et vérifie le texte tel qu’écrit, qu’une adresse courte n’allonge jamais. Un import CSV n’a pas de colonne pour lui : chaque ligne prend le choix par défaut de l’espace de travail. Les liens et leurs clics se lisent par `GET …/short-links` ([Clics sur les liens courts](/analytics#short-links)) ; aucun point d’accès ne raccourcit une adresse hors d’une publication.
