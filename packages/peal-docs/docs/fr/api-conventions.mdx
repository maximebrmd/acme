Tous les points d’accès de l’[API](/api-overview) suivent les règles de cette page : un client écrit pour l’un sait traiter les autres. La [référence de l’API](/reference) dit ce que chaque point d’accès attend et répond ; cette page dit ce qu’ils ont en commun.

## Requêtes et réponses [#requests]

Les requêtes vont à l’adresse où vous ouvrez Peal, sous `/api`. Les corps sont en JSON, envoyés avec `Content-Type: application/json`, et les réponses aussi, sauf celles qui n’ont pas de corps (204).

Chaque réponse porte un en-tête `X-Request-Id`, quel que soit ce qui a répondu, et que la requête ait abouti ou non. Envoyez votre propre `X-Request-Id` et Peal le garde, s’il compte de 8 à 128 caractères parmi les lettres, les chiffres, `.`, `_`, `:` et `-` ; sinon le serveur en attribue un, un UUIDv7. Cet identifiant figure sur chaque ligne que le serveur journalise pour la requête (`peal.request_id`), dans le corps de chaque erreur (`requestId`) et dans le [journal d’activité](/settings#activity) de l’espace de travail. Journalisez-le de votre côté, et citez-le quand vous demandez de l’aide.

```bash
curl -i https://api.example.com/api/workspaces/$WORKSPACE_ID/channels \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "X-Request-Id: nightly-sync:2026-11-16:0042"
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: nightly-sync:2026-11-16:0042
RateLimit-Policy: "default";q=600;w=60
RateLimit: "default";r=599;t=42
```

L’API ne fait qu’ajouter à ce qu’elle répond ([Versions](#versioning)) : ignorez les champs, les valeurs et les erreurs que votre client ne connaît pas.

## Authentification [#authentication]

En dehors des sondes de santé, du journal des modifications et des [documents de découverte](#discovery), chaque point d’accès demande un moyen d’authentification, envoyé en `Authorization: Bearer …` :

| Moyen                   | Agit en tant que                                                        | Ce qui lui est permis                                                                                                           |
| ----------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Une clé d’API, `peal_…` | La clé elle-même, dans le seul espace de travail auquel elle appartient | Les permissions choisies à sa création, comme `post:read` ou `post:schedule` ([Clés d’API](/settings#api-keys))                 |
| Un jeton d’accès OAuth  | Le membre qui a connecté l’application                                  | Ce que le rôle du membre permet, dans la limite des scopes qu’il a accordés ([Ce que permet chaque permission](/agents#scopes)) |

Le cookie de session de l’application web est réservé à l’application web. La section [Authentification](/api-overview#authentication) de la présentation décrit chacun de ces moyens.

La référence de chaque point d’accès nomme la permission qu’il demande. Un jeton OAuth doit aussi porter le scope qui la contient : `workspace:read` pour lire, `workspace:write` pour changer quelque chose, et `workspace:publish` pour tout ce qui demande `post:schedule`.

| Statut | Code              | Quand                                                                                                              |
| ------ | ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| 401    | `unauthenticated` | Aucun moyen d’authentification, ou un moyen qui ne fonctionne plus : une clé révoquée ou expirée, un jeton périmé. |
| 403    | `forbidden`       | Le moyen fonctionne, mais ne permet pas la requête. `reason` dit pourquoi ([plus bas](#forbidden)).                |
| 404    | `not_found`       | Aucune ressource de ce nom, ou un espace de travail auquel l’appelant n’appartient pas.                            |

## Erreurs [#errors]

Chaque erreur est un objet JSON qui porte les quatre mêmes champs, puis ceux qui lui sont propres :

| Champ       | Ce qu’il contient                                                                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `code`      | Le nom de l’erreur pour les programmes, en snake case, comme `post_not_found`. Il ne change jamais une fois publié : c’est sur lui que votre code se décide.                                            |
| `_tag`      | Le même nom, tel que le lisent les clients générés depuis le contrat, comme `PostNotFound`. Il ne change jamais non plus.                                                                               |
| `message`   | Une ou deux phrases en anglais, pour la personne qui lit un journal ou un terminal. Sa formulation peut changer : ne l’analysez jamais.                                                                 |
| `requestId` | L’identifiant de la requête, tel que le donne son en-tête `X-Request-Id`.                                                                                                                               |
| les autres  | Ce que l’erreur dit d’elle-même, comme la référence le liste pour chacune : le statut (`status`) d’une publication, la limite (`limit`) atteinte par un abonnement, les `violations` d’une publication. |

Deux familles de routes répondent autrement, comme leurs propres clients l’attendent : les routes du service de connexion, sous `/api/auth`, et le [point d’accès MCP](/mcp), qui répond des erreurs JSON-RPC. Leurs réponses portent aussi `X-Request-Id`.

### Une requête illisible [#invalid-request]

Une requête qui ne correspond pas à ce que son point d’accès attend répond 400 `invalid_request`, et rien n’a été fait. `issues` liste ce qui ne va pas, 20 problèmes au plus : chacun a un chemin (`path`), qui commence par la partie de la requête concernée (`path`, `query`, `headers` ou `body`) et descend jusqu’à la valeur, et un `message`. `field` est le chemin du premier problème, séparé par des points. La lecture peut s’arrêter au premier problème : corriger ce qui est listé peut en révéler un autre.

```bash
curl -i "https://api.example.com/api/workspaces/$WORKSPACE_ID/media?limit=500" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Request-Id: 019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37
```

```json
{
  "_tag": "InvalidRequest",
  "code": "invalid_request",
  "message": "The request does not match what the endpoint takes: `issues` says what and where. Nothing was done.",
  "requestId": "019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37",
  "field": "query.limit",
  "issues": [
    {
      "path": ["query", "limit"],
      "message": "Expected a value between 1 and 100"
    }
  ]
}
```

Une valeur de la bonne forme, mais inutilisable là où elle a été envoyée, comme un curseur venu d’une autre liste, répond 400 `bad_request`.

### Une requête qui n’est pas permise [#forbidden]

Un 403 dit pourquoi dans `reason`, nomme la `permission` que la requête demande quand il en manque une, et le `scope` à demander quand c’est une application OAuth qui ne l’a pas. Son `message` dit comment obtenir ce qui manque.

| `reason`            | Pourquoi                                                                                     | Que faire                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `missingScope`      | Le membre peut le faire, mais n’a pas accordé à l’application le scope nécessaire (`scope`). | Le membre connecte de nouveau l’application et l’autorise ; `peal login` pour la ligne de commande. |
| `missingPermission` | Le rôle du membre, ou la clé d’API, n’a pas la `permission`.                                 | Un propriétaire ou un administrateur change le rôle, ou crée une clé qui la porte.                  |
| `personRequired`    | Seule une personne, dans sa propre session de l’application web, peut le faire.              | Rien qu’une clé ou une application puisse faire.                                                    |
| `wrongWorkspace`    | La clé ou le jeton appartient à un autre espace de travail.                                  | Utilisez-le là-bas, ou prenez un moyen d’authentification de cet espace de travail.                 |
| `suspended`         | Le compte est suspendu.                                                                      | Écrivez à ceux qui gèrent le serveur.                                                               |
| `untrustedOrigin`   | Un navigateur a envoyé le cookie de session depuis un autre site.                            | Envoyez plutôt une clé d’API ou un jeton OAuth.                                                     |

Un jeton auquel il manque un scope reçoit aussi, dans `WWW-Authenticate`, la demande que lisent les clients OAuth :

```bash
curl -i -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/019a6c3f-1b72-7d3c-8e90-4f5a6b7c8d02/cancel \
  -H "Authorization: Bearer $PEAL_ACCESS_TOKEN"
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
WWW-Authenticate: Bearer error="insufficient_scope", scope="workspace:publish"
X-Request-Id: 019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68
```

```json
{
  "_tag": "Forbidden",
  "code": "forbidden",
  "message": "This application was not given the scope workspace:publish (schedule and publish posts), which this request takes (permission post:schedule). Its user connects it to Peal again and allows it; for Peal's command line, run peal login again and approve it.",
  "requestId": "019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68",
  "reason": "missingScope",
  "permission": "post:schedule",
  "scope": "workspace:publish"
}
```

### Que faire d’une erreur [#handling]

| Réponse                  | Ce qu’elle signifie                                                                      | Ce que fait un client                                                                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 400                      | La requête est fausse.                                                                   | La corriger comme le disent `issues` ou `message`. Renvoyée telle quelle, elle échoue de nouveau.                                                                                          |
| 401                      | Le moyen d’authentification ne fonctionne pas.                                           | Renouveler le jeton d’accès avec le jeton de renouvellement, ou prendre une clé qui fonctionne.                                                                                            |
| 402 `plan_limit_reached` | L’abonnement de l’espace de travail n’a plus de place.                                   | Prévenir la personne : `planWithRoom` et `billingUrl` disent où aller. Ne pas réessayer.                                                                                                   |
| 403                      | Le moyen d’authentification ne le permet pas.                                            | Lire `reason`. Ne pas réessayer tant que le scope ou la permission n’est pas accordé.                                                                                                      |
| 404                      | Rien à cet endroit pour cet appelant.                                                    | Vérifier les identifiants et l’espace de travail. Ne pas réessayer.                                                                                                                        |
| 409                      | Ce sur quoi porte la requête n’est pas dans un état qui la permet.                       | Le relire, puis décider : une publication déjà programmée n’a pas besoin d’une seconde requête.                                                                                            |
| 413, 422                 | Le contenu a été refusé.                                                                 | Le corriger comme le disent les champs de l’erreur : `violations`, `channelIds`, `mediaIds`, `reason`.                                                                                     |
| 429 `too_many_requests`  | La clé ou l’application a dépassé sa [limite de débit](#rate-limits). Rien n’a été fait. | Attendre ce que dit `Retry-After`, puis renvoyer la requête.                                                                                                                               |
| 429, un autre code       | La limite d’une fonction, comme les demandes quotidiennes à l’assistant.                 | Attendre ce que dit l’erreur (`resetsAt`), ou un instant pour `media_import_busy`.                                                                                                         |
| 500 `internal_error`     | Le serveur a échoué, et l’a consigné.                                                    | Réessayer une lecture. Pour une écriture, relire d’abord ce sur quoi elle porte : elle a pu être appliquée. Ne renvoyer `posts.send` qu’avec la même `Idempotency-Key`. Citer `requestId`. |
| 502, 503                 | Le serveur, ou un service dont il a besoin, ne peut pas répondre pour l’instant.         | Réessayer quelques fois, en espaçant de plus en plus les essais, sous la même `Idempotency-Key` là où le point d’accès en accepte une.                                                     |

## Codes d’erreur [#error-codes]

Tous les codes que l’API répond, avec le statut qui les accompagne. La référence liste, pour chaque point d’accès, les erreurs qu’il déclare et leurs champs. N’importe quel point d’accès peut aussi répondre les erreurs générales : `invalid_request`, `bad_request`, `unauthenticated`, `forbidden`, `not_found`, `method_not_allowed`, `payload_too_large`, `internal_error` et `service_unavailable`. Une réponse d’un autre statut, qui ne porte aucune erreur propre, a pour code `http_` suivi du statut, comme `http_415`.

| `approval_not_pending`       | 409    | La publication n’attend pas d’approbation.                                                                                                                                              |
| `assistant_failed`           | 502    | Le modèle de langage n’a donné aucune réponse que l’assistant de rédaction puisse proposer ; `reason` dit pourquoi.                                                                     |

## Identifiants et instants [#ids]

Les identifiants sont des chaînes de caractères. Les publications, leurs cibles, les canaux et les médias ont des UUIDv7, comme `019a6c3f-1b72-7d3c-8e90-4f5a6b7c8d02` ; les espaces de travail et les utilisateurs ont des UUID aléatoires ; les clés d’API et les applications ont des identifiants d’une autre forme. Traitez chaque identifiant comme une chaîne opaque : comparez-le, stockez-le, renvoyez-le, et n’en déduisez rien. Les identifiants s’écrivent en minuscules.

### Instants et fuseaux horaires [#instants]

- Les réponses donnent les instants en ISO 8601, en UTC, comme `2026-11-16T08:00:00.000Z`. Envoyez-les de la même façon.
- Programmer demande un instant et le fuseau horaire IANA dans lequel il a été choisi, comme `Europe/Paris`, que Peal garde avec la publication. Un décalage comme `+01:00` n’est pas un fuseau horaire, et répond 422 `invalid_time_zone`.
- Une heure passée depuis une minute au plus vaut maintenant ; une heure plus ancienne répond 422 `schedule_in_past`.
- Les statistiques prennent des jours calendaires, comme `2026-11-16`, avec le fuseau horaire dans lequel ces jours s’écoulent.

## Pagination [#paging]

Les listes qui peuvent grandir sans fin se lisent page par page, les plus récents d’abord. La requête prend `limit`, la taille d’une page, et `cursor` ; la réponse est un objet qui porte les éléments de la page (`items`) et un `nextCursor`. Passez `nextCursor` en `cursor` pour lire la page suivante, et arrêtez-vous quand il vaut `null`. Un curseur est une chaîne opaque, valable pour la liste dont il vient, avec les mêmes filtres : ailleurs, il répond 400 `bad_request`.

| Liste                                    | Une page contient | Au plus |
| ---------------------------------------- | ----------------- | ------- |
| `GET …/posts/drafts`                     | 20                | 50      |
| `GET …/media`                            | 30                | 100     |
| `GET …/webhooks/{endpointId}/deliveries` | 30                | 100     |
| `GET …/activity`                         | 30                | 100     |
| `GET /api/me/notices`                    | 20                | 100     |

Les chemins qui commencent par `…` sont sous `/api/workspaces/{workspaceId}`.

## Idempotence [#idempotency]

Une requête dont la réponse s’est perdue, après un délai dépassé ou une connexion coupée, a pu être appliquée, ou non. La renvoyer ne doit pas publier deux fois.

`POST …/posts/send`, qui crée une publication et l’envoie, accepte un en-tête `Idempotency-Key` : un texte de votre choix, de 255 caractères au plus, comme un UUID, nouveau pour chaque publication.

- Dans les 24 heures, la même clé avec le même corps répond la publication créée par la première requête, dans son état du moment, sans en faire une autre.
- La même clé avec un autre corps répond 409 `idempotency_key_reused`, et ne fait rien.
- Une fois cette publication supprimée, la clé répond 404 `post_not_found`.

Les clés sont gardées par espace de travail. [Publier depuis un agent IA](/agents#api) montre une requête entière.

Les autres écritures ne prennent pas de clé. Ce que fait chacune décide si elle peut être renvoyée sans risque :

| Requête                                                                                                | Renvoyée                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Les lectures (`GET`)                                                                                   | Sans risque.                                                                                                                                                                                                                                                          |
| `PUT`, `PATCH` et `DELETE`                                                                             | Sans risque : ils mettent une ressource dans l’état que dit la requête, ou la retirent. Un second `DELETE` répond 404.                                                                                                                                                |
| Programmer, déplacer, déprogrammer ou annuler une publication, confirmer une cible                     | Sans risque : ils portent sur une seule publication, désignée par son identifiant, qui ne part qu’une fois, quel que soit le nombre de fois où elle est programmée. Une répétition ne change rien de plus, ou répond 409 avec le statut (`status`) de la publication. |
| Créer un brouillon, importer un média, ajouter un point de terminaison de webhook, créer une clé d’API | En fait un de plus. Aucune ne fait rien partir : listez ce que l’espace de travail contient avant de renvoyer, et supprimez un doublon.                                                                                                                               |
| Inviter quelqu’un                                                                                      | Remplace l’invitation en attente à cette adresse, et renvoie l’e-mail.                                                                                                                                                                                                |
| Republier une cible (`POST …/posts/{postId}/targets/{targetId}/repost`)                                | Risqué : chaque republication renvoie la publication sur ce canal. Lisez d’abord la publication : seule une cible en échec ou non confirmée peut être republiée, et toute autre répond 409 `target_status_conflict`.                                                  |

### Publications non confirmées [#unconfirmed]

Peal a le même problème avec les plateformes. Quand la réponse d’une plateforme se perd, Peal y cherche la publication là où la plateforme le permet ; quand il ne peut pas savoir si elle est partie, la cible est non confirmée (`unconfirmed`) plutôt que renvoyée, car un second essai pourrait montrer la publication deux fois. Faites de même : ne republiez jamais à l’aveugle une cible non confirmée. Demandez à quelqu’un de regarder sur la plateforme, puis enregistrez ce qu’il a trouvé avec `…/targets/{targetId}/confirm`, ou republiez ([Suivre une publication](/scheduling#follow-up)).

Chaque tentative de publication, dans `GET …/posts/{postId}/attempts`, dit comment elle a fini dans `result`, et porte dans `refusalCode` le code qui accompagne un refus : celui de la plateforme, tel qu’elle l’a donné, ou celui de Peal quand Peal a refusé avant d’appeler la plateforme ; `null` quand il n’y en a pas. Les codes des plateformes leur appartiennent et changent avec elles : affichez-les, journalisez-les, et décidez d’après `result`.

## Limites de débit [#rate-limits]

Chaque clé d’API peut envoyer 600 requêtes par minute, une [clé partenaire](/embedding) aussi, tous espaces de travail où elle agit confondus, et chaque application autant pour chaque membre au nom duquel elle agit, quel que soit celui de ses jetons d’accès qu’elle envoie. Le compte est commun à l’API et au [point d’accès MCP](/mcp), et tenu par fenêtres fixes d’une minute, qui commencent à la minute ronde. Les sessions de l’application web ne sont pas comptées. Sur votre propre serveur, `PEAL_API_REQUESTS_PER_MINUTE` fixe un autre nombre ([Variables d’environnement](/environment-variables#core)).

Chaque réponse à une clé ou à un jeton compté dit où il en est, dans les en-têtes du brouillon de l’IETF « RateLimit header fields for HTTP » :

| En-tête            | Exemple                | Ce qu’il dit                                                                                   |
| ------------------ | ---------------------- | ---------------------------------------------------------------------------------------------- |
| `RateLimit-Policy` | `"default";q=600;w=60` | La règle : `q` requêtes toutes les `w` secondes.                                               |
| `RateLimit`        | `"default";r=412;t=23` | Ce qui reste : `r` requêtes, pendant encore `t` secondes, après quoi le compte repart de zéro. |
| `Retry-After`      | `23`                   | Sur un 429 seulement : combien de secondes attendre.                                           |

Un 429 `platform_rate_limited` est autre chose : une plateforme a demandé à Peal de ralentir, comme une [recherche](/api-overview) peut le constater, et ce compte n’y est pour rien. Les pages hébergées des liens de connexion et des liens de relecture, qui ne prennent aucune clé, ont leurs propres limites par adresse.

Passé la limite, la requête répond 429 `too_many_requests`, et rien n’a été fait :

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
RateLimit-Policy: "default";q=600;w=60
RateLimit: "default";r=0;t=17
Retry-After: 17
X-Request-Id: 019a7b33-41c7-7d50-a2e9-6b8c0d1e2f3a
```

```json
{
  "_tag": "TooManyRequests",
  "code": "too_many_requests",
  "message": "This credential sent more than `limit` requests in `windowSeconds` seconds: nothing was done. Wait `retryAfterSeconds` seconds, as the `Retry-After` header says, then send the request again. Every answer to a key or a token carries the `RateLimit-Policy` and `RateLimit` headers, which say how many requests are left.",
  "requestId": "019a7b33-41c7-7d50-a2e9-6b8c0d1e2f3a",
  "limit": 600,
  "windowSeconds": 60,
  "retryAfterSeconds": 17
}
```

Attendez `retryAfterSeconds`, puis renvoyez la requête. Un client qui lit `RateLimit` ralentit avant d’être refusé. Le point d’accès MCP répond le même statut et les mêmes en-têtes, avec une erreur JSON-RPC. Quand le serveur ne parvient pas à tenir le compte, il laisse passer la requête.

Certaines fonctions ont leur propre limite, que celle-ci ne remplace pas :

| Limite                                                                     | Erreur                     | Voir                                                                   |
| -------------------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------- |
| Les demandes à l’assistant de rédaction, par espace de travail et par jour | `assistant_quota_exceeded` | [Demander de l’aide à l’assistant de rédaction](/scheduling#assistant) |
| Les imports en cours en même temps                                         | `media_import_busy`        | [Médias](/media)                                                       |
| Les événements de test et les renvois de webhooks, par heure               | `too_many_webhook_sends`   | [Le journal des livraisons](/webhooks#log)                             |
| Les invitations en attente d’un espace de travail                          | `too_many_invitations`     | [Invitations](/settings#invitations)                                   |
| Ce que permet un abonnement, sur un serveur qui facture                    | `plan_limit_reached`       | [Abonnements et facturation](/billing#limits)                          |

## Versions [#versioning]

L’API n’a pas de version dans son chemin, et n’en a qu’une : elle ne fait que grandir. Des champs, des opérations, des valeurs d’énumération et des erreurs s’ajoutent ; rien n’est renommé, retiré ni rendu plus strict. Un client écrit aujourd’hui continue de fonctionner, pourvu qu’il ignore ce qu’il ne connaît pas :

- un champ qu’il ne lit pas, dans une réponse ou dans la charge utile d’un webhook ;
- une valeur qu’il ne connaît pas, là où un champ énumère ses valeurs, comme un nouveau statut de publication ou un nouveau motif d’échec : traitez-la comme « autre chose », jamais comme un échec de décodage ;
- un code d’erreur qu’il ne connaît pas : rabattez-vous sur le statut HTTP, et affichez `message`.

Une vérification y tient l’API. Chaque changement du contrat est comparé au dernier document OpenAPI publié, celui dont les SDK ont été générés (leur version 0.3.0 aujourd’hui), et les tests du projet échouent sur tout changement qui pourrait casser un client : une opération, un champ ou une valeur retirés ou renommés, un paramètre devenu obligatoire, un type qui a changé.

Une rupture ne se fait que sur décision. Elle est alors consignée avec sa raison, listée dans le [journal des modifications](#changelog) sous `breaking`, et annoncée d’abord par une [dépréciation](#deprecations) quand un point d’accès disparaît.

Les charges utiles des webhooks suivent la même règle, avec leur propre `version` ([Versions](/webhooks#versions)).

## Dépréciations [#deprecations]

Un point d’accès déprécié continue de répondre comme il l’a toujours fait. Il le dit à trois endroits :

- le document OpenAPI marque son opération `deprecated`, ce que montrent les clients générés et les éditeurs ;
- chacune de ses réponses porte les en-têtes ci-dessous ;
- le [journal des modifications](#changelog) le liste, par opération, dans la version qui l’a déprécié.

| En-tête       | Ce qu’il dit                                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `Deprecation` | Depuis quand le point d’accès est déprécié, comme l’écrit la RFC 9745 : `@` suivi des secondes écoulées depuis 1970, comme `@1803859200`. |
| `Sunset`      | Quand il cessera de répondre, une fois que c’est décidé, sous forme de date HTTP (RFC 8594), comme `Wed, 01 Sep 2027 00:00:00 GMT`.       |
| `Link`        | Où la dépréciation est expliquée, avec ce qu’il faut appeler à la place, quand une telle page existe : `rel="deprecation"`.               |

`Sunset` et `Link` ne sont là que s’il y a quelque chose à dire : un point d’accès déprécié sans `Sunset` n’a pas de fin décidée. Faites journaliser par votre client toute réponse qui porte `Deprecation`.

Aucun point d’accès n’est déprécié aujourd’hui.

## Découverte [#discovery]

Un programme qui ne connaît que l’adresse d’un serveur Peal trouve le reste à partir de ces documents. Aucun ne demande d’authentification.

| `/.well-known/api-catalog`                  | Le catalogue d’API (RFC 9727), en `application/linkset+json` : l’API et le point d’accès MCP, chacun avec sa description, sa documentation et l’endroit où obtenir de quoi s’y authentifier. |
| `/api/openapi.json`                         | Le document OpenAPI 3.1 de l’API : chaque point d’accès, ses paramètres, ses réponses et ses erreurs.                                                                                        |
| `/api/mcp/server-card`                      | La fiche du point d’accès MCP (server card), en `application/mcp-server-card+json` : son adresse, les révisions du protocole qu’il parle et l’en-tête qui porte le moyen d’authentification. |
