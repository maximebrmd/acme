Peal sert le Model Context Protocol (MCP) : un assistant IA, ou tout autre client MCP, peut travailler dans un espace de travail pour vous : lire ses publications, médias, statistiques, facturation et membres, écrire des brouillons, programmer et publier des publications quand vous l’y autorisez, assurer le suivi des publications parties et inviter des personnes. Le client se connecte en votre nom, dans un navigateur, et agit dans le seul espace de travail que vous choisissez, sans dépasser ce que votre rôle permet. Un agent qui tourne sans personne pour le connecter se sert plutôt d’une [clé d’API](#api-key). [Publier depuis un agent IA](/agents) déroule une publication entière.

## Le point d’accès [#endpoint]

Le point d’accès est `/api/mcp`, à l’adresse où vous ouvrez Peal, comme `https://peal.example.com/api/mcp`. Il parle Streamable HTTP, dans les révisions 2026-07-28, 2025-11-25 et 2025-06-18 du protocole.

`peal mcp`, depuis la [ligne de commande](/cli#mcp), affiche le point d’accès et une configuration que la plupart des clients MCP acceptent :

```json
{
  "mcpServers": {
    "peal": {
      "type": "http",
      "url": "https://peal.example.com/api/mcp"
    }
  }
}
```

Donnez au client cette adresse, ou cette configuration, comme sa documentation l’indique pour un serveur distant en HTTP.

Avant de se connecter, un client peut lire ce dont il a besoin dans la fiche du point d’accès (server card), à `/api/mcp/server-card`, comme `https://peal.example.com/api/mcp/server-card` : l’adresse du point d’accès, les révisions du protocole qu’il parle et l’en-tête qui porte le moyen d’authentification. Elle se lit sans authentification, et depuis des pages de n’importe quelle origine ([Découverte](/api-conventions#discovery)).

## Connecter le client [#sign-in]

Peal connecte les clients MCP avec OAuth. Vous ne donnez aucune clé au client : à sa première requête, Peal lui répond qu’il lui faut un jeton, et lui indique où le demander.

1. Le client s’enregistre auprès de Peal, puis ouvre un navigateur sur la page de connexion de Peal. Connectez-vous si ce n’est pas déjà fait.
2. **Choisissez un espace de travail.** Le client n’agit que dans celui-là. Pour l’utiliser dans un autre, connectez-le de nouveau et choisissez l’autre.
3. Peal montre ce que le client demande, et où il vous renvoie ensuite. Quand il demande à publier, cette permission a sa propre ligne, avec une case que vous pouvez décocher pour ne le laisser écrire que des brouillons ([Ce que le client peut faire](#scopes)). Vérifiez les deux, puis choisissez **Autoriser**, ou **Refuser**. Peal ne vérifie pas qui a fait un client qui s’est enregistré lui-même, et le dit : n’en autorisez un que si vous lui faites confiance et avez lancé la connexion vous-même.

De retour dans le client, ses outils fonctionnent. Peal retient votre réponse pour ce client et cet espace de travail : le connecter de nouveau ne repose pas la question.

<Callout type="note" title="Si le client ne peut pas s’enregistrer">
  La plupart des clients MCP s’enregistrent eux-mêmes avant de se connecter, ce
  qu’un serveur Peal n’autorise que si son administrateur l’active
  (`MCP_DYNAMIC_REGISTRATION`, voir [Auto-hébergement](/self-hosting#mcp)).
  `peal mcp` prévient quand ce n’est pas le cas.
</Callout>

## Se connecter avec une clé d’API [#api-key]

Un agent qui tourne sur un serveur, sans personne pour le connecter, envoie la [clé d’API](/settings#api-keys) d’un espace de travail à la place d’un jeton OAuth, dans l’en-tête `Authorization` :

```json
{
  "mcpServers": {
    "peal": {
      "type": "http",
      "url": "https://peal.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer ${PEAL_API_KEY}"
      }
    }
  }
}
```

La façon dont un client lit un en-tête dans son environnement dépend du client : voyez sa documentation, et gardez la clé hors des fichiers que vous partagez. N’envoyez la clé que dans cet en-tête, jamais dans l’adresse : une adresse finit dans des journaux et des historiques.

- La connexion agit dans l’espace de travail de la clé, avec les permissions de la clé, et sans scope : une clé sans `post:schedule` écrit tout au plus des brouillons. Créez une clé qui ne porte que ce dont l’agent a besoin.
- `whoami` répond la clé dans `apiKey`, avec son identifiant et son nom, jamais la clé elle-même ; `user` et le rôle (`role`) de l’espace de travail valent `null`, car une clé n’est personne, et `permissions` liste ce que la clé peut faire.
- Les outils réservés à une personne refusent une clé : `list_members`, `list_invitations`, `invite_member` et `revoke_invitation`.
- Ce que fait la clé figure dans le [journal d’activité](/settings#activity) de l’espace de travail, sous l’identifiant et le nom de la clé.
- Révoquer la clé, sous **Clés d’API** dans les paramètres de l’espace de travail, arrête l’agent aussitôt.

## Ce que le client peut faire [#scopes]

La page de consentement liste ce que le client demande :

| Permission                                                                                                                                 | Scope               | Ce qu’elle permet                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Savoir que c’est vous                                                                                                                      | `openid`            | L’identifiant de votre compte                                                                                                                                                                                |
| Voir votre nom et votre photo, voir votre adresse e-mail                                                                                   | `profile`, `email`  | Votre profil                                                                                                                                                                                                 |
| Rester connectée en votre absence, jusqu’à ce que vous la déconnectiez                                                                     | `offline_access`    | Renouveler son accès sans vous                                                                                                                                                                               |
| Lire l’espace de travail : publications, canaux, médias et statistiques                                                                    | `workspace:read`    | Lire, sans rien changer                                                                                                                                                                                      |
| Faire ce que votre rôle permet dans l’espace de travail, comme rédiger des brouillons et gérer les médias, sans rien programmer ni publier | `workspace:write`   | Tout ce que votre [rôle](/scheduling#roles) permet, lecture comprise, sauf ce qui fait partir des publications : rien de ce qu’il fait n’atteint une plateforme                                              |
| L’autoriser à programmer et publier des publications sur vos comptes connectés, où tout le monde peut les voir                             | `workspace:publish` | Ce que votre rôle permet de ce qui fait partir des publications, et la lecture : programmer, déplacer, publier et republier une publication, la déprogrammer, l’annuler, et confirmer ce qu’elle est devenue |

Publier est une permission à part. La page de consentement la montre sur sa propre ligne, avec une case cochée au départ : décochez-la, et le client reçoit le reste de ce qu’il a demandé, sans plus. Sans elle, un client qui peut écrire rédige toujours des brouillons, que vous relisez et programmez vous-même ; un client qui ne peut que lire lit toujours.

Un client connecté avant que publier ait sa propre permission n’a que celle d’écrire : il ne publie rien, et ne déprogramme, ne republie ni ne confirme plus rien, tant que vous ne l’avez pas connecté de nouveau en autorisant la publication. Une connexion garde jusque-là les permissions qu’elle a reçues.

Un client qui n’a aucune des trois permissions sur l’espace de travail ne peut rien faire. Son accès dure 15 minutes à la fois, et le client le renouvelle de lui-même. Chaque requête vérifie que vous appartenez toujours à l’espace de travail et n’êtes pas banni.

## Outils [#tools]

Chaque outil agit en votre nom, dans l’espace de travail où le client s’est connecté, avec les mêmes vérifications que l’application web : votre rôle décide de ce qu’il peut faire, et un client se voit refuser ce que vous ne lui avez pas permis, avec un message qui nomme la permission manquante : tout changement pour un client autorisé à lire seulement, et tout ce qui fait partir des publications pour un client que vous n’avez pas autorisé à publier. Pour lui en donner plus, connectez-le de nouveau et autorisez-le à ce moment-là.

« Demande la publication » : il faut la permission de programmer et publier (`workspace:publish`), et un rôle qui programme des publications : propriétaire, administrateur ou éditeur. Ce qu’envoient `schedule_post`, `publish_post`, `create_post`, `create_posts` et `repost_target` est public sur les plateformes, et Peal ne peut pas le reprendre une fois parti.

Avant d’être programmée, une publication est vérifiée contre la plateforme de chaque canal : longueur du texte, types, tailles et nombre de médias, options requises, et ce que le compte lui-même refuse. Si quelque chose ne va pas, rien n’est programmé, et le refus liste toutes les violations d’un coup, chacune avec son canal, et son champ ou son média ([Comment lire les refus](/agents#refusals)). `validate_post` répond la même liste à l’avance, sans rien créer.

`create_post` et `create_posts` refusent aussi une publication dont le contenu (le texte que reçoit le canal et les mêmes médias, dans le même ordre) part déjà sur l’un de ses canaux à moins de 23 heures de son heure, en nommant la publication qui l’a déjà : un appel fait deux fois par erreur ne crée pas de seconde publication. `allowDuplicate: true` la laisse passer, quand vous voulez vraiment publier deux fois la même chose. Programmer un brouillon avec `schedule_post` n’est pas vérifié ([Publications en double](/posting-api#duplicates)).

Les annotations sont des indications qu’un client peut vous montrer ; les vérifications de droits sont celles du serveur.

Chaque outil est écrit à la main, avec la description de ce qu’il change ; aucun n’est généré à partir d’un point d’accès de l’API, et l’API a des points d’accès qu’aucun outil n’appelle. Un client qui préfère ne pas lire toutes les descriptions appelle d’abord `find_tools`, puis ne lit que les outils qu’il a retenus.

### Ce qu’aucun outil ne donne [#account-data]

Aucun outil n’exporte vos données ni ne liste les applications qui agissent pour vous. Un client MCP transmet tout ce que ses outils répondent à un modèle d’IA, et votre export contient les adresses de vos sessions, vos invitations et tout ce que vous avez écrit : l’instance refuse les deux à tout client OAuth autre que la [ligne de commande](/cli#account), que vous connectez depuis votre propre terminal et qui les enregistre dans vos propres fichiers. Les paramètres du compte, dans l’application web, les montrent aussi.

## Limites [#limits]

- Une instance Peal ne sert les clients MCP que si son adresse est en HTTPS, ou sur `localhost` pour le développement. Ailleurs, le point d’accès refuse toutes les requêtes.
- Le point d’accès refuse les requêtes envoyées depuis des pages web (avec un en-tête `Origin`) : connectez un client qui tourne sur votre ordinateur ou sur un serveur.
- Une connexion peut envoyer 600 requêtes par minute, comptées avec celles que la même clé ou la même application envoie à l’API. Au-delà, le point d’accès répond 429 avec un en-tête `Retry-After` ([Limites de débit](/api-conventions#rate-limits)).
- Chaque réponse porte un en-tête `X-Request-Id` : citez-le quand vous demandez de l’aide ([Requêtes et réponses](/api-conventions#requests)).
- Les **Paramètres du compte**, dans l’application web, listent les clients que vous avez autorisés et les déconnectent ; `peal account apps` les liste depuis la [ligne de commande](/cli#account). Quitter l’espace de travail arrête tous les clients qui y agissent.
