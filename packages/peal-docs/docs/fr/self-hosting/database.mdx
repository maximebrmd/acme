Peal garde ses données et ses tâches durables dans une seule base Postgres, que nomme `DATABASE_URL`. Le serveur tient lui-même son schéma à jour.

## Base de données [#database]

Au démarrage, le serveur applique les migrations de la base de données qu’il n’a pas encore appliquées, un serveur à la fois, et n’écoute qu’une fois qu’elles sont terminées. Chaque partie de Peal range ses tables dans un schéma Postgres à elle (`assistant`, `auth`, `channels`, `legal`, `media`, `notifications`, `publishing`) ; les tables de l’exécuteur de tâches (`cluster_*`) sont dans `public`. Les migrations créent l’extension `pg_trgm`, que lit la recherche de la médiathèque : elle est livrée avec PostgreSQL et, en tant qu’extension de confiance, le propriétaire de la base de données peut la créer. Sur un Postgres géré, connectez-vous en tant que propriétaire de la base, ou créez-la une fois au préalable (`CREATE EXTENSION pg_trgm;`). Ses classes d’opérateurs doivent être accessibles par le chemin de recherche du rôle qui migre : quand le fournisseur range les extensions dans un schéma à part (comme `extensions`), ajoutez ce schéma au `search_path` du rôle (`ALTER ROLE … SET search_path = "$user", public, extensions;`) avant de démarrer le serveur, sinon la migration s’arrête sur « operator class gin_trgm_ops does not exist ».

Les nettoyages des médias lisent sur quel cluster Postgres tourne la base (`pg_control_system()`, et la timeline depuis `pg_walfile_name(pg_current_wal_lsn())`), pour distinguer une base restaurée de celle qu’elle était ([À quelle base appartient le dossier](/self-hosting/storage#media-owner)). PostgreSQL tel quel laisse tout rôle les appeler. Un Postgres géré qui les refuse fait échouer les deux nettoyages qui suppriment à chaque passage, sans rien supprimer, et l’alerte `peal-media-sweep-failing` se déclenche. Un clone ou une branche d’un fournisseur qui garde l’identifiant système et la timeline n’est vu que par l’époque des nettoyages : donnez à un clone un préfixe de médias à lui.

Le serveur exécute ses tâches durables depuis la même base, et les garde par des verrous consultatifs de session tant qu’il tourne.

<Callout type="warning" title="Pas de pooler en mode transaction">
  Connectez le serveur à Postgres directement, ou par un pooler en mode session.
  Un pooler en mode transaction donne une autre connexion à chaque requête, ce
  qui perd ces verrous.
</Callout>

| Réglage                  | Par défaut | Ce qu’il fait                                                                                                                              |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL`           | aucune     | La base Postgres. Chaque processus serveur y ouvre jusqu’à 10 connexions.                                                                  |
| `AUTH_DB_POOL_MAX`       | `5`        | Les connexions que chaque processus serveur ouvre en plus, pour la connexion des utilisateurs.                                             |
| `PEAL_CLUSTER_RETENTION` | `30 days`  | Un nettoyage quotidien supprime les traces des tâches terminées depuis plus longtemps. Les tâches encore en attente sont toujours gardées. |

[Variables d’environnement](/self-hosting/environment-variables#core) détaille chacun, `AUTH_DB_POOL_MAX` sous [Connexion](/self-hosting/environment-variables#sign-in).
