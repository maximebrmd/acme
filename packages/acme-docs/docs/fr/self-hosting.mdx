Acme accède à chaque service extérieur par un port doté d’une option par défaut auto-hébergeable. Une instance auto-hébergée fait tourner deux programmes à elle, le serveur et l’application web, et a besoin de Postgres, d’un stockage objet compatible S3 et d’un moyen d’envoyer des e-mails. Tout le reste est facultatif et reste désactivé tant que vous ne le configurez pas.

<Callout type="warning" title="Avant la première version">
  Acme n’est pas encore sorti et aucune image n’est publiée : construisez-les
  depuis le dépôt, comme le montre [Avec Docker Compose et Caddy](#compose).
  Cette page décrit le modèle d’auto-hébergement que suit le code, et toutes les
  valeurs indiquées sont des exemples.
</Callout>

## Services [#services]

| Service        | Requis     | Usage dans Acme                                                                                                                                     | Options                                                                                                            |
| -------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Postgres       | Oui        | Toutes les données, et les tâches durables qui diffusent les publications et renouvellent les jetons des plateformes. Acme n’a pas besoin de Redis. | N’importe quel serveur Postgres                                                                                    |
| Stockage objet | Oui        | Médias importés                                                                                                                                     | N’importe quelle API compatible S3                                                                                 |
| E-mail         | Oui        | Confirmer les adresses e-mail, réinitialiser les mots de passe, inviter, et envoyer les notifications sur les publications et les canaux            | Resend, ou n’importe quel serveur SMTP                                                                             |
| Facturation    | Facultatif | Offres et abonnements                                                                                                                               | Stripe. Sans clé, la facturation est désactivée et aucune limite d’offre ne s’applique.                            |
| Captcha        | Facultatif | Protection contre les robots à l’inscription et à la réinitialisation du mot de passe                                                               | Cloudflare Turnstile. Sans ses clés, le captcha est désactivé.                                                     |
| IA             | Facultatif | L’assistant de rédaction de l’éditeur                                                                                                               | L’API d’Anthropic, ou n’importe quel point d’accès compatible OpenAI. Sans fournisseur, l’assistant est désactivé. |
| Télémétrie     | Facultatif | Journaux, métriques et traces                                                                                                                       | N’importe quel collecteur OpenTelemetry (OTLP). Rien n’est exporté sans point d’accès configuré.                   |

Le déploiement d’Acme stocke les médias sur Cloudflare R2, et son environnement de développement utilise SeaweedFS pour le stockage et Mailpit pour l’e-mail. Une instance auto-hébergée peut utiliser ceux-ci, ou tout autre stockage et serveur de messagerie qui parle les mêmes protocoles.

## Ce qu’il faut faire tourner [#run]

- **Le serveur** (`acme-server`) : l’API HTTP sous `/api`, la connexion sous `/api/auth`, le point d’accès MCP à `/api/mcp`, et les tâches qui diffusent les publications, envoient les notifications par e-mail et renouvellent les jetons. Son image écoute sur le port 3000 et tourne sous un utilisateur sans privilèges.
- **L’application web** (`acme-web`) : toutes les pages, sur Node. Elle transmet `/api/*` et les documents de découverte OAuth (`/.well-known/oauth-*`) au serveur, à `ACME_API_URL` : les personnes, la ligne de commande et les clients MCP utilisent tous une seule adresse, `PUBLIC_URL`.

Faites tourner un seul processus serveur par instance : les clients MCP des anciennes révisions du protocole gardent leurs sessions dans sa mémoire. Chaque processus qui tourne a besoin de son propre `HOSTNAME`.

En production (`NODE_ENV=production`, que l’image du serveur définit), le serveur refuse de démarrer sans ces variables, et son erreur nomme celle qui manque :

| Variable                                                                                   | Ce que c’est                                                   |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `DATABASE_URL`                                                                             | La base de données Postgres                                    |
| `PUBLIC_URL`                                                                               | L’adresse où l’on ouvre Acme, comme `https://acme.example.com` |
| `BETTER_AUTH_SECRET`                                                                       | Le secret qui signe les sessions : `openssl rand -base64 32`   |
| `AUTH_IP_HEADERS`                                                                          | L’en-tête où votre frontal met l’adresse du client             |
| `MAIL_FROM`, et `SMTP_URL` ou `RESEND_API_KEY`                                             | L’expéditeur des e-mails, et le moyen de les envoyer           |
| `ACME_S3_ENDPOINT`, `ACME_S3_BUCKET`, `ACME_S3_ACCESS_KEY_ID`, `ACME_S3_SECRET_ACCESS_KEY` | Le stockage des médias                                         |

L’application web a besoin de `ACME_API_URL`. Pour connecter des canaux, le serveur a aussi besoin de `ACME_TOKEN_KEYS`. [Variables d’environnement](/environment-variables) liste chaque réglage, avec sa valeur par défaut.

## Avec Docker Compose et Caddy [#compose]

Le dossier `packages/acme-docker` du dépôt contient une pile à faire tourner telle quelle. `compose.production.yaml` fait tourner Postgres, le serveur, l’application web et une pile de télémétrie (un collecteur OpenTelemetry, Loki, Tempo, Prometheus et Grafana), chacun redémarré s’il s’arrête, avec chaque port sur `127.0.0.1`. `compose.self-host.yaml` place Caddy devant eux : il obtient un certificat auprès de Let’s Encrypt, et c’est le seul service joignable de l’extérieur, sur les ports 80 et 443.

1. Faites pointer votre domaine vers le serveur dans le DNS, et ouvrez les ports 80 et 443.
2. Copiez `self-host.env.example` hors du dépôt, par exemple vers `/srv/acme/acme.env`, ne laissez que root le lire, et remplissez-le : le domaine, les secrets qu’il dit comment générer, l’e-mail et le stockage des médias.
3. Depuis `packages/acme-docker`, construisez les images, puis démarrez la pile :

```sh
docker compose --project-name acme --file compose.production.yaml \
  --file compose.self-host.yaml --env-file /srv/acme/acme.env build
docker compose --project-name acme --file compose.production.yaml \
  --file compose.self-host.yaml --env-file /srv/acme/acme.env up --detach --wait
```

Le serveur applique ses migrations au démarrage : une mise à jour, c’est une extraction plus récente du dépôt et les deux mêmes commandes. Compose laisse au serveur ses 75 secondes pour s’arrêter.

Caddy (`self-host/Caddyfile`) envoie `/api/*` et `/.well-known/oauth-*` au serveur et tout le reste à l’application web, et attend une réponse 150 secondes, plus longtemps que l’assistant de rédaction et la transmission de l’application web. Définissez `AUTH_IP_HEADERS=x-forwarded-for`, comme le fait le fichier d’exemple.

Grafana n’écoute que sur `127.0.0.1:13000` : joignez-le par un tunnel SSH, comme `ssh -L 13000:127.0.0.1:13000 vous@votre-serveur`, et connectez-vous en `admin` avec `GRAFANA_ADMIN_PASSWORD`. Ses règles d’alerte sont fournies, et ne préviennent personne tant que vous n’ajoutez pas de point de contact.

Pour sauvegarder la base de données, définissez `ACME_POSTGRES_ARCHIVE_MODE=on` et les réglages `PGBACKREST_REPO1_*` que liste le fichier d’exemple. Postgres archive alors ses journaux de transactions (WAL) dans ce bucket avec pgBackRest, que fournit l’image Postgres de la pile. Créez le dépôt de sauvegarde une fois avec `docker compose … exec --user postgres postgres pgbackrest stanza-create`, puis lancez les sauvegardes à intervalles réguliers avec `… pgbackrest backup --type=full`. Les serveurs d’Acme le font avec l’Ansible de `packages/acme-infra`, dont le README et la procédure de restauration montrent chaque commande. [Variables d’environnement](/environment-variables#compose) liste les réglages de la pile.

## Devant Acme [#reverse-proxy]

Placez devant l’application web un proxy inverse qui termine TLS, comme Caddy, et n’exposez que le proxy. Envoyez toutes les requêtes à l’application web, qui transmet les chemins du serveur, ou envoyez `/api/*` et `/.well-known/oauth-*` directement au serveur et tout le reste à l’application web.

La connexion est limitée en débit par adresse du client, que le serveur lit dans l’en-tête que nomme `AUTH_IP_HEADERS`. Ne nommez qu’un en-tête que votre frontal définit en remplaçant ce que le client a envoyé :

- derrière Cloudflare, `cf-connecting-ip` ;
- derrière Caddy, qui remplace `X-Forwarded-For` sauf si on lui dit de faire confiance aux proxies placés avant lui, `x-forwarded-for` ;
- derrière des proxies qui ajoutent à `X-Forwarded-For`, `x-forwarded-for`, avec leurs adresses dans `AUTH_TRUSTED_PROXIES`, pour que l’adresse du client soit lue depuis la droite, après eux.

L’application web transmet ces en-têtes tels qu’ils arrivent : sans proxy devant elle, aucune adresse n’est fiable, et les limites ne distinguent pas les clients.

Laissez les requêtes durer au moins 90 secondes à travers tout ce qui sépare les navigateurs du serveur, tunnel compris : l’assistant de rédaction attend jusque-là son fournisseur d’IA. L’application web, quand elle transmet `/api/*`, attend jusqu’à 120 secondes.

Le serveur répond à deux sondes :

- `GET /api/health` répond `204 No Content` dès que le serveur a démarré, quel que soit l’état de sa base de données, ce qui convient à un contrôle de santé de conteneur. L’image du serveur l’utilise.
- `GET /api/ready` répond `204 No Content` quand la base de données répond elle aussi, et `503 Service Unavailable` avec une erreur `DatabaseUnavailable` sinon : un répartiteur de charge peut ainsi retenir le trafic jusque-là.

## Base de données [#database]

Au démarrage, le serveur applique les migrations de la base de données qu’il n’a pas encore appliquées, un serveur à la fois, et n’écoute qu’une fois qu’elles sont terminées. Chaque partie d’Acme range ses tables dans un schéma Postgres à elle (`assistant`, `auth`, `channels`, `media`, `notifications`, `publishing`) ; les tables de l’exécuteur de tâches (`cluster_*`) sont dans `public`.

Le serveur exécute ses tâches durables depuis la même base, et les garde par des verrous consultatifs de session tant qu’il tourne. Connectez-le à Postgres directement, ou par un pooler en mode session : un pooler en mode transaction donne une autre connexion à chaque requête, ce qui perd ces verrous. Chaque processus serveur ouvre jusqu’à 10 connexions, et jusqu’à 5 de plus pour la connexion des utilisateurs (`AUTH_DB_POOL_MAX`).

Un nettoyage quotidien supprime les traces des tâches terminées depuis plus de 30 jours (`ACME_CLUSTER_RETENTION`). Les tâches encore en attente sont toujours gardées.

## Arrêt [#stopping]

À l’arrêt, le serveur attend jusqu’à 60 secondes que les appels en cours aux plateformes répondent. Laissez-lui au moins 75 secondes avant de l’interrompre, avec `docker stop --time 75` ou `stop_grace_period: 75s` dans Compose. Un appel coupé est vérifié au redémarrage du serveur : sur Bluesky en relisant la publication, sur Mastodon en la renvoyant sous la même clé, que Mastodon garde une heure. Quand cela ne tranche pas, la publication est marquée à vérifier, et quelqu’un doit regarder sur la plateforme.

## E-mail [#email]

Définissez `MAIL_FROM`, l’expéditeur, comme `Acme <noreply@example.com>` ou une adresse depuis laquelle votre service de messagerie peut envoyer, et un moyen d’envoi :

- `RESEND_API_KEY`, pour envoyer par l’API de Resend ;
- sinon `SMTP_URL`, comme `smtp://utilisateur:motdepasse@mail.example.com:587`, ou `smtps://…:465` pour du TLS dès le premier octet.

Acme envoie l’e-mail qui confirme une adresse, les réinitialisations de mot de passe, les invitations à un espace de travail, et les [notifications](/notifications) sur les publications et les canaux, chacun dans la langue du lecteur. Les membres choisissent quelles notifications leur arrivent aussi par e-mail. Quand le service de messagerie refuse un e-mail pour le moment, un e-mail de compte est réessayé quelques secondes, puis abandonné, car on peut en demander un autre ; l’e-mail d’une notification est réessayé pendant environ cinq heures. Avec `AUTH_REQUIRE_EMAIL_VERIFICATION=false`, on peut se connecter avant d’avoir confirmé son adresse.

## Stockage des médias [#media-storage]

Les navigateurs envoient les médias directement au bucket, avec des requêtes que le serveur signe : le bucket doit donc laisser l’origine de l’application web les envoyer. Il lui faut une règle CORS qui autorise `PUT` depuis cette origine, avec les en-têtes `Content-Type` et `If-None-Match`. Avec les variables du serveur définies, et `PUBLIC_URL` et `TRUSTED_ORIGINS` nommant les origines de l’application web, cette commande pose la règle sur le bucket, en gardant ses autres règles, puis affiche la même politique pour le tableau de bord de Cloudflare R2 (R2 › le bucket › Settings › CORS policy) :

```sh
bun nx run acme-server:media-cors
```

La relancer ne change rien. Sa clé d’accès doit pouvoir modifier les réglages du bucket ; celle du serveur n’a besoin que de lire et d’écrire des objets.

Les grandes vidéos partent en plusieurs morceaux. Un import laissé inachevé garde ses morceaux dans le stockage : ajoutez une règle de cycle de vie qui abandonne les envois en plusieurs parties inachevés après un jour, si votre stockage le permet.

Une fois un fichier stocké, le serveur le lit : les dimensions d’une image avec sharp, les dimensions, la durée et le codec d’une vidéo avec ffprobe, que l’image du serveur contient. Une vidéo importée sur un serveur sans ffprobe reste importée, marquée comme non lue, jusqu’à ce qu’elle soit complétée à nouveau sur un serveur qui en dispose.

Les pages montrent les médias par des liens signés de courte durée. Si le bucket est aussi servi publiquement, par exemple par un domaine personnalisé R2, mettez cette adresse dans `ACME_MEDIA_PUBLIC_BASE_URL`, et les liens vers les médias l’utilisent à la place.

## Canaux [#channels]

Le serveur chiffre les jetons des comptes connectés avec les clés de `ACME_TOKEN_KEYS`. Sans elle, le serveur démarre, et la connexion d’un compte échoue. Créez une clé avec :

```sh
echo "k1:$(openssl rand -base64 32)"
```

La valeur liste des entrées `idDeClé:clé` séparées par des virgules, comme `k2:<clé>,k1:<clé>`. La première clé chiffre et toutes les clés listées déchiffrent : pour en changer, placez une nouvelle clé en tête et gardez les anciennes. Une valeur mal formée arrête le serveur au démarrage. Gardez les clés secrètes, et gardez-en une copie : sans elles, chaque canal doit être reconnecté.

Le serveur joint lui-même les plateformes, en HTTPS : il doit donc accéder à Internet, pour connecter des comptes et pour publier, sur le serveur Mastodon de chaque compte, sur le serveur Bluesky qui héberge chaque compte, par le service vidéo de Bluesky, `https://video.bsky.app`, pour les vidéos, sur LinkedIn (`www.linkedin.com`, `api.linkedin.com` et les adresses d’envoi que LinkedIn donne), sur X (`api.x.com`) et sur les API de Meta. Il n’appelle que des serveurs aux adresses publiques, sur le port HTTPS par défaut, ce qui empêche de le diriger vers votre réseau privé. Les plateformes renvoient les personnes vers `PUBLIC_URL/connect/<plateforme>/callback`, par leur navigateur : elles n’appellent jamais le serveur elles-mêmes, sauf Bluesky, qui lit la description du client d’Acme, et les demandes de suppression de données de Meta, ci-dessous.

Pour publier une image ou une vidéo, le serveur la lit dans le stockage des médias, en entier, en mémoire, puis l’envoie : une vidéo Bluesky peut prendre jusqu’à 300 Mo. LinkedIn et X prennent les vidéos par parties de 4 Mio : le serveur n’en garde qu’une à la fois. Donnez au serveur la mémoire nécessaire aux plus gros fichiers que publient vos membres.

### Bluesky [#bluesky]

Un serveur en production ne connecte des comptes Bluesky qu’avec des clés à lui, qui l’identifient auprès de Bluesky. `PUBLIC_URL` doit être en HTTPS, sans port. Créez une clé, depuis le dépôt :

```sh
bun nx run acme-server:bluesky-key
```

Mettez la ligne qu’elle affiche dans `BLUESKY_CLIENT_KEYS`. Les entrées sont séparées par des virgules : pour en changer, placez une nouvelle clé en tête, et gardez les anciennes jusqu’à ce que les sessions qu’elles ont signées aient été rafraîchies. Bluesky lit la description du client d’Acme à `PUBLIC_URL/api/channels/oauth/bluesky/client-metadata.json`, et ses clés publiques à côté.

Sans clés, un serveur lancé depuis les sources sur `localhost` utilise le client de développement de Bluesky, dont les sessions durent deux semaines, et tout autre serveur ne peut pas connecter Bluesky.

### LinkedIn [#linkedin]

Un serveur connecte des membres LinkedIn une fois que vous lui avez enregistré une application sur le portail développeurs de LinkedIn, qui demande une page LinkedIn pour la détenir :

1. Ajoutez les produits **Sign In with LinkedIn using OpenID Connect** et **Share on LinkedIn**. Les deux sont accordés tout de suite, sans examen.
2. Sous **Auth**, ajoutez `PUBLIC_URL/connect/linkedin/callback` comme URL de redirection autorisée, comme `https://acme.example.com/connect/linkedin/callback`.
3. Mettez l’identifiant client de l’application dans `LINKEDIN_CLIENT_ID` et son secret client principal dans `LINKEDIN_CLIENT_SECRET`.

Ces applications n’obtiennent pas de jeton de rafraîchissement : les membres reconnectent leur canal tous les 60 jours, et en sont prévenus une semaine avant. Acme appelle l’API de LinkedIn dans la version que nomme `LINKEDIN_API_VERSION`, une version récente si elle n’est pas définie ; LinkedIn retire chaque version un an après sa sortie, et une version retirée fait échouer chaque publication.

### X [#x]

Un serveur connecte des comptes X une fois que vous lui avez enregistré une application dans la console développeurs de X :

1. Dans les réglages d’authentification des utilisateurs de l’application, activez OAuth 2.0, comme **Web App, Automated App or Bot**, avec les permissions **Read and write**.
2. Ajoutez `PUBLIC_URL/connect/x/callback` comme URI de rappel, exactement, comme `https://acme.example.com/connect/x/callback`. X refuse `localhost` : en développement, utilisez `http://127.0.0.1` et son port.
3. Mettez l’identifiant client OAuth 2.0 dans `X_CLIENT_ID` et son secret client dans `X_CLIENT_SECRET`.

X facture chaque requête de l’API à l’application, et une publication avec un lien coûte plus. Fixez une limite de dépenses dans la console de X : une fois atteinte, X refuse les publications, qui échouent avec leur raison, jusqu’à ce que vous la releviez. Acme renouvelle l’accès de chaque compte toutes les deux heures, et le garde valable tant qu’il est renouvelé.

Pour LinkedIn comme pour X, l’un des deux réglages sans l’autre arrête le serveur au démarrage ; sans les deux, **Canaux** ne propose pas la plateforme.

### Threads, Instagram et Pages Facebook [#meta]

Une application du tableau de bord des développeurs de Meta connecte les trois. Donnez-lui le cas d’usage Facebook Login, avec les autorisations `pages_show_list`, `pages_read_engagement` et `pages_manage_posts` pour les Pages Facebook, et `instagram_basic` et `instagram_content_publish` pour Instagram ; et le cas d’usage Threads, avec `threads_basic` et `threads_content_publish`. Définissez ensuite `META_APP_ID` et `META_APP_SECRET` d’après les paramètres de base de l’application, et `THREADS_APP_ID` et `THREADS_APP_SECRET` d’après ses paramètres Threads. Une plateforme dont les paramètres manquent n’est pas proposée.

Dans le tableau de bord, enregistrez ces adresses :

| Paramètre                                          | Adresse                                                                                         |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| URI de redirection OAuth valides de Facebook Login | `PUBLIC_URL/connect/facebook/callback` et `PUBLIC_URL/connect/instagram/callback`               |
| URL de rappel de redirection de Threads            | `PUBLIC_URL/connect/threads/callback`                                                           |
| URL de demande de suppression des données          | `PUBLIC_URL/api/data-deletion/facebook`, et `PUBLIC_URL/api/data-deletion/threads` pour Threads |

Quand l’une de ses utilisatrices ou l’un de ses utilisateurs demande à Meta de supprimer ce qu’Acme détient sur elle ou lui, Meta appelle cette adresse avec une demande signée avec le secret de l’application. Acme vérifie la signature, supprime, dans chaque espace de travail, les canaux que la personne a connectés et leurs jetons, et répond avec un code de confirmation et la page où s’affiche son état, `PUBLIC_URL/data-deletion/<code>`. La même demande envoyée à nouveau, comme Meta peut la renvoyer, reçoit la même réponse et ne supprime rien de plus.

Meta va chercher les images et vidéos qu’il publie par des liens vers le stockage des médias, valables deux heures : le stockage doit répondre aux serveurs de Meta sur Internet, par des liens présignés ou `ACME_MEDIA_PUBLIC_BASE_URL`. Le serveur appelle `graph.facebook.com` et `graph.threads.com`, et signe chaque appel à Facebook et Instagram avec le secret de l’application : vous pouvez activer **Exiger la clé secrète** dans les paramètres avancés de l’application.

Tant que l’application est en mode développement, seules les personnes qui y ont un rôle peuvent connecter leurs comptes : ajoutez-vous, ainsi que les testeurs Threads, sous Rôles de l’application. Servir d’autres personnes demande l’examen par Meta de chaque autorisation. Les comptes Instagram doivent être des comptes professionnels liés à une Page Facebook.

### YouTube [#youtube]

Un serveur connecte des chaînes YouTube une fois que vous lui avez créé un client OAuth dans un projet Google Cloud :

1. Dans la console Google Cloud, créez un projet, et activez la **YouTube Data API v3** sous API et services.
2. Sous **Google Auth Platform**, configurez l’écran de consentement pour des utilisateurs **Externes**, et ajoutez les champs d’application `https://www.googleapis.com/auth/youtube.upload` et `https://www.googleapis.com/auth/youtube.readonly`.
3. Sous **Clients**, créez un client **Application Web**, avec `PUBLIC_URL/connect/youtube/callback` comme URI de redirection autorisée, comme `https://acme.example.com/connect/youtube/callback`.
4. Mettez l’identifiant client dans `YOUTUBE_CLIENT_ID` et son secret dans `YOUTUBE_CLIENT_SECRET`.

L’un des deux réglages sans l’autre arrête le serveur au démarrage ; sans les deux, **Canaux** ne propose pas YouTube. Les membres se connectent avec Google et choisissent la chaîne, celle d’un compte de marque comprise, dans le sélecteur de comptes de Google : une connexion est une chaîne. Acme demande à mettre en ligne des vidéos et à lire la chaîne et ses vidéos, rien de plus, et renouvelle son accès toutes les heures. Déconnecter une chaîne révoque cet accès chez Google, sauf si un autre espace de travail connecte encore la même chaîne.

Tant que l’écran de consentement du projet est en **Test**, seuls les utilisateurs test que vous listez peuvent se connecter, et Google met fin à leur accès sept jours après la connexion : leurs chaînes doivent alors être reconnectées, et Acme prévient l’espace de travail. Publiez l’écran de consentement, et faites vérifier l’application par Google pour ses champs d’application, pour servir tout le monde durablement.

Le serveur appelle `oauth2.googleapis.com` et `www.googleapis.com`, et y envoie chaque vidéo par parties de 8 Mio, en n’en gardant qu’une à la fois ; un envoi coupé, même par un redémarrage, reprend là où en est YouTube. Les mises en ligne puisent dans le quota **Video Uploads** du projet, 100 par jour sauf si Google en accorde plus, qui repart à minuit, heure du Pacifique : Acme les compte pour tout le serveur, et une mise en ligne au-delà de `YOUTUBE_DAILY_UPLOADS`, ou que YouTube refuse pour son quota ou la limite quotidienne de la chaîne, attend le jour suivant. Le suivi du traitement et les statistiques puisent dans l’autre quota du projet, 10 000 unités par jour.

Jusqu’en novembre 2026, Google gardait privées les vidéos des projets d’API qu’il n’avait pas audités. Il ne le fait plus, mais les réglages d’une chaîne ou les restrictions de Google peuvent encore garder une vidéo privée : Acme compare la réponse de YouTube à la visibilité choisie par le membre, et le dit sur la page de la publication.

## Assistant de rédaction [#ai]

L’assistant de rédaction de l’éditeur réécrit une publication sur un ton, la raccourcit pour une plateforme, la traduit ou suggère des hashtags. Il est désactivé tant que `ACME_AI_PROVIDER` ne nomme pas de fournisseur : d’ici là, l’application web le masque, et ses points d’accès répondent `AssistantUnavailable`.

- **Anthropic** : définissez `ACME_AI_PROVIDER=anthropic` et `ACME_AI_API_KEY`. L’assistant interroge `claude-opus-5-5`, sauf si `ACME_AI_MODEL` nomme un autre modèle, sur l’API d’Anthropic, sauf si `ACME_AI_BASE_URL` nomme un proxy.
- **N’importe quel point d’accès compatible OpenAI**, comme un serveur de modèles que vous faites tourner : définissez `ACME_AI_PROVIDER=openai-compatible`, `ACME_AI_BASE_URL` à l’adresse que suit `/chat/completions`, comme `http://127.0.0.1:8000/v1`, et `ACME_AI_MODEL` à l’un de ses modèles. Ajoutez `ACME_AI_API_KEY` s’il en demande une.

Un fournisseur nommé sans les réglages qu’il demande arrête le serveur au démarrage, et l’erreur nomme la variable manquante. Le serveur appelle le fournisseur directement, sans passer par la garde qui limite les appels aux plateformes aux adresses publiques : le point d’accès peut tourner sur la même machine ou sur votre réseau privé.

Chaque espace de travail peut envoyer à l’assistant `ACME_AI_DAILY_REQUESTS` demandes par jour UTC, 100 sans réglage ; `0` n’en laisse passer aucune. Avec la [facturation](#billing), chaque abonnement fixe la sienne à la place. Sans elle, chaque espace de travail en a autant : sur une instance où tout le monde peut s’inscrire, chaque nouvel espace de travail s’ajoute à ce que votre fournisseur peut facturer. Une demande pour laquelle le fournisseur n’a pas pu être joint ne compte pas. Une demande sans réponse au bout de 90 secondes échoue et compte, car le fournisseur a pu la traiter.

Ce que les membres envoient, c’est le texte de la publication, jusqu’à 5 000 caractères, et les réponses sont limitées à 4 096 tokens. Le texte est envoyé comme une donnée, avec des consignes que le texte ne peut pas changer. Le serveur n’écrit jamais le texte ni la réponse dans ses journaux ou ses traces, n’enregistre ni l’un ni l’autre, et n’envoie au fournisseur aucun contexte de trace : ses journaux et ses traces ne nomment que le fournisseur, le modèle, le nombre de tokens et le type d’échec.

## Facturation [#billing]

La facturation est désactivée tant que `STRIPE_SECRET_KEY` n’est pas définie : il n’y a pas d’abonnement, rien n’est limité, et la page de facturation des espaces de travail le dit. Avec une clé, chaque espace de travail commence avec l’abonnement gratuit, et un abonnement Stripe le fait passer à Pro ou Business :

| Abonnement | Canaux | Membres | Publications par mois | Demandes à l’assistant par jour |
| ---------- | ------ | ------- | --------------------- | ------------------------------- |
| Gratuit    | 3      | 2       | 30                    | 10                              |
| Pro        | 10     | 5       | 300                   | 100                             |
| Business   | 30     | 20      | Illimitées            | 500                             |

Les publications comptent dans le mois civil (UTC) où elles partent, une fois programmées : les brouillons et les publications annulées ne comptent pas, une publication repassée en brouillon libère sa place, et une publication renvoyée sur un canal ne compte qu’une fois. Les membres comptent avec les invitations encore en attente au moment d’inviter. Les Pages ou les comptes Instagram cochés ensemble doivent tous avoir de la place, sinon aucun n’est connecté. Une limite s’applique quand on ajoute quelque chose : un espace de travail passé à un abonnement inférieur garde ce qu’il a déjà.

1. Dans Stripe, créez un produit pour chaque abonnement payant avec un prix mensuel, et définissez `STRIPE_PRICE_PRO` et `STRIPE_PRICE_BUSINESS` à leurs identifiants.
2. Ajoutez un webhook vers `PUBLIC_URL/api/auth/stripe/webhook` avec les événements `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted` et `checkout.session.completed`, et définissez `STRIPE_WEBHOOK_SECRET` à son secret de signature. Laissez ce chemin ouvert à Stripe si quelque chose protège le reste de `/api/auth`.
3. Activez l’espace client, où les membres changent de moyen de paiement et résilient. Pour la TVA européenne, activez Stripe Tax et définissez `STRIPE_AUTOMATIC_TAX=true`.

Les propriétaires et les administrateurs ouvrent le paiement et l’espace client depuis la page de facturation de l’espace de travail ; l’équipe qui se fait passer pour eux ne le peut pas. L’état d’un abonnement ne vient que de ses événements de webhook, vérifiés avec le secret de signature : un événement envoyé deux fois n’est enregistré qu’une fois, et un événement plus ancien ne remplace jamais un plus récent. Un abonnement reste payé tant que Stripe retente un paiement échoué ; impayé, suspendu ou résilié, l’espace de travail revient à l’abonnement gratuit. Un espace de travail dont un abonnement peut encore être facturé par Stripe, impayé ou suspendu compris, ne peut pas être supprimé, ni le compte de son seul membre, tant que l’abonnement n’est pas résilié.

## Captcha [#captcha]

Avec `TURNSTILE_SITE_KEY` et `TURNSTILE_SECRET_KEY`, l’inscription et la demande de réinitialisation du mot de passe demandent un jeton Cloudflare Turnstile : les formulaires montrent le widget, et le serveur vérifie chaque jeton auprès de Cloudflare avant de continuer. La connexion s’appuie sur ses limites de fréquence. Ajoutez votre adresse publique aux noms d’hôte du widget dans Cloudflare. Les clés de test de Cloudflare permettent d’essayer sans vrai widget.

## La ligne de commande et les clients MCP [#mcp]

La [ligne de commande](/cli) se connecte avec un code que l’on approuve à `PUBLIC_URL/device`, et n’a besoin de rien d’autre.

Les [clients MCP](/mcp) se connectent avec OAuth, qui demande `PUBLIC_URL` en HTTPS, ou sur `localhost` pour le développement. Sur une adresse en HTTP simple ailleurs, comme `http://192.168.1.20:3001`, le serveur démarre, journalise un avertissement, et son point d’accès MCP refuse toutes les requêtes.

La plupart des clients MCP s’enregistrent eux-mêmes avant de se connecter, ce que le serveur n’autorise qu’avec `MCP_DYNAMIC_REGISTRATION=true`. N’importe qui peut alors enregistrer un client, sous n’importe quel nom : la page de consentement prévient qu’Acme ne l’a pas vérifié, et indique où il renvoie ensuite.

## Comptes d’équipe [#staff]

L’équipe, le rôle d’administrateur de Better Auth, peut se faire passer pour un membre pendant une heure et bannir des comptes, par les points d’accès d’administration de Better Auth sous `/api/auth/admin/`. Elle ne peut pas supprimer un compte : seul son titulaire le peut, depuis [ses paramètres de compte](/settings#delete-account), ce qui supprime ce qu’Acme conserve à son sujet. Donnez ce rôle à un compte dans la base de données, puis reconnectez-vous :

```sql
UPDATE auth."user" SET role = 'admin' WHERE email = 'vous@example.com';
```

En se faisant passer pour un membre, l’équipe ne peut ni connecter de canaux, ni publier, ni gérer les clés d’API ou la facturation, ni modifier les espaces de travail, ni laisser une application agir pour le membre. Elle peut lire les notifications du membre, mais pas les marquer comme lues ni changer ses préférences d’e-mail. Elle peut demander de l’aide à l’assistant de rédaction dans les espaces de travail du membre, ce qui compte dans les demandes du jour de ces espaces.

## Télémétrie [#telemetry]

Mettez dans `OTEL_EXPORTER_OTLP_ENDPOINT` l’adresse OTLP/HTTP d’un collecteur OpenTelemetry, comme `http://otel-collector:4318`, et le serveur y exporte ses journaux, métriques et traces, en JSON. [Variables d’environnement](/environment-variables#telemetry) liste les autres réglages OpenTelemetry qu’il lit.
