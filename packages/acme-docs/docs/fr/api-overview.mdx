L’application web, la ligne de commande et le point d’accès MCP reposent sur la même API HTTP : tout ce qu’ils font, votre propre code peut le faire aussi.

<Callout type="warning" title="Pas encore stable">
  L’API change à chaque commit jusqu’à la première version. Attendez-vous à des
  points d’accès ajoutés, renommés ou supprimés.
</Callout>

## Un seul contrat [#contract]

L’API est définie une seule fois, dans le paquet `acme-contract`. Le serveur implémente cette définition, les clients en tirent leurs types, et la [référence de l’API](/reference) de cette documentation en est générée : les trois ne peuvent pas diverger.

## URL de base [#base-url]

Les requêtes vont à l’adresse où vous ouvrez Acme, et le chemin de chaque point d’accès commence par `/api` : l’application web transmet `/api/*` au serveur. Dans cette documentation, `https://api.example.com` représente cette adresse ; remplacez-la par la vôtre.

```bash
curl -i https://api.example.com/api/health
```

## Authentification [#authentication]

En dehors des sondes de santé et des documents que les plateformes lisent sur Acme, chaque point d’accès demande l’un de ces moyens :

- **Une clé d’API**, pour les scripts et les intégrations : envoyez-la en `Authorization: Bearer acme_…`. Une clé appartient à un espace de travail et porte une partie des permissions du membre qui l’a créée, jamais plus. Les membres qui peuvent gérer les clés (propriétaires et administrateurs) en créent une avec `POST /api/workspaces/{workspaceId}/api-keys` une fois connectés, et ne voient la clé que dans cette réponse. Une clé peut envoyer 600 requêtes par minute.
- **Un jeton d’accès OAuth**, que la [ligne de commande](/cli) et les [clients MCP](/mcp) obtiennent quand vous les connectez, envoyé de la même façon. Il agit en votre nom, dans la limite de ce que vous avez accepté.
- **Le cookie de session** de l’application web, pour l’application web elle-même. Une requête qui change quelque chose avec lui doit venir de l’origine même de l’application web.

Avec une session ou un jeton OAuth, `GET /api/me` dit qui vous êtes, et liste vos espaces de travail, avec votre rôle et vos permissions dans chacun. Une clé d’API appartient à un espace de travail, pas à une personne, et y reçoit 403.

## Espaces de travail [#workspaces]

Les ressources d’un espace de travail se trouvent sous `/api/workspaces/{workspaceId}/` : `channels`, `posts`, `media`, `assistant` et `api-keys`. La référence de chaque point d’accès nomme la permission qu’il demande, comme `post:schedule` ou `channel:connect`.

| Code | Signification                                                                                |
| ---- | -------------------------------------------------------------------------------------------- |
| 401  | Pas d’identifiants, ou des identifiants qui ne fonctionnent plus.                            |
| 403  | Les identifiants fonctionnent, mais ne permettent pas cette requête, ou le compte est banni. |
| 404  | Aucune ressource de ce nom, ou un espace de travail auquel l’appelant n’appartient pas.      |

Les erreurs répondent par un corps JSON dont `_tag` nomme l’erreur, comme `PostContentInvalid` ou `ConnectFailed`, avec les détails que liste la référence. Les points d’accès de l’assistant de rédaction répondent aussi 429 une fois que l’espace de travail a utilisé ses demandes du jour, 503 quand l’instance n’a pas de fournisseur d’IA, et 502 quand le fournisseur n’a donné aucune réponse que l’assistant puisse utiliser. Sur une instance qui facture, connecter un canal ou programmer une publication pour lesquels l’abonnement de l’espace de travail n’a plus de place répond 402 `PlanLimitReached`, qui nomme la limite (`limit`) ; `GET /api/workspaces/:workspaceId/billing` montre l’abonnement, ce qu’il permet et ce que l’espace de travail en utilise.

## Votre compte [#me]

Ce qui vous appartient, plutôt qu’à un espace de travail, se trouve sous `/api/me` : qui vous êtes (`GET /api/me`), vos [notifications](/notifications#api) sous `/api/me/notices`, et celles qui partent par e-mail, sous `/api/me/notification-preferences`. Les points d’accès des notifications répondent 403 aux clés d’API, qui appartiennent à un espace de travail, et aux jetons OAuth liés à un seul espace de travail, comme celui d’un client MCP.

## Document OpenAPI [#openapi]

Le serveur publie son document OpenAPI 3.1 à `/openapi.json` sur sa propre adresse, comme `http://localhost:3000/openapi.json` pour un serveur lancé depuis les sources ; l’application web ne le transmet pas. Servez-vous-en pour générer un client dans un autre langage ou pour importer l’API dans un outil HTTP.

## Référence [#reference]

La [référence de l’API](/reference) propose une page par point d’accès, avec ses paramètres, les schémas de requête et de réponse, et des exemples de code ; les pages sont regroupées par tag.
